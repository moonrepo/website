<Callout>
  Requires the `env` Cargo feature, which is enabled by default.
</Callout>

Settings can also inherit values from environment variables via the `#[setting(env)]` attribute
field. When using this, variables take the _highest_ precedence, and are merged as the last layer.

```rust
#[derive(Config)]
struct AppConfig {
	#[setting(default = 3000, env = "PORT")]
	pub port: usize,
}
```

## Container prefixes

If you'd prefer to not define `env` for _every_ setting, you can instead define a prefix on the
containing struct using the `#[config(env_prefix)]` container attribute field. This will define an
environment variable for _all_ direct fields in the struct, in the format of "env prefix + field
name" in uppercase.

For example, the environment variable below for `port` is now `APP_PORT`.

```rust
#[derive(Config)]
#[config(env_prefix = "APP_")]
struct AppConfig {
	#[setting(default = 3000)]
	pub port: usize,
}
```

A derived key is the field's Rust name (or its explicit `rename`) uppercased, and nothing more. It
is deliberately not reshaped by `rename_all`, so changing how a setting is spelled in a config file
never moves its environment variable.

An explicit `#[setting(env)]` is absolute. A prefix is never applied to it, and the two cannot be
combined on the same setting.

### Nested prefixes

`env_prefix` only applies to direct fields, not to nested children, and prefixes are _not_
concatenated between parent and child. Each struct declares its own.

```rust
#[derive(Config)]
#[config(env_prefix = "APP_SERVER_")]
struct AppServerConfig {
	// ...
}

#[derive(Config)]
#[config(env_prefix = "APP_")]
struct AppConfig {
	#[setting(nested)]
	pub server: AppServerConfig,
}
```

A parent can add a prefix for a nested child to read, with `env_prefix` on the field itself. The
child must still declare an `env_prefix` of its own, as that is what opts its fields into being
derived at all, and it fails to compile without one. When variables with both prefixes are set, the
child's own prefix wins.

```rust
#[derive(Config)]
struct AppConfig {
	#[setting(nested, env_prefix = "OVERRIDE_")]
	pub server: AppServerConfig,
}
```

<Callout>
  The parent's prefix is only known at runtime, so it isn't reflected in the
  [schema](../../schema/index.mdx). A derived key appears in a generated [config
  template](../../schema/generator/template.mdx) and in
  [`Config::settings()`](https://docs.rs/schematic/latest/schematic/trait.Config.html#method.settings)
  with the child's own prefix, which always works.
</Callout>

## Enums

The fields of a [named variant](./index.mdx#enum-variants) read environment variables like a
struct's, with `env`, `parse_env`, or an `env_prefix` on the enum, which derives a key for each
field.

```rust
#[derive(Config)]
#[config(env_prefix = "AUTH_")]
#[serde(tag = "type", rename_all = "snake_case")]
enum Auth {
	#[setting(default)]
	None,
	Token {
		// AUTH_TOKEN
		token: String,
	},
	Basic {
		// AUTH_USER
		user: String,
		#[setting(env = "AUTH_PASSWORD")]
		password: String,
	},
}
```

Only the variables of the variant that's been picked (by a source, the default, or the
[tag's variable](#picking-a-variant)) are read, and they're merged over its fields as the last layer.
So with `type: basic` in a config file, `AUTH_TOKEN` does nothing. Because only one variant is ever
picked, variants may share a derived key, like a `path` field in each.

A nested config held by a variant reads its own variables, and an optional enum, like
`Option<Auth>`, that no source provided reads those of its default variant, as an optional struct
does. A parent's `#[setting(nested, env_prefix)]` also applies to an enum, as long as the enum has an
`env_prefix` of its own.

### Picking a variant

A tagged enum, with serde's `tag` (and optionally `content`), also derives a key from its tag, which
picks the variant. Above, `AUTH_TYPE=token` picks `Token`, and `AUTH_TOKEN` then fills it in. Like
any other variable, it takes precedence over the sources, so it replaces a variant a source picked,
while naming the same variant keeps the fields the source set.

- The value is matched against each variant's name (after `rename_all`) and its aliases, exactly as
  serde matches the tag. Any other value fails to load, listing the names it accepts.
- A unit variant, a named variant, or one that only holds nested configs can be picked, as its
  fields are filled in from their defaults and variables. One that holds a plain value, like
  `Path(String)`, can't be.
- An externally tagged or untagged enum has no tag, so variables can only fill in its variants.

The key is reported on the tag in the [schema](../../schema/index.mdx), so TypeScript renders it as
`@env AUTH_TYPE`. A tagged enum without named variants accepts an `env_prefix` too, purely to pick a
variant.

## Parsing values

A variable is parsed into the setting's type with `FromStr`, so its error type must implement
`Display`. That's what's reported when a variable fails to parse, like
`Failed to parse "70000" into u16: number too large to fit in target type.`

To parse a variable another way, like a comma separated list of values, use the
`#[setting(parse_env)]` attribute field. It requires a path to a function to handle the parsing,
which receives the variable value as a single argument.

```rust
#[derive(Config)]
struct AppConfig {
	#[setting(env = "ALLOWED_HOSTS", parse_env = schematic::env::split_comma)]
	pub allowed_hosts: Vec<String>,
}
```

<Callout>
  We provide a handful of built-in parsing functions in the [`env`
  module](https://docs.rs/schematic/latest/schematic/env/index.html). The ones
  that convert values, like `split_comma`, also use `FromStr`.
</Callout>

For example, `FromStr` makes a `bool` setting accept only `true` and `false`. For values like `1`,
`yes`, or `on`, use `schematic::env::parse_bool`, which ignores case, treats an empty variable as
unset, and fails on anything it doesn't recognize.

```rust
#[derive(Config)]
struct AppConfig {
	#[setting(env = "APP_DEBUG", parse_env = schematic::env::parse_bool)]
	pub debug: bool,
}
```

`parse_env` needs a variable to read, so it requires either an `env` on the setting, or an
`env_prefix` on the container. It's a derive-time error otherwise.

## Parse handler function

You can also define your own function for parsing values out of environment variables.

When defining a custom `parse_env` function, the variable value is passed as the 1st argument. A
`None` value can be returned, which will fallback to the previous or default value.

```rust
pub fn custom_parse(var: String) -> ParseEnvResult<ReturnValue> {
	do_parse()
		.map(|v| Some(v))
		.map_err(|e| HandlerError::new(e.to_string()))
}

#[derive(Config)]
struct ExampleConfig {
	#[setting(env = "FIELD", parse_env = custom_parse)]
	pub field: String,
}
```
