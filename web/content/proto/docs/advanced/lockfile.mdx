A lockfile records what each pinned [version specification](<../(fundamentals)/version-spec.mdx>)
resolved to, along with a checksum of what was downloaded, in a `.protolock` file next to the
[`.prototools`](<../(fundamentals)/config.mdx>) that pins it. Commit it, and every machine, including
CI, installs exactly the same versions, and a download that changes after it was locked fails to
install instead of slipping through.

It works like the lockfile of a package manager. You keep writing the pins that are convenient to
maintain, like `node = "24"`, and the lockfile holds the exact version each one resolved to, like
`24.11.0`, until you choose to move it forward. Without a lockfile, `24` resolves to whatever's
newest on each machine at the time it installs.

## Enabling lockfiles

Lockfiles are opt-in, per [`.prototools`](<../(fundamentals)/config.mdx>). Enable the
[`lockfile`](<../(fundamentals)/config.mdx#lockfile>) setting in a project's
[`.prototools`](<../(fundamentals)/config.mdx>), then install its tools:

```toml title=".prototools"
node = "24"
pnpm = "10"

[settings]
lockfile = true
```

```shell
$ proto install
```

[`proto install`](../commands/install.mdx) creates the `.protolock`, with a record for each tool it
installed. Commit both files. `lockfile` isn't a
[security-sensitive setting](<../(fundamentals)/trust.mdx#security-sensitive-settings>), so the
lockfile is used as soon as the repository is cloned, without [trusting](<../(fundamentals)/trust.mdx>)
it.

A few rules apply to the setting:

- **Project files only** - It's ignored in your user `~/.prototools` and the global
  `~/.proto/.prototools`, so pins in those files are never locked.
- **Not inherited** - Each [`.prototools`](<../(fundamentals)/config.mdx>) enables its own lockfile.
  Enabling it at the root of a repository doesn't lock the pins of a nested
  [`.prototools`](<../(fundamentals)/config.mdx>), like one in a package of a monorepo, which needs
  its own `lockfile = true`.

<Callout type="warning">
  A `.protolock` belongs to the [`.prototools`](<../(fundamentals)/config.mdx>)
  next to it. When that file doesn't enable `lockfile`, or doesn't exist, proto
  deletes the `.protolock` the next time it loads configuration from that
  directory. Disabling the setting removes the lockfile.
</Callout>

## How it works

### Scope

Each [`.prototools`](<../(fundamentals)/config.mdx>) that enables `lockfile` owns the `.protolock` in
the same directory, and a tool's records go to exactly one of them:

- **Pinned tools** - The lockfile of the closest [`.prototools`](<../(fundamentals)/config.mdx>) that
  pins the tool. If that file doesn't enable a lockfile, the tool isn't locked, even when a parent
  directory's file does.
- **Ad-hoc installs** - A tool that no file pins, like one installed with
  [`proto install deno 2`](../commands/install.mdx) to try it out, is recorded in the lockfile of the
  closest directory with a [`.prototools`](<../(fundamentals)/config.mdx>), if it has one enabled.

For example, in a monorepo with a locked root, and a package that pins an older Node.js:

```text
monorepo/
├── .prototools      # node = "24", pnpm = "10", lockfile = true
├── .protolock
└── packages/
    └── legacy/
        └── .prototools  # node = "20"
```

Within `packages/legacy`, pnpm is locked by `monorepo/.protolock`, but Node.js 20 isn't locked at all,
as the file that pins it doesn't enable a lockfile. Add `lockfile = true` to
`packages/legacy/.prototools` to lock it in its own `packages/legacy/.protolock`.

#### Environment scopes

In [environment mode](<../(fundamentals)/config.mdx#environment-mode>), each environment file has a
lockfile of its own: `.prototools.production` is locked to `.protolock.production`. An environment
file inherits `lockfile` from the [`.prototools`](<../(fundamentals)/config.mdx>) in the same
directory, unless it sets the setting itself.

The same rules decide where records go. With `PROTO_ENV=production`, a tool pinned in
`.prototools.production` is recorded in `.protolock.production`, while a tool that's only pinned in
the base [`.prototools`](<../(fundamentals)/config.mdx>) stays in `.protolock`. Ad-hoc installs
aren't environment specific, so they always go to the base `.protolock`.

### Records

A `.protolock` is a TOML file with a list of records per tool. Each record locks one specification
on one platform:

```toml title=".protolock"
# Generated by proto. Do not modify!

[[tools.node]]
os = "linux"
arch = "x64"
libc = "gnu"
spec = "~24"
version = "24.11.0"
checksum = "sha256:a6d3f2c9e4b0..."

[[tools.node]]
os = "macos"
arch = "arm64"
spec = "~24"
version = "24.11.0"
checksum = "sha256:1f0c7b2e8d93..."
```

- `spec` - The specification that was resolved, as written in
  [`.prototools`](<../(fundamentals)/config.mdx>), in its normalized form. A partial version like
  `24` is normalized to the requirement `~24`.
- `version` - The version it resolved to.
- `os`, `arch`, and `libc` - The platform the record was created on. `libc` (`gnu` or `musl`) is
  only recorded on Linux, where tools are commonly built for both.
- `checksum` - The checksum of the downloaded archive, prefixed with its algorithm, like `sha256:`
  or `sha512:`. For tools that publish signatures instead, it's the key that verified the download.
  See [checksum verification](./checksums.mdx).
- `variant` <VersionLabel version="0.64.0" /> - The build that was downloaded, for tools that
  publish more than one for the same platform. See [variants](#variants).
- `backend` - The [backend](<../(fundamentals)/(plugin)/backend.mdx>), for tools that are installed
  through one.

The version applies to every platform, but each platform downloads a different archive, with a
different checksum, so each one gets its own record. Tools whose download is the same everywhere,
like npm, Kotlin, and Poetry, have a single record without a platform. And some tools aren't
recorded at all, as there's no download to lock: Rust, which is installed with rustup, and tools from
the built-in `asdf`, `cargo`, and `npm` backends, which are installed by another program.

The file is written by proto, so don't edit it by hand. Change the pins in
[`.prototools`](<../(fundamentals)/config.mdx>) instead, and let the
[lockfile-aware commands](#lockfile-aware-commands) update it.

#### Variants

<VersionLabel version="0.64.0" /> Some tools publish more than one build for the
same platform, and their plugin picks the one that suits your machine. Bun, for
example, has a `baseline` build for x64 CPUs without AVX2, and Swift publishes a
toolchain per Linux distribution. Two machines with the same operating system
and architecture can therefore download different archives, with different
checksums.

So each build gets a record of its own, with its name in `variant`. The default build has no
variant, so most lockfiles never contain one.

```toml title=".protolock"
[[tools.bun]]
os = "linux"
arch = "x64"
libc = "gnu"
spec = "~1.3"
version = "1.3.2"
checksum = "sha256:3b8f6a2d71c0..."

[[tools.bun]]
os = "linux"
arch = "x64"
libc = "gnu"
variant = "baseline"
spec = "~1.3"
version = "1.3.2"
checksum = "sha256:c94e1d07ab52..."
```

When a machine downloads a build that hasn't been locked yet, its archive can't be compared to the
other build's checksum, so proto adds a record for it instead of failing, like it does for
[a new platform](#version-resolution). Commit that change too.

### Version resolution

Whenever proto resolves a pinned specification, it checks the lockfile that applies to the tool
first. That includes [`proto install`](../commands/install.mdx), [`proto run`](../commands/run.mdx),
and therefore every [shim](<../(fundamentals)/workflows.mdx#shims>), so the version you run matches
the version you installed. proto looks for a record with the same specification (and backend), and:

1. **A record for the current platform** - Its version is used, instead of resolving the
   specification against the available versions.
2. **Only records for other platforms** - The version is inherited from them (the highest, if they
   differ), so every platform converges on the same version. Installing it adds a record for the
   current platform, with its own checksum, which you should commit too.
3. **No record** - The specification is resolved as usual, to the newest matching version, and
   installing it adds a record.

To move a specification forward, re-resolve it and replace its record with `--update-lockfile`:

```shell
# Re-resolve node = "24" to the newest 24.x release
$ proto install node --update-lockfile
```

Changing the pin itself updates the lockfile too. [`proto pin`](../commands/pin.mdx) removes the
records of the previous specification, or with `--resolve`, migrates them to the version it pinned,
as does [`proto outdated --update`](../commands/outdated.mdx). When the version changes, the old
checksums are dropped, and the next [`proto install`](../commands/install.mdx) on each platform
records new ones. Or record them all at once, without installing anything, with
[`proto lock`](#locking-without-installing).

### Checksum verification

Every install computes a checksum of the downloaded archive, after verifying it against the
[checksum or signature](./checksums.mdx) that the tool publishes. When the lockfile has a record for
the version on the current platform, proto then compares the two, and fails the install when they
differ:

```text
Checksum mismatch for https://nodejs.org/dist/v24.11.0/node-v24.11.0-darwin-arm64.tar.xz!
Received sha256:9b1e... but expected sha256:1f0c...
```

A mismatch means the archive isn't the one that was locked. Perhaps the release was re-published, a
mirror serves a different file, or the download was tampered with. Find out why before replacing
the record with `--update-lockfile`. A record that doesn't match the current operating system,
architecture, or libc fails the same way.

This is what makes a lockfile more than a list of versions. For a tool that doesn't publish
checksums at all, proto records a SHA-256 checksum of its first download, so every later install is
compared against that one. Installing a version in a different way than it was locked, like building
it from source instead of downloading a prebuilt, skips the comparison, as the files differ.

### Orphaned records

Records can outlive the pins they were created for, like when you edit
[`.prototools`](<../(fundamentals)/config.mdx>) by hand, changing `node = "24"` to `node = "25"`.
The records for `~24` are now orphaned. After every [`proto install`](../commands/install.mdx) and
[`proto uninstall`](../commands/uninstall.mdx), proto removes them: a record is pruned, on every
platform, when its tool is pinned in the [`.prototools`](<../(fundamentals)/config.mdx>) that owns the
lockfile, but its specification no longer matches that pin. Records for ad-hoc installs are never
pruned, as nothing pins them.

To check a lockfile for orphaned records, duplicates, and records without a resolved version, run
[`proto diagnose`](../commands/diagnose.mdx).

## Locking without installing

<VersionLabel version="0.64.0" /> Installing is how records usually get into a
lockfile, so a lockfile only knows about the platforms that someone has
installed on. If your team develops on macOS and CI runs on Linux, the Linux
records don't exist until a Linux machine installs, which is too late if CI is
[immutable](#immutable-lockfiles).

[`proto lock`](../commands/lock.mdx) fills in those records without installing anything. For each
pinned tool, it resolves the version (from the lockfile first, like an install does), downloads the
tool's prebuilt archive for the platform, verifies it against the checksum the tool publishes, and
writes a record. Nothing is unpacked or installed, and each download is deleted once it's verified.

```shell
# Lock every pinned tool, for this platform and every platform already locked
$ proto lock

# Lock a single tool
$ proto lock node

# Lock macOS on Apple silicon and Linux on x64, from any machine
$ proto lock --platform arm64-macos,x64-linux
```

Without `--platform`, proto locks the current platform, plus every platform that already has a
record for the tool. That's the quick way to fill in the checksums that changing a pin drops, like
after [`proto outdated --update`](../commands/outdated.mdx), as every platform moves to the new
version in one go. With `--platform`, proto locks exactly the platforms you list, instead.

A platform is written as `<arch>-<os>`, like `x64-linux` or `arm64-macos`, with an optional libc on
Linux, like `x64-linux-musl`. The operating system can come first too, as in `linux-x64-musl`, and
Rust target triples like `x86_64-unknown-linux-gnu` work as well. Every platform is locked to the
same version, so they can't drift apart.

A few things to know:

- **Already locked is skipped** - A platform that already has a record with a checksum, for the same
  version, isn't downloaded again. Pass `--force` to download it anyway, and verify it against the
  locked checksum, which fails on a mismatch. It's a handy way to audit a lockfile.
- **Some tools can't be locked** - Tools that install natively, like Rust and tools from
  [backends](<../(fundamentals)/(plugin)/backend.mdx>), and tools that
  [build from source](../guides/build-from-source.mdx), can only be verified by installing them, so
  they're skipped. So are tools pinned in a [`.prototools`](<../(fundamentals)/config.mdx>) without a
  lockfile.
- **Other platforms get the default build** - A plugin can't inspect a machine it isn't running on,
  so when locking another platform, it downloads the default [variant](#variants). A machine that
  needs another build, like Bun's `baseline`, adds a record for it when it installs.
- **It writes to the lockfile** - [Orphaned records](#orphaned-records) are pruned afterwards, like
  after an install, and the command fails when `PROTO_IMMUTABLE_LOCKFILE` is set.

The command prints a table of each tool and platform, with whether it was locked, already locked,
skipped (and why), or failed. If any fail, it exits with a non-zero code.

## Immutable lockfiles

In CI, the lockfile should be the source of truth, not something that the build updates. Pass
`--immutable-lockfile` to [`proto install`](../commands/install.mdx), or set the
`PROTO_IMMUTABLE_LOCKFILE` environment variable, to install from the lockfile without ever changing
it:

```shell
$ proto install --immutable-lockfile
```

In this mode, proto never writes to the lockfile, and instead of adding a record, it fails when:

- A pinned specification has no record, because the lockfile is out of date, or isn't enabled for
  the [`.prototools`](<../(fundamentals)/config.mdx>) that pins it.
- Only other platforms have a record, so the download can't be verified against a checksum for this
  platform.
- Only other [variants](#variants) <VersionLabel version="0.64.0" /> of the version have a record
  for this platform, so the build this machine downloaded can't be verified. The error names the
  build that's missing.

Checksum mismatches fail as always. Each error explains the fix: run
[`proto install`](../commands/install.mdx) without `--immutable-lockfile`, on the platform in
question, and commit the changes. The missing platform error is easy to hit when developers use
macOS and CI runs on Linux, so before making CI immutable, lock Linux from your own machine with
[`proto lock --platform x64-linux`](#locking-without-installing), and commit the result.
`--immutable-lockfile` can't be combined with `--pin` or `--update-lockfile`, as both write to the
lockfile.

See the [CI guide](../guides/ci.mdx#immutable-lockfiles) for a complete setup.

## Lockfile-aware commands

The following commands read or update lockfiles:

| Command                                                                           | Lockfile behavior                                                                                                                   |
| --------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| [`proto install`](../commands/install.mdx)                                        | Resolves versions from records, verifies checksums, adds records, and prunes orphaned ones                                          |
| [`proto install --update-lockfile`](../commands/install.mdx)                      | Re-resolves specifications, ignoring their records, and replaces them                                                               |
| [`proto install --immutable-lockfile`](../commands/install.mdx)                   | Resolves and verifies from records only, and fails instead of writing                                                               |
| [`proto lock`](../commands/lock.mdx) <VersionLabel version="0.64.0" />            | Resolves versions, and adds records for one or many platforms without installing, then prunes orphaned ones                         |
| [`proto pin`](../commands/pin.mdx)                                                | Removes the records of the previous specification, or migrates them with `--resolve`                                                |
| [`proto unpin`](../commands/unpin.mdx)                                            | Removes the records of the unpinned specification                                                                                   |
| [`proto outdated`](../commands/outdated.mdx)                                      | Shows the locked version of each tool, and with `--update`, migrates records to the updated specifications                          |
| [`proto uninstall`](../commands/uninstall.mdx)                                    | Removes the current platform's records pinned to the uninstalled version, or every record of the tool when uninstalling it entirely |
| [`proto status`](../commands/status.mdx)                                          | Shows the locked version of each tool                                                                                               |
| [`proto versions`](../commands/versions.mdx)                                      | Labels locked versions                                                                                                              |
| [`proto run`](../commands/run.mdx), [`proto bin`](../commands/bin.mdx), and shims | Resolve versions from records                                                                                                       |
| [`proto debug config`](../commands/debug/config.mdx)                              | Prints each lockfile after the config that owns it                                                                                  |
| [`proto diagnose`](../commands/diagnose.mdx)                                      | Reports orphaned, duplicate, and unresolved records                                                                                 |
