[npm](https://www.npmjs.com/) is the package manager that ships with Node.js, and the default way to
install dependencies and run `package.json` scripts in JavaScript projects. It's a
[built-in tool](<../(fundamentals)/(plugin)/tool.mdx#built-in-tools>) with the `npm` ID, so it
works without configuring a plugin.

proto downloads npm from the npm registry, and manages it separately from [Node.js](./node.mdx),
so a project can pin the npm version it needs, whatever Node.js version it runs on. It detects the
version to use from [`.prototools`](<../(fundamentals)/config.mdx>) or `package.json`, and runs it
with the Node.js version detected for the current directory. npm is written in JavaScript, so it
requires the [`node`](./node.mdx) tool.

## Prerequisites

- **Node.js** - npm requires the [`node`](./node.mdx) tool, which must have a version configured
  too, like a pin in [`.prototools`](<../(fundamentals)/config.mdx>). Installing npm fails without
  one, and when [`proto install`](../commands/install.mdx) installs every pinned tool, Node.js is
  installed first.
- **A supported platform** - npm is supported on macOS, Linux, and Windows, on x64 or arm64, even
  though Node.js runs on more. Other platforms fail with an unsupported platform error.
- **Bash** - On macOS and Linux, the `npm` and `npx` executables are launched with small Bash
  scripts, so `bash` must be installed. Minimal container images, like Alpine, don't include it by
  default.

## Installation

npm requires Node.js, so pin both. Install npm with [`proto install`](../commands/install.mdx),
and pin a version with [`proto pin`](../commands/pin.mdx), or with the `--pin` option while
installing:

```shell
# Install the detected version, or the latest when none is detected
$ proto install npm

# Install the newest npm 11 release, and pin it to the closest .prototools
$ proto install npm 11 --pin

# Pin a version without installing it
$ proto pin npm 11

# Install the npm version that ships with the detected Node.js version
$ proto install npm bundled

# Run it
$ proto run npm -- --version
```

```toml title=".prototools"
node = "24.11.0"
npm = "11.6.2"
```

Besides versions and ranges, npm supports the `latest`
[alias](<../(fundamentals)/version-spec.mdx#built-in-aliases>), but not `canary`. Versions are the
releases of the [`npm`](https://www.npmjs.com/package/npm) package, and `latest` follows its
`latest` dist-tag, falling back to the highest stable version when that tag points to a
pre-release. See [versions & aliases](#versions--aliases) for the aliases that npm provides.

npm provides three [executables](<../(fundamentals)/(plugin)/tool.mdx#executables>), each with a
[shim](<../(fundamentals)/workflows.mdx#shims>), but no
[binary](<../(fundamentals)/workflows.mdx#binary-linking>), as they need Node.js to run:

- `npm` - The primary executable.
- `npx` - Runs a package's executable, from `node_modules/.bin`, or fetched from the registry.
- `node-gyp` - The copy of [node-gyp](https://github.com/nodejs/node-gyp) that ships with npm, for
  building native addons.

## Configuration

npm is configured in the `[tools.npm]` table of [`.prototools`](<../(fundamentals)/config.mdx>).
Like other [tool settings](<../(fundamentals)/config.mdx#tools>), these only apply from a
project's [`.prototools`](<../(fundamentals)/config.mdx>) once it's
[trusted](<../(fundamentals)/trust.mdx>). Along with the settings below, the tool settings that
every tool supports apply too, like `env`, and
[`versions-source`](<../(fundamentals)/config.mdx#tools-versions-source>) to list versions from a
mirror, though dist-tag aliases like `next-11` are only available from the registry.

### `registry-url`

<TypeLabel type="string" /> - The npm registry to list versions from, and
download npm from, without a trailing slash. Defaults to
`https://registry.npmjs.org`.

Set it to use a private registry or mirror, which is authenticated with your `.npmrc` credentials
(see [private registries](#private-registries)).

```toml title=".prototools"
[tools.npm]
registry-url = "https://npm.corp.internal"
```

### `dist-url`

<TypeLabel type="string" /> - The URL template to download npm's tarball from.
Defaults to `{registry}/{package}/-/{package_without_scope}-{version}.tgz`.

The default is the npm registry's tarball URL, and the template supports the following
placeholders:

- `{registry}` - The [`registry-url`](#registry-url) setting.
- `{package}` and `{package_without_scope}` - The package name, `npm`.
- `{version}` - The version to install, like `11.6.2`.
- `{file}` - The tarball's file name, like `npm-11.6.2.tgz`.

```toml title=".prototools"
[tools.npm]
dist-url = "https://artifacts.corp.internal/npm/{version}/{file}"
```

The credentials for [`registry-url`](#registry-url) are sent with the download too, even when this
URL points to another host, so only point it at hosts you trust.

### `shared-globals-dir`

<TypeLabel type="boolean" /> - Install global packages into
`~/.proto/tools/node/globals`, a directory shared by every Node.js version, and
by pnpm, Yarn, and Nub when they enable this setting, instead of into the
directory of the Node.js version that runs npm. Defaults to `false`.

This setting is experimental. See [global packages](#global-packages).

```toml title=".prototools"
[tools.npm]
shared-globals-dir = true
```

## Core features

### Execution environment

Whenever npm runs through proto, with a [shim](<../(fundamentals)/workflows.mdx#shims>),
[`proto run`](../commands/run.mdx), [`proto exec`](../commands/exec.mdx), or
[shell activation](<../(fundamentals)/workflows.mdx#shell-activation>), proto:

- Adds the directory of the Node.js version detected for the directory to `PATH`, after npm's own,
  and sets `PROTO_NODE_VERSION` to that version. So npm, and every script it runs, like `npm test`
  or a `postinstall` script, uses that version of `node`. This only happens with shims and
  [`proto run`](../commands/run.mdx). With [`proto exec`](../commands/exec.mdx), pass `node` too,
  and with shell activation, `node` is activated from its own pin in
  [`.prototools`](<../(fundamentals)/config.mdx>).
- Sets `PREFIX`, which npm uses as its global prefix, to `~/.proto/tools/node/globals` (or its
  `bin` directory on Windows), when [`shared-globals-dir`](#shared-globals-dir) is enabled. With
  shell activation, it's exported into your shell session.

### Global packages

By default, npm installs global packages into its prefix, which is the directory of the Node.js
version that runs it, like `~/.proto/tools/node/24.11.0`. Their executables are linked into its
`bin` directory on macOS and Linux, and into the directory itself on Windows. Each Node.js version
therefore has its own global packages, so after switching versions, install them again, or enable
[`shared-globals-dir`](#shared-globals-dir).

proto looks for their executables in the following directories, in order, skipping any whose
environment variable isn't set:

1. `$PREFIX/bin`, when `PREFIX` is set.
2. `~/.proto/tools/node/<version>/bin`, for the Node.js version in `PROTO_NODE_VERSION`, when set.
3. `$NPM_CONFIG_PREFIX/bin`, then `$npm_config_prefix/bin`, when set.
4. `~/.proto/tools/node/globals/bin`, the [shared directory](#shared-globals-dir).

On Windows, the first three are used without `/bin`, and when a variable already points to a `bin`
directory, it's used as-is. With [`shared-globals-dir`](#shared-globals-dir) enabled, only the
shared directory is used.

proto adds these directories to `PATH` whenever npm runs through proto, and with
[shell activation](<../(fundamentals)/workflows.mdx#shell-activation>), along with the Node.js
version's directory, so the executables of global packages, like `tsc`, are found. With shims
alone, enable [`shared-globals-dir`](#shared-globals-dir) and add `~/.proto/tools/node/globals/bin`
to your `PATH` yourself, as shims only exist for npm's own executables.

```shell
# Install a package globally
$ npm install -g typescript

# Print the executables directory of the detected Node.js version, where tsc is linked by default
$ proto bin node --dir exes

# Print the directories that proto looks in
$ proto bin npm --dir globals --all
```

For a CLI that you want in every project, whatever its Node.js version, the
[npm backend](../backends/npm.mdx) is an alternative:
[`proto install npm:typescript`](../commands/install.mdx) installs the package as its own tool, with
a version you can pin, and shims for its executables. The backend runs on this tool, so it needs
`npm` configured too.

### Version files

Besides [`.prototools`](<../(fundamentals)/config.mdx>), proto
[detects](<../(fundamentals)/detection.mdx#4-ecosystem-files>) an npm version from the following
fields of `package.json`, checked in this order, and skips any `package.json` within
`node_modules`:

1. `devEngines.packageManager` - An entry named `npm`, as an object or within a list. Only versions
   and ranges are read.
2. `packageManager` - Like `npm@11.6.2`, the field that Corepack uses. A hash, like
   `+sha512.…`, is ignored, and a bare `npm` means `latest`.
3. `volta.npm` - Including from the file that `volta.extends` points to.
4. `engines.npm` - Only versions and ranges are read.

The first field with a valid version for `npm` wins. A field that proto can't parse, like a URL in
`packageManager`, is skipped in favor of the next one, and fields for other package managers are
ignored. In the following example, npm `11.6.2` is used:

```json title="package.json"
{
  "packageManager": "npm@11.6.2",
  "engines": {
    "node": ">=22",
    "npm": ">=10"
  }
}
```

`engines.npm` is often a broad compatibility range, like `>=10`, which proto treats as the version
to run. To only use explicit pins, change the
[detection strategy](<../(fundamentals)/detection.mdx#detection-strategies>).

To pin a version in `package.json` instead of [`.prototools`](<../(fundamentals)/config.mdx>), pass
`--tool-native` to [`proto pin`](../commands/pin.mdx). It writes an entry named `npm` to
`devEngines.packageManager`, alongside any other package manager, and
[`proto unpin --tool-native`](../commands/unpin.mdx) removes it again. The `package.json` must
already exist, and as `devEngines` doesn't support aliases, pass `--resolve` to pin one.

```shell
# Pin to devEngines in package.json
$ proto pin npm 11.6.2 --tool-native

# Pin the version that latest resolves to
$ proto pin npm latest --resolve --tool-native
```

## Ecosystem

### Versions & aliases

The plugin provides the following aliases, in addition to proto's
[built-in aliases](<../(fundamentals)/version-spec.mdx#built-in-aliases>):

- `bundled` - The version that ships with the detected Node.js version (see
  [bundled npm](#bundled-npm)).
- `<dist-tag>` - The version that any other dist-tag of the `npm` package points to, like
  `next-11`, which follows the newest npm 11 release.

Aliases resolve to a newer version as releases are published. To pin the version an alias
currently resolves to, pass `--resolve` to [`proto pin`](../commands/pin.mdx).

```shell
# Pin the version that next-11 resolves to
$ proto pin npm next-11 --resolve

# List the versions, and the dist-tag aliases with the versions they point to
$ proto versions npm --aliases
```

### Bundled npm

Every Node.js release ships with a version of npm, inside the Node.js version's directory. The `npm`
tool is installed separately, into `~/.proto/tools/npm`, and when it's configured for a directory,
it takes precedence over the copy in Node.js. Without it, the copy in Node.js is still available
wherever Node.js's directory is on `PATH`, like with shell activation and
[`proto exec`](../commands/exec.mdx), but not through shims.

To use the npm that ships with your Node.js version, while still managing it with proto, pin the
`bundled` alias. It resolves to the npm version of the Node.js version detected for the current
directory, so npm moves along with Node.js whenever you upgrade it. Then enable Node.js's
[`bundled-npm`](./node.mdx#bundled-npm) setting, which installs that npm version whenever you
install Node.js:

```toml title=".prototools"
node = "24.11.0"
npm = "bundled"

[tools.node]
bundled-npm = true
```

```shell
# Install Node.js 24.11.0, and the npm version that ships with it
$ proto install

# Skip the bundled npm for a single install
$ proto install node 24 -- --no-bundled-npm
```

[`bundled-npm`](./node.mdx#bundled-npm) installs npm, but doesn't pin it, so pair it with
`npm = "bundled"`. Pin an explicit version instead when a project needs a specific npm release,
independent of Node.js upgrades.

### Private registries

To install npm from a private registry or mirror, instead of the public registry, set
[`registry-url`](#registry-url). proto doesn't read the `registry` setting from `.npmrc`, so set it
even when npm itself is already configured for that registry.

When the registry requires authentication, proto reads its credentials from `.npmrc`, like npm
does: the project's `.npmrc`, next to the closest `package.json`, takes precedence over your user
`~/.npmrc`. Credentials are matched to the registry's URL, and sent with every request for versions
and downloads:

- `_authToken` - Sent as a bearer token.
- `username` and `_password`, or `_auth` - Sent with basic authentication.

```ini title=".npmrc"
//npm.corp.internal/:_authToken=<token>
```

This only affects how proto downloads npm itself. Once installed, npm reads `.npmrc` on its own.

## Troubleshooting

### `npm install -g npm` doesn't change the version

proto runs the npm version it detects for the directory, while a global install only adds another
copy to npm's global prefix, like the Node.js version's directory. To upgrade, install and pin a
newer version, like with [`proto install npm latest --pin`](../commands/install.mdx).

### A global package's command isn't found

With shims alone, the executables of global packages aren't on `PATH`. See
[global packages](#global-packages).

### `bundled` installs the latest npm

When proto can't find the Node.js version to look up, like when Node.js isn't installed yet, or is
a canary build, `bundled` falls back to `latest`. Install Node.js first, or pin an explicit npm
version.

### Downloads from a private registry fail

proto doesn't read the `registry` setting from `.npmrc`, so it downloads from
[`registry-url`](#registry-url), with the `.npmrc` credentials for that host. Check that
`registry-url` is set, and that your `.npmrc` has credentials for its host (see
[private registries](#private-registries)).

## Caveats

- **Published hashes aren't verified** - proto doesn't verify npm's downloads against the registry's
  integrity hashes, so it [records a checksum](../advanced/checksums.mdx#tools-without-checksums)
  from the first download, and with a [lockfile](../advanced/lockfile.mdx), later installs must
  match it.
- **A single lockfile record** - The tarball is the same on every platform, so a
  [lockfile](../advanced/lockfile.mdx#records) has a single record for npm, shared by every
  operating system and architecture.
- **`bundled` needs `nodejs.org`** - The `bundled` alias looks up which npm ships with each Node.js
  release on `nodejs.org`, so it needs access to that host, even when Node.js itself downloads from
  a mirror.
- **`PREFIX` leaks to other tools** - With [`shared-globals-dir`](#shared-globals-dir), `PREFIX` is
  set for npm and every script it runs, and with shell activation, for your whole shell session.
  Other tools that read `PREFIX`, like many Makefiles, see it too.
