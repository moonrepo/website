[npm](https://www.npmjs.com/) is the package manager that ships with Node.js, and the default way to
install dependencies and run `package.json` scripts in JavaScript projects. It's a
[built-in tool](<../(fundamentals)/(plugin)/tool.mdx#built-in-tools>) with the `npm` ID, managed
separately from [Node.js](./node.mdx), so a project can pin the npm version it needs, whatever
Node.js version it runs on.

proto downloads npm from the npm registry, detects the version to use from
[`.prototools`](<../(fundamentals)/config.mdx>) or `package.json`, and runs it with the Node.js
version detected for the current directory. npm is written in JavaScript, so it requires the
[`node`](./node.mdx) tool.

## Prerequisites

- **Node.js** - npm [requires](<../(fundamentals)/config.mdx#tools-requires>) the `node` tool, which
  must have a version configured too, like a pin in [`.prototools`](<../(fundamentals)/config.mdx>).
  Installing npm fails without one, and when [`proto install`](../commands/install.mdx) installs
  every pinned tool, Node.js is installed first.
- **A supported platform** - macOS, Linux, or Windows, on x64 or arm64. Other operating systems and
  architectures fail with an unsupported error, even where Node.js itself runs.
- **Bash** - On macOS and Linux, npm's executables are launched with small Bash scripts, so `bash`
  must be installed. Minimal container images, like Alpine, don't include it by default.

## Installation

Install npm with [`proto install`](../commands/install.mdx), and pin a version with
[`proto pin`](../commands/pin.mdx), or with the `--pin` option while installing:

```shell
# Install the detected version, or the latest when none is detected
$ proto install npm

# Install the newest npm 11 release, and pin it to the closest .prototools
$ proto install npm 11 --pin

# Install the npm version that ships with the detected Node.js version
$ proto install npm bundled

# Run it
$ proto run npm -- --version
```

```toml title=".prototools"
node = "24.11.0"
npm = "11.6.2"
```

Versions are the releases of the [`npm`](https://www.npmjs.com/package/npm) package, and its
dist-tags are [aliases](<../(fundamentals)/version-spec.mdx#aliases>), like `next-11`. `latest`
follows the `latest` dist-tag, falling back to the highest stable version when that tag points to a
pre-release. npm also supports `bundled`, the version that ships with Node.js (see
[bundled npm](#bundled-npm)). The `canary` spec isn't supported.

npm provides three [executables](<../(fundamentals)/(plugin)/tool.mdx#executables>), each with a
[shim](<../(fundamentals)/workflows.mdx#shims>), but no
[binary](<../(fundamentals)/workflows.mdx#binary-linking>), as they need Node.js to run:

- `npm` - The primary executable.
- `npx` - Runs a package's executable, from `node_modules/.bin`, or fetched from the registry.
- `node-gyp` - The copy of [node-gyp](https://github.com/nodejs/node-gyp) that ships with npm, for
  building native addons.

## Configuration

npm is configured in the `[tools.npm]` table of [`.prototools`](<../(fundamentals)/config.mdx>).
Like other tool settings, its settings only apply from a project's
[`.prototools`](<../(fundamentals)/config.mdx>) once it's [trusted](<../(fundamentals)/trust.mdx>).
Along with the settings below, the [tool settings](<../(fundamentals)/config.mdx#tools>) that every
tool supports apply too, like `env`, and
[`versions-source`](<../(fundamentals)/config.mdx#tools-versions-source>) to list versions from a
mirror, though dist-tag aliases like `next-11` are only available from the registry.

### `registry-url`

<TypeLabel type="string" /> - The npm registry to list versions from, and
download npm from, without a trailing slash. Defaults to
`https://registry.npmjs.org`. Set it to use a private registry or mirror, which
is authenticated with your `.npmrc` credentials (see [private
registries](#private-registries)).

```toml title=".prototools"
[tools.npm]
registry-url = "https://npm.corp.internal"
```

### `dist-url`

<TypeLabel type="string" /> - The URL template to download npm's tarball from.
Defaults to `{registry}/{package}/-/{package_without_scope}-{version}.tgz`, the
npm registry's tarball URL. Supports the following placeholders:

- `{registry}` - The [`registry-url`](#registry-url) setting.
- `{package}` and `{package_without_scope}` - The package name, `npm`.
- `{version}` - The version to install, like `11.6.2`.
- `{file}` - The tarball's file name, like `npm-11.6.2.tgz`.

```toml title=".prototools"
[tools.npm]
dist-url = "https://artifacts.corp.internal/npm/{version}/{file}"
```

The credentials for [`registry-url`](#registry-url) are sent with the download too, even when this
URL points to another host, so only point it at hosts you trust.

### `shared-globals-dir`

<TypeLabel type="boolean" /> - Install global packages into
`~/.proto/tools/node/globals`, a directory shared by every Node.js version, and
by pnpm, Yarn, and Nub when they enable this setting, instead of into the
directory of the Node.js version that runs npm. Defaults to `false`. This
setting is experimental. See [global packages](#global-packages).

```toml title=".prototools"
[tools.npm]
shared-globals-dir = true
```

## Core features

### Execution environment

Whenever npm runs through a shim, [`proto run`](../commands/run.mdx), or
[`proto exec`](../commands/exec.mdx), the Node.js version detected for the directory is added to its
environment: its directory is put on `PATH`, after npm's own, and `PROTO_NODE_VERSION` is set to
it. So npm, and every script it runs, like `npm test` or a `postinstall` script, uses that version
of `node`.

With [`shared-globals-dir`](#shared-globals-dir) enabled, proto also sets `PREFIX`, which npm uses
as its global prefix, to `~/.proto/tools/node/globals` (or its `bin` directory on Windows). This
applies to [shell activation](<../(fundamentals)/workflows.mdx#shell-activation>) too, which exports
it into your shell session.

### Global packages

By default, npm installs global packages into its prefix, which is the directory of the Node.js
version that runs it, like `~/.proto/tools/node/24.11.0`. Their executables are linked into its
`bin` directory on macOS and Linux, and into the directory itself on Windows. Each Node.js version
therefore has its own global packages, so after switching versions, install them again, or enable
[`shared-globals-dir`](#shared-globals-dir).

proto looks for the executables of global packages in the following directories, in order:

1. `$PREFIX/bin`, when `PREFIX` is set.
2. `~/.proto/tools/node/<version>/bin`, for the Node.js version in `PROTO_NODE_VERSION`, when set.
3. `$NPM_CONFIG_PREFIX/bin`, then `$npm_config_prefix/bin`, when set.
4. `~/.proto/tools/node/globals/bin`, the [shared directory](#shared-globals-dir).

On Windows, the first three are used without `/bin`, and when a variable already points to a `bin`
directory, it's used as-is. With [`shared-globals-dir`](#shared-globals-dir) enabled, only the
shared directory is used.

Whenever npm runs through proto, and with
[shell activation](<../(fundamentals)/workflows.mdx#shell-activation>), proto puts these
directories on `PATH`, along with the Node.js version's directory, so the executables of global
packages, like `tsc`, are found. Shims only exist for npm's own executables, though, so with shims
alone, they aren't on your shell's `PATH`. Use shell activation, or enable
[`shared-globals-dir`](#shared-globals-dir) and add `~/.proto/tools/node/globals/bin` to your
`PATH`.

```shell
# Install a package globally
$ npm install -g typescript

# Print the directory of the detected Node.js version, where it's installed by default
$ proto bin node --dir exes
```

For a CLI that you want in every project, whatever its Node.js version, the
[npm backend](../backends/npm.mdx) is an alternative:
[`proto install npm:typescript`](../commands/install.mdx) installs the package as its own tool, with
a version you can pin, and shims for its executables. The backend runs on this tool, so it needs
`npm` configured too.

### Version files

npm's version is [detected](<../(fundamentals)/detection.mdx#4-ecosystem-files>) from
`package.json` files, skipping any within `node_modules`. The following fields are checked in order,
and the first with a valid version for `npm` wins:

1. `devEngines.packageManager` - An entry named `npm`, as an object or within a list. Only versions
   and ranges are read.
2. `packageManager` - Like `npm@11.6.2`, the field that Corepack uses. A hash, like
   `+sha512.…`, is ignored, and a bare `npm` means `latest`.
3. `volta.npm` - Including from the file that `volta.extends` points to.
4. `engines.npm` - Only versions and ranges are read.

A field that proto can't parse, like a URL in `packageManager`, is skipped in favor of the next one,
and fields for other package managers are ignored. In the following example, npm `11.6.2` is used:

```json title="package.json"
{
  "packageManager": "npm@11.6.2",
  "engines": {
    "node": ">=22",
    "npm": ">=10"
  }
}
```

`engines.npm` is often a broad compatibility range, like `>=10`, which proto treats as the version
to run. To only use explicit pins, change the
[detection strategy](<../(fundamentals)/detection.mdx#detection-strategies>).

To pin a version in `package.json` instead of [`.prototools`](<../(fundamentals)/config.mdx>), pass
`--tool-native` to [`proto pin`](../commands/pin.mdx). It writes an entry named `npm` to
`devEngines.packageManager`, alongside any other package manager, and
[`proto unpin --tool-native`](../commands/unpin.mdx) removes it again. The `package.json` must
already exist, and as `devEngines` doesn't support aliases, pass `--resolve` to pin one.

```shell
# Pin to devEngines in package.json
$ proto pin npm 11.6.2 --tool-native

# Pin the version that latest resolves to
$ proto pin npm latest --resolve --tool-native
```

## Ecosystem

### Bundled npm

Every Node.js release ships with a version of npm, inside the Node.js version's directory. The `npm`
tool is installed separately, into `~/.proto/tools/npm`, and when it's configured for a directory,
it takes precedence over the copy in Node.js. Without it, the copy in Node.js is still available
wherever Node.js's directory is on `PATH`, like with shell activation and
[`proto exec`](../commands/exec.mdx), but not through shims.

To use the npm that ships with your Node.js version, while still managing it with proto, pin the
`bundled` alias. It resolves to the npm version of the Node.js version detected for the current
directory, so npm moves along with Node.js whenever you upgrade it. Then enable Node.js's
[`bundled-npm`](./node.mdx#bundled-npm) setting, which installs that npm version whenever you
install Node.js:

```toml title=".prototools"
node = "24.11.0"
npm = "bundled"

[tools.node]
bundled-npm = true
```

```shell
# Install Node.js 24.11.0, and the npm version that ships with it
$ proto install

# Skip the bundled npm for a single install
$ proto install node 24 -- --no-bundled-npm
```

[`bundled-npm`](./node.mdx#bundled-npm) installs npm, but doesn't pin it, so pair it with
`npm = "bundled"`. Pin an explicit version instead when a project needs a specific npm release,
independent of Node.js upgrades.

### Private registries

To install npm from a private registry or mirror, instead of the public registry, set
[`registry-url`](#registry-url). proto doesn't read the `registry` setting from `.npmrc`, so set it
even when npm itself is already configured for that registry.

When the registry requires authentication, proto reads its credentials from `.npmrc`, like npm
does: the project's `.npmrc`, next to the closest `package.json`, takes precedence over your user
`~/.npmrc`. Credentials are matched to the registry's URL, and sent with every request for versions
and downloads:

- `_authToken` - Sent as a bearer token.
- `username` and `_password`, or `_auth` - Sent with basic authentication.

```ini title=".npmrc"
//npm.corp.internal/:_authToken=<token>
```

This only affects how proto downloads npm itself. Once installed, npm reads `.npmrc` on its own.

## Troubleshooting

- **`npm install -g npm` doesn't change the version** - proto runs the npm version it detects for
  the directory, while a global install only adds another copy to npm's global prefix, like the
  Node.js version's directory. To upgrade, install and pin a newer version, like with
  [`proto install npm latest --pin`](../commands/install.mdx).
- **A global package's command isn't found** - With shims alone, the executables of global packages
  aren't on `PATH`. See [global packages](#global-packages).
- **`bundled` installs the latest npm** - When proto can't find the Node.js version to look up, like
  when Node.js isn't installed yet, or is a canary build, `bundled` falls back to `latest`. Install
  Node.js first, or pin an explicit npm version.
- **Downloads from a private registry fail** - Check that [`registry-url`](#registry-url) is set,
  and that your `.npmrc` has credentials for its host (see
  [private registries](#private-registries)).

## Caveats

- npm's tarballs have no published checksum for proto to verify against, so proto
  [records one](../advanced/checksums.mdx#tools-without-checksums) from the first download. The
  tarball is the same on every platform, so a [lockfile](../advanced/lockfile.mdx#records) has a
  single record for npm, shared by every operating system and architecture.
- The `bundled` alias looks up which npm ships with each Node.js release on `nodejs.org`, so it
  needs access to that host, even when Node.js itself downloads from a mirror.
- With [`shared-globals-dir`](#shared-globals-dir), `PREFIX` is set for npm and every script it
  runs, and with shell activation, for your whole shell session. Other tools that read `PREFIX`,
  like many Makefiles, see it too.
