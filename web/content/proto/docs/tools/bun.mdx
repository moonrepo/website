[Bun](https://bun.sh/) is an all-in-one JavaScript toolkit: a runtime, a package manager, a test
runner, and a bundler, in a single executable. It's a
[built-in tool](<../(fundamentals)/(plugin)/tool.mdx#built-in-tools>) with the `bun` ID, so it works
without configuring a plugin. Since Bun is its own package manager, `bun install` and `bun add` come
with it, and there's no separate tool to pin.

proto downloads Bun's prebuilt releases from GitHub, verifies them against Bun's published
checksums, and picks the build that runs on your machine, like the baseline build for older x64 CPUs
(see [builds](#builds)). Each version provides two
[executables](<../(fundamentals)/(plugin)/tool.mdx#executables>): `bun`, the primary one, and
`bunx`, Bun's equivalent of `npx`, for running a package's executable.

## Prerequisites

- **No other tools** - Bun doesn't require Node.js, or any other proto tool, to install or run.
- **A supported platform** - Bun publishes builds for the following platforms, and installing a
  version that isn't available for yours fails with an error, instead of installing a build that
  can't run:
  - Linux and macOS, on x64 and arm64.
  - Windows on x64 from Bun 1.1, and on arm64 from Bun 1.3.10.
  - FreeBSD on x64 and arm64, from Bun 1.3.14.
  - musl-based Linux distributions, like Alpine, from Bun 1.1.35.

## Installation

Install Bun with [`proto install`](../commands/install.mdx), and pin a version with
[`proto pin`](../commands/pin.mdx), or with the `--pin` option while installing. Besides versions
and ranges, Bun supports proto's built-in `latest` and `canary`
[aliases](<../(fundamentals)/version-spec.mdx#built-in-aliases>) (see
[canary builds](#canary-builds)).

```shell
# Install the detected version, or the latest when none is detected
$ proto install bun

# Install the newest 1.3 release, and pin it to the closest .prototools
$ proto install bun 1.3 --pin

# Pin a version, without installing it
$ proto pin bun 1.3
```

```toml title=".prototools"
bun = "~1.3"
```

## Configuration

### `dist-url`

<TypeLabel type="string" /> - The URL template that release archives are
downloaded from, like an internal mirror of Bun's GitHub releases. Defaults to
`https://github.com/oven-sh/bun/releases/download/bun-v{version}/{file}`.
Supports the following placeholders:

- `{version}` - The version being installed, like `1.3.2`. For [canary builds](#canary-builds), it's
  `canary`, and a `bun-v` before it is removed, matching the `canary` release on GitHub.
- `{file}` - The archive's file name, in the format `bun-<os>-<arch>[-musl][-baseline].zip`, like
  `bun-linux-x64.zip` or `bun-darwin-aarch64.zip`. Checksums are downloaded from the same URL, with
  `{file}` replaced by `SHASUMS256.txt`, so a mirror must host that file next to the archives.

```toml title=".prototools"
[tools.bun]
dist-url = "https://mirror.internal/bun/bun-v{version}/{file}"
```

This only changes where archives are downloaded from. Available versions are still listed from the
tags of `https://github.com/oven-sh/bun`, like `bun-v1.3.2`, so to list them from a mirror too,
configure [`versions-source`](<../(fundamentals)/config.mdx#tools-versions-source>).

## Core features

### Global packages

Packages installed globally with `bun add --global` (or `-g`) live outside of proto's
[store](<../(fundamentals)/store.mdx>), so every Bun version shares them. Bun links their
executables into a global bin directory, and proto looks for it in the following order, skipping
any directory whose environment variable isn't set:

1. `$BUN_INSTALL_BIN`
2. `$BUN_INSTALL/bin`, or `$BUN_INSTALL` itself when it already is a `bin` directory
3. `$XDG_CACHE_HOME/.bun/bin`
4. `~/.bun/bin`, Bun's default

When Bun runs through a [shim](<../(fundamentals)/workflows.mdx#shims>),
[`proto run`](../commands/run.mdx), or [`proto exec`](../commands/exec.mdx), these directories are
added to its `PATH`, so a script that calls a global package's command finds it.
[Shell activation](<../(fundamentals)/workflows.mdx#shell-activation>) adds them to your shell too.

```shell
# Install a package globally
$ bun add --global cowsay

# Print the directory that global executables are linked into
$ proto bin bun --dir globals
```

### Version files

Besides [`.prototools`](<../(fundamentals)/config.mdx>), proto detects a Bun version from the
following [ecosystem files](<../(fundamentals)/detection.mdx#4-ecosystem-files>), checked in this
order in each directory:

- `.bumrc` and `.bun-version` - Plain text files, where the version is the first line with content.
  Comments, after a `#` or `//`, are ignored.
- `package.json` - The first of the following fields that declares a Bun version:
  1. `devEngines.runtime`, an entry named `bun`.
  2. `devEngines.packageManager`, an entry named `bun`.
  3. `volta.bun`, including from a file that `volta.extends` points to.
  4. `packageManager`, like `bun@1.3.2`. A Corepack hash after the version, like `+sha512.…`, is
     removed.
  5. `engines.bun`.

In `devEngines` and `engines`, only versions and ranges are read, so values like `latest` are
skipped. Files within `node_modules` are ignored, so a dependency's `package.json` never decides
which version you run.

```text title=".bun-version"
1.3.2
```

```json title="package.json"
{
  "devEngines": {
    "runtime": { "name": "bun", "version": "^1.3.0" }
  }
}
```

To pin a version in these files, instead of [`.prototools`](<../(fundamentals)/config.mdx>), pass
`--tool-native` to [`proto pin`](../commands/pin.mdx). It updates `.bumrc` or `.bun-version` when
one exists in the directory, as they're detected first, and writes to `devEngines.runtime` in
`package.json` otherwise. `devEngines` only accepts versions and ranges, so pin an alias with
`--resolve`. [`proto unpin --tool-native`](../commands/unpin.mdx) removes the version file, or the
`bun` entries in `devEngines`.

```shell
# Pin to .bumrc or .bun-version when one exists, or devEngines in package.json otherwise
$ proto pin bun 1.3.2 --tool-native

# Pin the version that latest resolves to
$ proto pin bun latest --resolve --tool-native
```

## Ecosystem

### Builds

Bun publishes more than one build for some platforms, and proto picks the one that runs on your
machine, with nothing to configure:

- **Baseline** - On x64 CPUs without AVX2 support, like older Intel processors, proto installs the
  baseline build, as the default build can't run on them. A
  [lockfile](../advanced/lockfile.mdx) records it as the `baseline`
  [variant](../advanced/lockfile.mdx#variants), so machines with different CPUs can share one.
  Locking another platform with [`proto lock`](../commands/lock.mdx) locks the default build.
- **musl** - On musl-based Linux distributions, like Alpine, proto installs the musl build, which
  Bun publishes from version 1.1.35. Installing an older version fails, instead of installing a
  glibc build that can't run.

### Canary builds

Bun publishes a canary build, its latest unreleased build, which you can install with the `canary`
spec. Canary builds don't have reliable checksums, so they aren't verified against a published one
(see [tools without checksums](../advanced/checksums.mdx#tools-without-checksums)). Once installed,
a canary build isn't replaced by a newer one, so reinstall it with `--force` to update.

```shell
# Install the canary build
$ proto install bun canary

# Run it for a single command
$ PROTO_BUN_VERSION=canary bun --version

# Update to the newest canary build
$ proto install bun canary --force
```

## Troubleshooting

### A global package's command isn't found

Executables of global packages are only on `PATH` within Bun's own process, or with
[shell activation](<../(fundamentals)/workflows.mdx#shell-activation>) (see the
[comparison of workflows](<../(fundamentals)/workflows.mdx#comparison>)). To run them from a shell
that isn't activated, add the globals directory to your `PATH` yourself, as printed by
[`proto bin bun --dir globals`](../commands/bin.mdx).

If you've changed the directory with `globalBinDir` in `bunfig.toml`, proto doesn't read it. Set
the `BUN_INSTALL_BIN` environment variable to the same directory instead, which both Bun and proto
use.

## Caveats

- **`bunx` shims run `bun x`** - Bun doesn't ship a separate `bunx` executable. It's the `bun`
  executable under another name, which Bun checks to behave like `bun x`. The `bunx`
  [binary](<../(fundamentals)/workflows.mdx#binary-linking>) in `~/.proto/bin` links to `bun`, so it
  works exactly like Bun's own. The `bunx` shim can't rename the executable it runs, so it runs
  `bun x` instead, where Bun-specific flags, like `--bun`, don't work.
- **`bun upgrade` is blocked** - It would replace a version that proto manages. In an interactive
  terminal, proto offers to install and pin the `latest` version instead, and elsewhere, like in
  CI, it fails with the command to run (see
  [running tools](<../(fundamentals)/(plugin)/tool.mdx#running-tools>)).
