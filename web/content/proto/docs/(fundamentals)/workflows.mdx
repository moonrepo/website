proto installs every version of a [tool](<./(plugin)/tool.mdx>) into its own directory in the
[store](./store.mdx), like `~/.proto/tools/node/22.5.1`. Your shell doesn't look there, so something
has to put those tools on your `PATH`, and decide which version runs when you type `node`. proto
offers three workflows for this, and they're designed to be combined:

- **[Shims](#shims)** - Small executables in `~/.proto/shims` that hand every call to proto, which
  [detects](./detection.mdx) the version for the current directory and runs it.
- **[Binary linking](#binary-linking)** - Links in `~/.proto/bin` that point straight at a specific
  installed version, with no detection and no overhead.
- **[Shell activation](#shell-activation)** - A shell hook that updates `PATH` and environment
  variables for the current directory, every time the prompt is drawn or the directory changes.

[`proto setup`](../commands/setup.mdx), which the install scripts run, configures shims and binary
linking for you. Shell activation is opt-in. Not sure which to use? See the
[comparison](#comparison).

## Shims

A shim is a tiny executable in `~/.proto/shims`, named after an executable that a tool provides,
like `node`, `npm`, or `npx`. A shim isn't a link to the tool. Every shim is a copy of the
`proto-shim` binary that ships with proto (with an `.exe` extension on Windows), which reads its own
file name to determine the tool, and re-invokes proto with [`proto run`](../commands/run.mdx). These
are equivalent:

```shell
# Through the shim
$ node --version

# What the shim runs
$ proto run node -- --version

# The shim itself
$ which node
~/.proto/shims/node
```

On every call, [`proto run`](../commands/run.mdx) then:

1. Detects the version to use from the current directory, following the
   [detection order](./detection.mdx#detection-order). A `PROTO_NODE_VERSION` environment variable
   overrides it, so `PROTO_NODE_VERSION=20 node --version` runs Node.js 20 for one command.
2. Installs the version when it's missing and [`auto-install`](./config.mdx#auto-install) is enabled.
   Otherwise, it fails with the [`proto install`](../commands/install.mdx) command to run.
3. Prepares the tool's process: applies [`[env]`](./config.mdx#env) and
   [`[tools.*.env]`](./config.mdx#tools-env) variables, prepends the tool's executable and globals
   directories to `PATH`, and sets `PROTO_NODE_VERSION` to the resolved version, so child processes,
   like a script that spawns `node`, use the same version.
4. Runs the tool's executable with your arguments.

On macOS and Linux, the shim and proto each replace their own process instead of spawning a child,
so signals like `Ctrl+C` go straight to the tool, and no extra processes linger. On Windows, where
that isn't possible, the shim waits for proto and passes `Ctrl+C` through to the tool.

Shims for secondary executables, like `npx` from npm or `bunx` from Bun, are described in
`~/.proto/shims/registry.json`, which records the tool that owns the executable and any arguments to
add (`bunx` runs `bun x`). When two tools provide the same executable name, the tool whose
identifier matches the name keeps it, and otherwise the first tool installed does.

If no version is detected for the current directory, or proto doesn't manage the tool at all, the
shim falls back to an executable with the same name elsewhere on `PATH`, like a system install,
skipping proto's own directories. To give every directory a default version instead, pin one in the
[global configuration](./detection.mdx#5-global-configuration) with
[`proto pin --to global`](../commands/pin.mdx).

Shims are the most flexible workflow: they pick the version for the directory you call them from,
on every call, and work anywhere `~/.proto/shims` is on `PATH`, including scripts, editors, and CI.
The trade-off is a small cost per call, as proto loads its configuration and the tool's plugin
before the tool starts. It's rarely noticeable for commands you run by hand, but adds up in
something that spawns a tool thousands of times.

To see what a shim is doing, set `PROTO_DEBUG_SHIM` to print its steps to stderr, and run
[`proto bin node --shim`](../commands/bin.mdx) to print the shim's path. The variables that shims
set are listed in [environment variables](../advanced/env-vars.mdx#within-shims).

### Setup

Shims are used when `~/.proto/shims` is on `PATH`, before `~/.proto/bin`.
[`proto setup`](../commands/setup.mdx) adds both to your shell profile, in the right order:

```shell
export PROTO_HOME="$HOME/.proto"
export PATH="$PROTO_HOME/shims:$PROTO_HOME/bin:$PATH"
```

<Callout type="warning">
  Both directories contain a `node`, so if `~/.proto/bin` comes first, `node`
  always runs the highest installed version, and version detection never
  happens. [`proto diagnose`](../commands/diagnose.mdx) warns about this order.
</Callout>

You don't create shims yourself. When you install a tool version, proto creates a shim for each
executable that the tool's plugin exposes (a plugin can opt an executable out, see
[executables](<./(plugin)/tool.mdx#executables>)). Re-running [`proto install`](../commands/install.mdx) for an
installed version recreates any shims that are missing, and when a proto upgrade changes
`proto-shim`, a tool's shims are recreated the next time you install it. A tool's shims are removed
when its last version is uninstalled.

If your shims are missing or broken, regenerate them with [`proto regen`](../commands/regen.mdx). It
deletes `~/.proto/shims`, and recreates shims for every tool that has a version configured in the
[`.prototools`](./config.mdx) files of the current directory and its parents, and the global one. Tools without a
configured version are skipped, so run it from a directory where your tools are configured.

```shell
$ proto regen
```

## Binary linking

Binary linking puts links in `~/.proto/bin` that point directly at a tool's executables, for a
specific installed version. On macOS and Linux they're symlinks. On Windows, where creating
symlinks requires administrator privileges, they're copies of the executables. Running one runs the
tool itself: proto isn't involved, so there's no version detection, no `[env]` variables, and no
overhead.

A linked binary doesn't follow the version you pinned. Each one points at the highest installed
version within its range, and proto links several of them per tool:

- `~/.proto/bin/node` - The highest installed version.
- `~/.proto/bin/node-<major>` - The highest installed version of each major, like `node-20` and
  `node-22`.
- `~/.proto/bin/node-<major>.<minor>` - The highest installed version of each major and minor, like
  `node-20.18` and `node-22.5`.
- `~/.proto/bin/node-canary` - The canary version, when one is installed.

Versioned binaries are the easiest way to run a specific version without detection, even alongside
shims, as there's no shim with the same name:

```shell
# The highest installed 20.x version
$ node-20 --version
v20.18.0

# Where the binary points
$ readlink ~/.proto/bin/node
/Users/you/.proto/tools/node/22.5.1/bin/node
```

Not every executable can be linked. npm, and the versions of pnpm and Yarn written in JavaScript,
need Node.js to run them, so they're only available as shims. Each tool's plugin decides which of its
[executables](<./(plugin)/tool.mdx#executables>) get a binary.

### Setup

Binaries are used when `~/.proto/bin` is on `PATH`, after `~/.proto/shims` if you use both.
[`proto setup`](../commands/setup.mdx) adds it (see [shims setup](#setup)). Keep it on `PATH` even if
you don't use binary linking, as `proto` and `proto-shim` themselves live there, unless you installed
proto elsewhere, like with [Nix](../index.mdx#nix).

Binaries update as you install and uninstall versions. Installing a version relinks the tool's
binaries, so a new highest version takes over `node`, `node-22`, and so on. Uninstalling a version
re-points its binaries to the next highest version in their range, or removes them when nothing is
left in it.

Pinning a version with [`proto pin`](../commands/pin.mdx), even globally, doesn't change any binary,
as binaries only follow what's installed. To change what `node` points to, install a higher
version, or uninstall the current one.

To rebuild every binary from scratch, pass `--bin` to [`proto regen`](../commands/regen.mdx). It
deletes everything in `~/.proto/bin` except `proto` and `proto-shim`, and relinks every installed
version of each tool with a configured version, alongside regenerating shims.

```shell
$ proto regen --bin
```

## Shell activation

Shell activation, also known as shell hooks, changes your shell session itself, instead of routing
calls through proto. In your shell profile, you evaluate the output of
[`proto activate`](../commands/activate.mdx), which registers a hook that runs whenever the prompt
is drawn or the directory changes (depending on the [shell](#supported-shells)). Each time it runs,
proto:

1. Loads the [`.prototools`](./config.mdx) files in the current directory and its parents, and selects the tools
   with a configured version.
2. [Detects](./detection.mdx) the version of each tool, as shims do.
3. Prepends the tool's executable directories, and its globals directories (where executables of
   globally installed packages live), to `PATH`. A version that isn't installed is skipped, as
   activation never installs anything.
4. Exports [`[env]`](./config.mdx#env) and [`[tools.*.env]`](./config.mdx#tools-env) variables, and
   defines [shell aliases](#shell-aliases).
5. Puts a [pinned proto version](./config.mdx#pinning-proto) (an exact version) on `PATH`, and sets
   `PROTO_HOME` when it isn't set.
6. Appends `~/.proto/shims` and `~/.proto/bin` after the tool directories, so tools that weren't
   activated still resolve through [shims](#shims) and [binaries](#binary-linking).
7. Reverts what the previous run applied, unsetting variables and aliases that are no longer
   configured, and replacing its own `PATH` entries instead of piling up new ones.

```shell
$ cd ~/projects/client && node --version
v20.18.0

$ cd ~/projects/server && node --version
v22.5.1

# Resolves straight to the installed version
$ which node
~/.proto/tools/node/22.5.1/bin/node
```

Because `node` resolves to the real executable, calls have no overhead. The cost moves to the hook
instead, which runs proto once per prompt or directory change. And because variables and
directories are exported into the session, everything you run sees them, not only the tools proto
runs, including executables from globally installed packages.

A few things to keep in mind:

- Versions pinned in the global [`~/.proto/.prototools`](./config.mdx) aren't activated, as activation loads
  configuration in the `upwards` [resolution mode](./config.mdx#resolution-modes). Those tools
  resolve through shims and binaries instead. To include them, pass
  `--config-mode upwards-global` to [`proto activate`](../commands/activate.mdx), which makes every hook run load more tools.
- Activation only happens in interactive shells that evaluate the hook. Processes you start from the
  session inherit its environment as it was when they started, but don't re-activate when they
  change directories, and non-interactive scripts and CI jobs never activate. Keep shims on `PATH`
  for those.
- `[env]` variables and shell aliases are [security-sensitive](./trust.mdx#security-sensitive-settings),
  so a local [`.prototools`](./config.mdx) must be [trusted](./trust.mdx) before activation applies them. The hook
  warns about an untrusted file once per shell session.

For a one-off session instead, [`proto shell`](../commands/shell.mdx) starts a new interactive shell
with the configured tools (or the ones you list, like
[`proto shell node@20`](../commands/shell.mdx)) on `PATH` and their environment variables applied,
without registering a hook. Versions stay fixed for the life of that shell, and exiting it returns
you to the original session. To run a single command this way, use
[`proto exec`](../commands/exec.mdx).

### Setup

Add the hook for your shell near the end of its profile, after `PATH` is configured, as the hook
runs `proto` and needs it on `PATH`. Then open a new terminal. Keep the `PATH` lines that
[`proto setup`](../commands/setup.mdx) added, so that shims and binaries keep working in scripts and
editors.

The hook also activates the session immediately, so tools are available before you type anything.
Pass `--no-init` to wait for the first trigger instead. Options like `--no-shim`, `--no-bin`, and
`--config-mode` are baked into the hook, so every run uses them:

```shell title="~/.zshrc"
eval "$(proto activate zsh --config-mode upwards-global)"
```

### Supported shells

Activation is supported in the following shells. Pass the argument to [`proto activate`](../commands/activate.mdx), or omit it
to detect the shell from `$SHELL` and the parent process (in a profile, pass it explicitly).

| Shell          | Argument               | Activates on                                        |
| -------------- | ---------------------- | --------------------------------------------------- |
| Bash           | `bash`                 | Every prompt                                        |
| Zsh            | `zsh`                  | Directory change and every prompt                   |
| Fish           | `fish`                 | Directory change and every prompt                   |
| Nushell        | `nu`                   | Directory change and every prompt                   |
| PowerShell 6+  | `pwsh`                 | Directory change and every prompt                   |
| PowerShell 5.1 | `powershell`           | Every prompt                                        |
| Elvish         | `elvish`               | Directory change, and every prompt when interactive |
| Murex          | `murex`                | Every prompt                                        |
| Xonsh          | `xonsh`                | Directory change and every prompt                   |
| sh, ash, dash  | `sh`, `ash`, or `dash` | `cd` only                                           |

The prompt trigger is what picks up changes without a directory change: after you edit
[`.prototools`](./config.mdx) or run [`proto install`](../commands/install.mdx), the next prompt activates the new version. POSIX shells have
no hooks, so the hook replaces the `cd` builtin with a function that runs the original and then
activates, which overrides any other `cd` wrapper. In those shells, run `cd .` to re-activate in
place.

### Shell aliases

Activation can also define aliases in your shell, from the [`[shell.aliases]`](./config.mdx#shell-aliases) table in
[`.prototools`](./config.mdx). Each key is the alias name, and the value is the command it runs:

```toml title=".prototools"
[shell.aliases]
gs = "git status"
dev = "pnpm run dev"
```

Aliases from every loaded [`.prototools`](./config.mdx) are combined, and like everything activation applies,
they're removed when you leave a directory where they're configured. They're only defined by shell
activation, not by shims, [`proto run`](../commands/run.mdx), or [`proto shell`](../commands/shell.mdx),
and they aren't part of the `--json` output, as they aren't environment variables. In Elvish,
aliases are only available in an interactive session.

### Deactivating

To turn activation off for the current session, call the `proto_deactivate` function that the hook
defines (in Xonsh, `proto_deactivate()`):

```shell
$ proto_deactivate
```

It unregisters the hook so nothing re-activates, unsets the variables and aliases that activation
set, removes the `PATH` entries it added, and finally removes the `proto_activate` and
`proto_deactivate` functions. Directories that your profile put on `PATH` itself, like
`~/.proto/shims` and `~/.proto/bin`, stay where they were. In Nushell, the teardown applies on the
next prompt.

The function evaluates the output of [`proto deactivate`](../commands/deactivate.mdx) with
`--export`. Running [`proto deactivate`](../commands/deactivate.mdx) by itself only reminds you to call the function, as a command
can't change the shell that launched it. To activate again, evaluate [`proto activate`](../commands/activate.mdx) again, or open
a new terminal.

## Comparison

Each workflow trades flexibility for speed differently:

|                           | Shims                                        | Binary linking                           | Shell activation                                       |
| ------------------------- | -------------------------------------------- | ---------------------------------------- | ------------------------------------------------------ |
| Version used              | Detected for the current directory, per call | Highest installed, or a versioned binary | Detected for the current directory, when the hook runs |
| Overhead                  | proto runs before every call                 | None                                     | None per call; proto runs on each trigger              |
| `[env]` variables         | Set for the tool's process                   | Not applied                              | Exported into the shell                                |
| Global packages on `PATH` | Only within the tool's process               | No                                       | Yes                                                    |
| Missing versions          | Installed when `auto-install` is enabled     | Only installed versions are linked       | Skipped                                                |
| Pinned proto version      | No                                           | No                                       | Yes                                                    |
| Scripts, editors, and CI  | Yes                                          | Yes                                      | Interactive shells only                                |
| Setup                     | `~/.proto/shims` on `PATH`                   | `~/.proto/bin` on `PATH`                 | A hook in your shell profile                           |

Which to use:

- **Shims and binaries (the default)** - What [`proto setup`](../commands/setup.mdx) configures, and
  right for most people. Shims come first, so every tool follows the version of the directory you're
  in, everywhere. Binaries fill in behind them, with `proto` itself, versioned executables like
  `node-20`, and executables that don't have a shim.
- **Add shell activation** - For your interactive shell, when you want `[env]` variables, shell
  aliases, and globally installed packages in your session, a pinned proto version, or no overhead
  per call. Keep shims and binaries on `PATH` underneath, for scripts and editors, and for tools that
  activation skips.
- **Binaries only** - When you want one version of each tool everywhere, with zero overhead, like in
  a container image that installs a single version of each tool. Leave `~/.proto/shims` off `PATH`.

For CI pipelines, see the [CI guide](../guides/ci.mdx).
