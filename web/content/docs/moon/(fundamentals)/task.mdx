Tasks are the fundamental building blocks of moon's execution system. They define discrete units of work that can be executed within projects, such as building, testing, linting, or running development servers. Tasks form the backbone of moon's automation capabilities, providing incremental builds, smart hashing, local/remote caching, and parallel execution.

## Types

Tasks are categorized into three primary types:

- **Build** - Tasks that produce artifacts or compiled outputs, and is derived from the
  [`outputs`](#outputs) setting.
- **Run** - Tasks for development servers, or long-running scripts, and is derived from the
  [`preset`](#preset) setting.
- **Test** - Tasks that run tests, lints, validations, or quality checks. This is the default.

<Callout>
  The type of task will be automatically inferred based on its configuration,
  but can also be explicitly defined with the [`type`](#type) setting.
</Callout>

<ConfigTabs
  file="moon"
  config={{
    tasks: {
      build: {
        command: "build-project",
        type: "build",
      },
    },
  }}
/>

## Modes

Alongside types, tasks can also grouped into a special mode that provides unique handling within the
action graph and pipelines.

### Local only

Tasks either run locally, in CI, or both. For tasks that should
_only_ be ran locally, such as, development servers and watchers, we provide a mechanism for opting out of running in CI.

To mark a task as local only, disable [`options.runInCI`](#runinci) or configure the appropriate [`preset`](#preset).

<ConfigTabs
  file="moon"
  config={{
    tasks: {
      dev: {
        command: "start-dev-server",
        preset: "server",
      },
    },
  }}
/>

### Internal only

Internal tasks are not meant to be ran explicitly by the user (on the command line), but are used internally as
dependencies of other tasks. Additionally, internal tasks are not displayed in a project's tasks
list, but can be inspected with [`moon task`](./commands/task).

To mark a task as internal, enable [`options.internal`](#internal).

<ConfigTabs
  file="moon"
  config={{
    tasks: {
      internal: {
        command: "intermediate-step",
        options: {
          internal: true,
        },
      },
    },
  }}
/>

### Interactive

Tasks that need to interact with the user via terminal prompts are known as interactive tasks.
Because interactive tasks require stdin, and it's not possible to have multiple parallel running
tasks interact with stdin, we isolate interactive tasks from other tasks in the action graph. This
ensures that only 1 interactive task is ran at a time.

To mark a task as interactive, enable [`options.interactive`](#interactive).

<ConfigTabs
  file="moon"
  config={{
    tasks: {
      init: {
        command: "init-project",
        options: {
          interactive: true,
        },
      },
    },
  }}
/>

### Persistent

Tasks that never complete, like servers and watchers, are known as persistent tasks. Persistent
tasks are typically problematic when it comes to dependency graphs, because if they run in the
middle of the graph, subsequent tasks will never run because the persistent task never completes!

However in moon, this is a non-issue, as we collect all persistent tasks within the action graph and
run them _last as a batch_. This is perfect for a few reasons:

- All persistent tasks are ran in parallel, so they don't block each other.
- Running both the backend API and frontend webapp in parallel is a breeze.
- Dependencies of persistent tasks are guaranteed to have ran and completed.

To mark a task as persistent, enable [`options.persistent`](#persistent) or configure the appropriate [`preset`](#preset).

<ConfigTabs
  file="moon"
  config={{
    tasks: {
      dev: {
        command: "start-dev-server",
        options: {
          persistent: true,
        },
      },
    },
  }}
/>

## Command

The work unit of a task is the `command` (or [`script`](#script)) setting. This setting represents a simple command line, comprised of an executable (binary, file path, etc), and zero or more arguments (options, flags, positionals, etc).

<ConfigTabs
  file="moon"
  config={{
    tasks: {
      example: {
        command: "executable --option value -f arg1 arg2",
      },
    },
  }}
/>

This setting can also be defined with a list of strings, where each list item is an individual argument. This pattern should be used when the string variant is too complex to parse correctly, or is not parsed into the proper individual arguments.

<ConfigTabs
  file="moon"
  config={{
    tasks: {
      example: {
        command: ["executable", "--option", "value", "-f", "arg1", "arg2"],
      },
    },
  }}
/>

### Arguments

The `args` setting is a collection of _additional_ arguments to merge into the [`command`](#command), and purely exists for composition when [task inheritance](./task-inheritance) occurs. This setting also supports a string, or a list of strings.

<ConfigTabs
  file="moon"
  config={{
    tasks: {
      example: {
        args: "--another arg -x",
      },
    },
  }}
/>

<Callout>
  Argument merging is powered by the
  [`options.mergeArgs`](./task-inheritance#merge-strategies) task option.
</Callout>

### Supported syntax

As stated above, `command` only supports a single simple command, and does not support compound commands. A compound command may contain pipes (`|`), redirects (`>`, `<`, etc), multiple sequences (`&&`, `||`, etc), or other shell specific syntax. So what syntax is supported?

<Tabs items={['Simple command', 'Compound command']}>
<Tab>

- Flags & flag groups: `-f`, `-aBc`
- Options: `--option`, `--option=value`
- Quoted values: `'value'`, `"value"`, `$'value'`, `$"value"`
- Unquoted values: `value`, `file/path.md`, `glob/file.*`
- Environment variables <sup>1</sup>: `KEY=value`
- Expansion <sup>2</sup>: `$((expr))`, `${param}`, `~` (tilde), `*?[]` (globs)
- Substitution <sup>2</sup>: `$(cmd)`, `<(cmd)`, `>(cmd)`
- Passthrough: `--` (everything after)

</Tab>
<Tab>

- Everything from simple commands
- Pipes: `|`, `|&`, etc
- Redirects: `>`, `>>`, `<`, `&>`, etc
- Terminators: `;`, `&`, `2&>1`, etc
- Sequences (multiple commands): `&&`, `||`, `;`

</Tab>
</Tabs>

If you need to use a compound command or advanced syntax, use one of these alternate approaches:

- Use [`script`](#script) instead of `command`, as it supports raw shell syntax.
- Wrap the command in a shell script, and execute that directly: `bash ./example.sh`.

> 1. Environment variable assignments _before_ the executable will be extracted as task [`env`](#environment-variables), otherwise it will be preserved as an argument.
> 2. Expansion and substitution syntax is specific to the shell the task will run in.

## Script

Script is the opposite of [`command`](#command), in that it supports compound commands and advanced shell syntax, but does not support argument parsing or merging. The script is passed directly to the shell for execution, and is not parsed or transformed by moon in any way.

<ConfigTabs
  file="moon"
  config={{
    tasks: {
      example: {
        script: "ls -Rl ./src | grep 'index' > result.txt",
      },
    },
  }}
/>

## Dependencies

Tasks can depend on other tasks, which means that when the task is executed, all of its dependencies will be executed first. This allows you to create complex workflows and ensure that certain tasks are always ran before others.

Dependencies can be defined with the `deps` setting, which accepts a list of [targets](./target) in string or object format. The string format is a simple and concise way to define dependencies, while the object format provides more flexibility and options for each dependency.

<Tabs items={['String', 'Object']}>
<Tab>

<ConfigTabs
  file="moon"
  config={{
    tasks: {
      example: {
        deps: ["lint", "test"],
      },
    },
  }}
/>

</Tab>
<Tab>

<ConfigTabs
  file="moon"
  config={{
    tasks: {
      example: {
        deps: [{ target: "lint" }, { target: "test" }],
      },
    },
  }}
/>

</Tab>
</Tabs>

### Parameters

When using the object format for dependencies, you can also specify parameters to be passed to the dependency task when it's executed. The following parameters are supported:

- `target` <TypeLabel type="string" /> _(required)_ - The [target](./target) of the dependency task(s).
- `args` <TypeLabel type="string[]" /> - A list of additional arguments to append to the task's [`command`](#command) when it's executed.
- `env` <TypeLabel type="Record<string, string>" /> - A map of additional variables to merge into the task's environment when it's executed.
- `optional` <TypeLabel type="boolean" /> - Controls how this dependency is treated during task inheritance. When `false` (the default), will error if the task does not exist. When `true`, will be ignored if the task does not exist. This does _not_ allow the task to fail during execution.

<ConfigTabs
  file="moon"
  config={{
    tasks: {
      example: {
        deps: [
          {
            target: "lint",
            args: ["--additional", "param"],
            env: { KEY: "value" },
          },
          { target: "test", optional: true },
        ],
      },
    },
  }}
/>

### Scopes

Dependencies support different [target](./target) scopes to reference tasks flexibly:

#### Current project

Tasks within the current/owning project can be referenced using multiple target scopes. Without a scope (just the task identifier), the `~:` scope (which means in the current project), or the explicit `<project-id>:` scope.

<ConfigTabs
  file="moon"
  config={{
    tasks: {
      example: {
        deps: ["lint", "~:test", "current-project-id:validate"],
      },
    },
  }}
/>

#### Other projects

Tasks within other/external projects can be referenced using the explicit `<project-id>:` scope.

<ConfigTabs
  file="moon"
  config={{
    tasks: {
      example: {
        deps: ["other-project-id:lint", "external-project-id:test"],
      },
    },
  }}
/>

#### Dependency projects

Tasks can be referenced from the current [project's dependencies](./project#dependencies) using the `^:` or `^<type>:` scopes. This will be expanded to all depended on projects of the current project. If you do not want all projects, then you'll need to explicitly define the dependencies.

<VersionLabel version="2.1.0" /> Additionally, dependend on projects can be
filtered by their dependency type, such as `production`, or `development`. The
following dependency types are supported:

- `dev` / `development`
- `prod` / `production`
- `peer`
- `build`

<ConfigTabs
  file="moon"
  config={{
    tasks: {
      example: {
        deps: ["^:lint", "^development:test"],
      },
    },
  }}
/>

#### Tagged projects

Tasks can be referenced from [tagged projects](./project#tags) using the `#<tag-id>:` scope. For example, if the target is `#example:build`, then the `build` task in all projects with the tag `example` will be included as a dependency.

<ConfigTabs
  file="moon"
  config={{
    tasks: {
      example: {
        deps: ["#dev:lint", "#dev:test"],
      },
    },
  }}
/>

## Environment variables

Environment variables allow you to pass configuration values to your tasks at execution time. Variables can be defined with the `env` setting, which accepts a map of key-value pairs.

<ConfigTabs
  file="moon"
  config={{
    tasks: {
      example: {
        env: {
          APP_ENV: "development",
          LOG_LEVEL: "debug",
        },
      },
    },
  }}
/>

<Callout>
  Environment variable merging is powered by the
  [`options.mergeEnv`](./task-inheritance#merge-strategies) task option.
</Callout>

### `.env` files

Tasks can also load environment variables from `.env` files (known as dotenv or env files), which are simple text files that contain key-value pairs of environment variables. This is useful for storing sensitive information, such as API keys or database credentials. To load environment variables from an `.env` file, use the `options.envFile` setting.

<ConfigTabs
  file="moon"
  config={{
    tasks: {
      example: {
        options: {
          envFile: true,
        },
      },
    },
  }}
/>

```text title=".env"
APP_ENV=production
LOG_LEVEL=debug
```

When `true`, this will expand to the following list of env files, in order of precedence, where the latter overwrites the former:

- `/.env`
- `/.env.local`
- `.env`
- `.env.local`
- `.env.<task_id>`
- `.env.<task_id>.local`

If you'd prefer to customize this, you can also provide a single file path or list of file paths.

<ConfigTabs
  file="moon"
  config={{
    tasks: {
      example: {
        options: {
          envFile: [".env", ".env.development", ".env.local"],
        },
      },
    },
  }}
/>

<Callout type="warning">
  Env files are loaded and processed _before_ task execution, and are not
  available during task creation or expansion (building the task graph).
  Continue reading for more information.
</Callout>

### Precedence

In the context of moon, there are 3 tiers of environment variables: system, task, and dotenv. Each tier has a different level of precedence, which determines which variable value is used when there are conflicts. The tiers are evaluated in the following order, from lowest precedence to highest:

- Task `.env` files
  - via `options.envFile`
- Task env variables
  - via `env` or `deps.*.env`
- System variables
  - via profile scripts (`.bashrc`, `.zshrc`, etc)
  - via command line: `KEY=value moon ...`

As noted above, system variables are the highest precedence, which means they will overwrite any conflicting variables defined in the task or dotenv tiers. If you don't want to inherit a system variable, you can override it in the task with a null value.

<ConfigTabs
  file="moon"
  config={{
    tasks: {
      example: {
        env: {
          NO_SYSTEM_VAR: null,
        },
      },
    },
  }}
/>

### Substitution

Environment variables support substitution (also known as interpolation or expansion), which allows you to reference other variables within the same tier or higher tiers. This is useful for creating dynamic variables that depend on other variable values. The syntax for variable substitution is similar to shell variable syntax, and supports a variety of operators for different substitution patterns. Refer to the following table:

```text title=".env"
APP_URL="https://${HOST}:${PORT}"
```

| Syntax                                                | Effect                                                                                       |
| ----------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `$VAR`, `${VAR}`                                      | Substitute with an empty string if variable is empty                                         |
| `${VAR?}`                                             | Substitute with shell variable syntax (`$VAR`) if variable empty                             |
| `${VAR!}`                                             | Don't substitute and keep shell variable syntax (`$VAR`)                                     |
| `${VAR:default}`, `${VAR:-default}`, `${VAR-default}` | Substitute with variable if defined, otherwise with the provided default value               |
| `${VAR:+alternate}`, `${VAR+alternate}`               | Substitute with provided alternate value if variable defined, otherwise with an empty string |

In regards to [precedence](#precedence), each tier can reference variables within the same tier or
higher tier(s), but _not_ from lower tier(s). This is because variables are processed in _reverse
order_. Refer to the following table:

| Tier   | Can reference        | Evaluated during      |
| ------ | -------------------- | --------------------- |
| Dotenv | Dotenv, Task, System | Before task execution |
| Task   | Task, System         | After task creation   |
| System | System               | CLI startup           |

<Callout>
  We also support shell specific variable syntax: `$env:VAR` (powershell),
  `$E:VAR` (elvish), `$env.VAR` (nushell), etc.
</Callout>

## Inputs

Task inputs specify which sources affect a task's execution cycle. They're critical for effective caching, as we generate a smart content hash from all inputs,
and when inputs and the hash change, the cached result is invalidated and the task re-runs.

Inputs can be defined with the `inputs` setting, which accepts a list of strings or objects, and defaults `**/*` (all files in the project). The string format is a simple and concise way to define inputs, while the object format provides more flexibility and options for each input.

<ConfigTabs
  file="moon"
  config={{
    tasks: {
      example: {
        inputs: ["src/**/*", "*.config.json", "manifest.json", "$APP_ENV"],
      },
    },
  }}
/>

<Callout>
  Input merging is powered by the
  [`options.mergeInputs`](./task-inheritance#merge-strategies) task option.
</Callout>

### Files

Files are simply that, project-relative or workspace-relative files on the file system (within the moon workspace). They can be defined with literal strings, the `file://` URI protocol, or the `file` property when using the object format.

<Tabs items={['String', 'Object']}>
<Tab>

<ConfigTabs
  file="moon"
  config={{
    tasks: {
      example: {
        inputs: [
          "project/file",
          "/workspace/file",
          "file://project/file",
          "file:///workspace/file",
        ],
      },
    },
  }}
/>

</Tab>
<Tab>

<ConfigTabs
  file="moon"
  config={{
    tasks: {
      example: {
        inputs: [{ file: "project/file" }, { file: "/workspace/file" }],
      },
    },
  }}
/>

</Tab>
</Tabs>

When using the URI or object formats, the following parameters are supported:

- `content` <TypeLabel type="string" /> - A [regex pattern](./config) to match the file's contents against when determining affected status. Otherwise, any change to the file will mark the task as affected.
- `optional` <TypeLabel type="boolean" /> - Mark the file as optional and log a warning instead of failing with an error when hashing. Files are required by default.

<Tabs items={['String', 'Object']}>
<Tab>

<ConfigTabs
  file="moon"
  config={{
    tasks: {
      example: {
        inputs: ["file://src/file?content=^foobar$&optional=true"],
      },
    },
  }}
/>

</Tab>
<Tab>

<ConfigTabs
  file="moon"
  config={{
    tasks: {
      example: {
        inputs: [{ file: "src/file", content: "^foobar$", optional: true }],
      },
    },
  }}
/>

</Tab>
</Tabs>

### File groups

File group inputs allow you to reference the [`fileGroups`](./project#file-groups) setting in the project, effectively including all files within the specified file group as inputs to the task. They can be defined with the `group://` URI protocol, or the `group` property when using the object format.

<Tabs items={['String', 'Object']}>
<Tab>

<ConfigTabs
  file="moon"
  config={{
    fileGroups: {
      sources: ["src/**/*", "resources/**/*"],
      tests: ["tests/**/*"],
    },
    tasks: {
      example: {
        inputs: ["group://sources", "group://tests"],
      },
    },
  }}
/>

</Tab>
<Tab>

<ConfigTabs
  file="moon"
  config={{
    fileGroups: {
      sources: ["src/**/*", "resources/**/*"],
      tests: ["tests/**/*"],
    },
    tasks: {
      example: {
        inputs: [{ group: "sources" }, { group: "tests" }],
      },
    },
  }}
/>

</Tab>
</Tabs>

When using the URI or object formats, the following parameters are supported:

- `format` <TypeLabel type="string" /> - The format that all paths within the file group should be resolved to when included as an input. If the file group contains glob patterns, they will walk the file system. Supports one of the following values:
  - `static` _(default)_ - Returns the paths as-is.
  - `dirs` - Returns only directories. Will walk the file system if needed.
  - `envs` - Returns only environment variables.
  - `files` - Returns only files. Will walk the file system if needed.
  - `globs` - Returns only glob patterns as-is. Will not walk the file system.
  - `root` - Returns the common root directory of all paths in the group. Will walk the file system.

<Tabs items={['String', 'Object']}>
<Tab>

<ConfigTabs
  file="moon"
  config={{
    tasks: {
      example: {
        inputs: ["group://sources?format=files"],
      },
    },
  }}
/>

</Tab>
<Tab>

<ConfigTabs
  file="moon"
  config={{
    tasks: {
      example: {
        inputs: [{ group: "sources", format: "globs" }],
      },
    },
  }}
/>

</Tab>
</Tabs>

### Globs

Globs are simply that, project-relative or workspace-relative [glob patterns](./config#glob-patterns) that will walk and match files on the file system (within the moon workspace). They can be defined with literal strings, the `glob://` URI protocol, or the `glob` property when using the object format.

<Callout type="warning">
  Be aware that files that match the glob, but are ignored via `.gitignore` (or
  similar), will not be considered an input. To work around this, use explicit
  file inputs.
</Callout>

<Tabs items={['String', 'Object']}>
<Tab>

<ConfigTabs
  file="moon"
  config={{
    tasks: {
      example: {
        inputs: [
          "project/**/*",
          "/workspace/*.json",
          "glob://project/**/*",
          "glob:///workspace/*.json",
        ],
      },
    },
  }}
/>

</Tab>
<Tab>

<ConfigTabs
  file="moon"
  config={{
    tasks: {
      example: {
        inputs: [{ glob: "project/**/*" }, { glob: "/workspace/*.json" }],
      },
    },
  }}
/>

</Tab>
</Tabs>

When using the URI or object formats, the following parameters are supported:

- `cache` <TypeLabel type="boolean" /> - Cache the result of the glob walk in-memory to improve performance on subsequent runs. Defaults to `true`.

<Tabs items={['String', 'Object']}>
<Tab>

<ConfigTabs
  file="moon"
  config={{
    tasks: {
      example: {
        inputs: ["glob://src/**/*?cache=false"],
      },
    },
  }}
/>

<Callout type="warning">
  If you're glob pattern contains a `?`, such as `files?.txt`, we suggest using
  the object format to avoid parsing issues with the query string.
</Callout>

</Tab>
<Tab>

<ConfigTabs
  file="moon"
  config={{
    tasks: {
      example: {
        inputs: [{ glob: "src/**/*", cache: false }],
      },
    },
  }}
/>

</Tab>
</Tabs>

### Other projects

Other project inputs can be used to depend on files and globs from other/external projects within the same workspace. This is useful for handling cross-project relationships without needing to define explicit task dependencies.

They can be defined with the `project://` URI protocol, or the `project` property when using the object format, both of which require a project identifier, or `^` for all dependent projects of the current project.

Dependent projects can be scoped further by using `^development`, `^production`, `^peer`, or `^build` to only include projects with the specified dependency type.

<Tabs items={['String', 'Object']}>
<Tab>

<ConfigTabs
  file="moon"
  config={{
    tasks: {
      example: {
        inputs: ["project://utils", "project://^production", "project://^"],
      },
    },
  }}
/>

</Tab>
<Tab>

<ConfigTabs
  file="moon"
  config={{
    tasks: {
      example: {
        inputs: [
          { project: "utils" },
          { project: "^production" },
          { project: "^" },
        ],
      },
    },
  }}
/>

</Tab>
</Tabs>

When using the URI or object formats, the following parameters are supported:

- `filter` <TypeLabel type="string[]" /> - A list of glob patterns, relative from the project's root, to include as inputs. If not defined, defaults to `**/*`.
- `fileGroup` <TypeLabel type="string" /> - An identifier of a [file group](./project#file-groups) in the external project to include as inputs. If defined, will override `filter`.

<Tabs items={['String', 'Object']}>
<Tab>

<ConfigTabs
  file="moon"
  config={{
    tasks: {
      example: {
        inputs: [
          "project://utils?filter=src/**/*",
          "project://^development?fileGroup=sources",
        ],
      },
    },
  }}
/>

</Tab>
<Tab>

<ConfigTabs
  file="moon"
  config={{
    tasks: {
      example: {
        inputs: [
          { project: "utils", filter: ["src/**/*"] },
          { project: "^development", fileGroup: "sources" },
        ],
      },
    },
  }}
/>

</Tab>
</Tabs>

### Environment variables

Environment variables can also be used as inputs, and must start with a `$`. They can be defined with an explicit name, or a wildcard name using `*`. They do not support the URI or object formats, and therefore do not support additional parameters.

<ConfigTabs
  file="moon"
  config={{
    tasks: {
      example: {
        inputs: ["$ENV_MODE", "$APP_*"],
      },
    },
  }}
/>

<Callout type="info">
  When using an environment variable, we assume it's not defined by default, and
  will trigger an affected state when it is defined. If the environment variable
  always exists, then the task will always run and bypass the cache.
</Callout>

## Toolchains

Toolchains are a very important concept for tasks, as they define the runtime environment in which a task executes. By specifying a toolchain for a task, you can ensure that it runs in the correct environment with the necessary tools, executables, and more.

With that said, we suggest _not configuring toolchains explicitly_ for tasks, and instead rely on our internal detection mechanism, which inherits from the project, and is detected based on manifest, lock, and config files, and executable names.

If for some reason you do need to explicitly configure a toolchain for a task, you can do so with the `toolchains` setting, which accepts a list of toolchain identifier(s) defined in [`.moon/toolchains.config`](./toolchains#configuration).

<ConfigTabs
  file="moon"
  config={{
    tasks: {
      example: {
        toolchains: ["javascript", "node"],
      },
    },
  }}
/>
