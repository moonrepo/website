Projects are the primary organizational unit within a moon [workspace](./workspace). A project is a
directory containing related source code — an application, a library, a tool, or anything in
between — along with the [tasks](./task) that operate on it. Every project is a node in the
[project graph](./project-graph), and the relationships between projects are what power moon's
dependency ordering, affected detection, and task inheritance.

## Discovery

Projects are located through the [`projects`](/api/moon/WorkspaceConfig#projects) setting in [`.moon/workspace.config`](./workspace),
which accepts three shapes:

- **A map** of project identifiers to their source paths, for explicit control.
- **A list of globs**, for convention-based discovery.
- **Both**, using the [`sources`](/api/moon/WorkspaceProjectsConfig#sources) and [`globs`](/api/moon/WorkspaceProjectsConfig#globs) keys together.

<ConfigTabs
  file=".moon/workspace"
  config={{
    projects: {
      globs: ["apps/*", "packages/*"],
      sources: {
        root: ".",
      },
    },
  }}
/>

When a project is found by a glob, its identifier is inferred from the matched path. By default
that's the directory name, but [`projects.globFormat`](/api/moon/WorkspaceProjectsConfig#globformat) <VersionLabel version="2.0.0" /> can switch it
to the full workspace-relative source path instead, which is useful when directory names collide
across the repository.

<Callout>
  Globs are matched against directories, and hidden directories (those beginning
  with `.`) are skipped. Suffix a glob with the project config file name to be
  explicit about what counts as a project.
</Callout>

Beyond configuration, [toolchain](./toolchain) and [extension](./extension) plugins can contribute
to discovery through their `extend_project_graph` hook, registering additional projects, aliases,
and input files. This is how a toolchain can teach moon about projects that its own ecosystem
already defines, such as a package manager's workspace members.

### Default project

In a workspace built around one primary application, having to name that project in every command
gets repetitive. The [`defaultProject`](/api/moon/WorkspaceConfig#defaultproject) <VersionLabel version="2.0.0" /> setting in [`.moon/workspace.config`](./workspace) nominates a
project as the default, so tasks can be run without a project scope at all.

<ConfigTabs
  file=".moon/workspace"
  config={{
    defaultProject: "app",
  }}
/>

With the above configured, a bare task identifier resolves against `app`, making these two
commands equivalent:

```shell
$ moon run build
$ moon run app:build
```

The value must be the identifier of an existing project, otherwise configuration will fail to
build. When no default is configured, running a bare task identifier errors instead of guessing,
and an explicit [target](./target) is required.

## Configuration

Projects are configured with an optional [`moon.config`](#configuration) file at the root of the
project directory. A project without one is still a project; the file only exists to add
dependencies, tasks, categorization, and overrides on top of what moon can already detect.

## Identifiers

Every project has an ID — the stable, unique handle moon uses to refer to it in configs, in
the CLI, and in other projects' dependencies. Whenever you see a project mentioned,
you're seeing its ID.

An ID comes from one of two places. First, through the [`projects`](/api/moon/WorkspaceConfig#projects) setting in
[`.moon/workspace.config`](./workspace), which is either derived from the folder path, or explicitly defined. Otherwise, you can override it by configuring [`id`](/api/moon/ProjectConfig#id).

<ConfigTabs
  file="moon"
  config={{
    id: "custom-id",
  }}
/>

## Aliases

An alias is a secondary, toolchain-derived name for a project. Aliases work as drop-in replacements
for the ID — anywhere an ID is accepted, the alias works
too.

However, you don't configure aliases directly. They're picked up automatically from the project's associated toolchain(s). For example, a project on the `javascript` toolchain will use the `name` field from its `package.json` as
its alias. Other toolchains do something analogous for their ecosystems.

Aliases exist because most packages already have a canonical name in their ecosystem, and it is
often more natural to use that name than to invent a separate moon-specific ID. A shared UI library
might be declared with the ID `uiKit` at `packages/ui-kit`, while its
`package.json` declares `@org/ui-kit`. In that case, both `uiKit` and `@org/ui-kit`
refer to the same project:

<ConfigTabs
  file="moon"
  config={{
    dependsOn: ["uiKit", "@org/ui-kit"],
  }}
  comments={{
    dependsOn: "Both values are equivalent!",
  }}
/>

<Callout>
  Aliases also need to be unique. An alias cannot collide with an existing
  project ID, and two projects can't share the same alias. moon will assign an
  aliases to the first receiving project.
</Callout>

## Dependencies

Projects can depend on other projects, and those relationships form the edges of the
[project graph](./project-graph). Dependencies determine the order projects are synced in, what
the `^` [target scope](./target) expands to, which projects are affected by a change,
and what [`moon docker scaffold`](./commands/docker/scaffold) copies into a build context.

Dependencies come from two sources:

- **Explicit** - Declared with the [`dependsOn`](#dependencies) setting, by project ID or [alias](#aliases).
- **Implicit** - Inferred by [toolchains](#toolchains) from the project's manifest files. For
  example, the `javascript` toolchain reads `dependencies` from `package.json`, so workspace
  packages that depend on each other are connected automatically.

<ConfigTabs
  file="moon"
  config={{
    dependsOn: ["api-client", "design-system"],
  }}
/>

<Callout>
  When a manifest already declares a relationship, there's no need to repeat it
  in `dependsOn`. Explicit dependencies are for relationships that manifests
  can't express, such as a project that consumes another project's build output.
</Callout>

### Scopes

Every dependency has a scope, describing _why_ the relationship exists. When using the string
format, the scope defaults to `production`. To change it, use the object format with the [`id`](/api/moon/ProjectDependencyConfig#id) and
[`scope`](/api/moon/ProjectDependencyConfig#scope) fields.

- `production` - Required at runtime. **This is the default.**
- `development` - Required only during development, such as testing or linting utilities.
- `build` - Required to build the project.
- `peer` - A peer relationship, mirroring the package manager concept.
- `root` - A special scope for depending on the workspace root-level project.

<ConfigTabs
  file="moon"
  config={{
    dependsOn: [
      "api-client",
      { id: "test-utils", scope: "development" },
      { id: "codegen", scope: "build" },
    ],
  }}
/>

Scopes are what allow targets like `^production:build` to select a subset of dependencies, and
they also affect how cycles are detected. Refer to the
[project graph](./project-graph#graph-partitions) for more information.

## Toolchains

[Toolchains](./toolchain) provide the language and ecosystem integration for a project: detecting
implicit dependencies, installing dependencies, setting up tool versions, and more. A project can
belong to multiple toolchains, and its tasks inherit those toolchains unless configured otherwise.

A project's toolchains are resolved in the following order:

- Explicitly configured with the [`toolchains.default`](/api/moon/ProjectToolchainsConfig#default) setting.
- Inferred from the project's [`language`](#language).
- Detected by each toolchain plugin, based on manifest files, lock files, and config files within
  the project. For example, a `Cargo.toml` associates the project with the `rust` toolchain.

For most projects, detection is enough and nothing needs to be configured. If detection doesn't
match your intent, configure the defaults explicitly.

<ConfigTabs
  file="moon"
  config={{
    toolchains: {
      default: ["node", "typescript"],
    },
  }}
/>

The resolved toolchains are also what the [`inheritedBy.toolchains`](/api/moon/InheritedByConfig#toolchains)
condition matches against, so they determine which workspace tasks a project inherits.

### Overrides

Toolchains are configured at the workspace level in [`.moon/toolchains.config`](./toolchain), but a
project can override them by toolchain ID. Each entry supports the following values:

- `false` or `null` - Disables the toolchain for this project, even if it was detected.
- `true` - Enables the toolchain for this project, even if it wasn't detected.
- An object - Enables the toolchain, and overrides workspace-level settings, such as [`version`](/api/moon/ToolchainPluginConfig#version).

<ConfigTabs
  file="moon"
  config={{
    toolchains: {
      node: {
        version: "22.12.0",
      },
      python: false,
    },
  }}
/>

## Tasks

A project's [tasks](./task) are defined with the [`tasks`](/api/moon/ProjectConfig#tasks) setting, a map of task identifiers to task
configuration. Tasks defined here are merged with any tasks the project
[inherits](./task-inheritance) from the workspace, with the project's configuration taking
precedence.

<ConfigTabs
  file="moon"
  config={{
    tasks: {
      build: {
        command: "vite build",
        inputs: ["src/**/*"],
        outputs: ["dist"],
      },
      dev: {
        command: "vite dev",
        preset: "server",
      },
    },
  }}
/>

<VersionLabel version="2.4.0" /> To apply the same [options](./task#options) to
every task in the project, both local and inherited, configure the
[`taskOptions`](/api/moon/ProjectConfig#taskoptions) setting. Each task can
still override these values individually.

<ConfigTabs
  file="moon"
  config={{
    taskOptions: {
      retryCount: 2,
      runInCI: false,
    },
  }}
/>

### Environment variables

The [`env`](/api/moon/ProjectConfig#env) setting defines environment variables that are inherited by every task in the project.
It's a convenient way to avoid repeating the same variables across many tasks.

<ConfigTabs
  file="moon"
  config={{
    env: {
      NODE_ENV: "production",
    },
  }}
/>

Project variables act as the base for each task's environment, so a task that defines the same
variable in its own `env` will overwrite the project value. System variables still take precedence
over both; refer to [task environment variables](./task#precedence) for the full order.

<VersionLabel version="2.5.0" /> Projects also inherit variables from the
[`env`](/api/moon/InheritedTasksConfig#env) setting in
[`.moon/tasks/*.config`](./task-inheritance#configuration) files. By default,
project variables are appended on top of inherited ones, which can be changed
with the
[`workspace.mergeStrategies.env`](/api/moon/ProjectWorkspaceMergeStrategiesConfig#env)
setting.

### File groups

File groups are named collections of file paths, globs, and environment variables, defined with the
[`fileGroups`](/api/moon/ProjectConfig#filegroups) setting. They exist to avoid repeating the same list of [inputs](./task#inputs)
across multiple tasks.

<ConfigTabs
  file="moon"
  config={{
    fileGroups: {
      sources: ["src/**/*", "types/**/*"],
      tests: ["tests/**/*", "**/*.test.ts"],
    },
    tasks: {
      test: {
        command: "vitest run",
        inputs: ["@group(sources)", "@group(tests)"],
      },
    },
  }}
/>

File groups are referenced from tasks through [tokens](./advanced/tokens), and a different token can
be used depending on what's needed.

Like environment variables, file groups can be inherited from
[`.moon/tasks/*.config`](./task-inheritance#configuration) files. Groups with the same identifier
are merged per group, and <VersionLabel version="2.5.0" /> the strategy used can be changed with the
[`workspace.mergeStrategies.fileGroups`](/api/moon/ProjectWorkspaceMergeStrategiesConfig#filegroups) setting. Refer to [file groups](./advanced/file-groups) for
more information.

### Inheritance overrides

Projects inherit tasks from the workspace automatically, but not every inherited task makes sense
for every project. The [`workspace.inheritedTasks`](/api/moon/ProjectWorkspaceConfig#inheritedtasks) setting controls this on a per-project basis:

- [`include`](/api/moon/ProjectWorkspaceInheritedTasksConfig#include) - Only inherit tasks with these identifiers.
- [`exclude`](/api/moon/ProjectWorkspaceInheritedTasksConfig#exclude) - Inherit all tasks except these identifiers.
- [`rename`](/api/moon/ProjectWorkspaceInheritedTasksConfig#rename) - Rename inherited tasks, scoped to this project.

<ConfigTabs
  file="moon"
  config={{
    workspace: {
      inheritedTasks: {
        exclude: ["typecheck"],
        rename: {
          test: "unit-test",
        },
      },
    },
  }}
/>

Refer to [task inheritance](./task-inheritance#filtering-what-a-project-inherits) for more
information on how these filters interact with task dependencies.

## Categorization

These four settings are the project's categorization dimensions. Each one answers a different
question about the project. None of them are strictly required, but filling them in is how you
get the most out of moon.

### Stacks

The [`stack`](/api/moon/ProjectConfig#stack) setting describes _which broad technology stack the project belongs to_. It's used for
categorization and querying, and it also scopes [layer constraints](#layers), which are only
enforced between projects in the same stack.

Supported values:

- `backend` — Server-side APIs and services.
- `data` — Data sources, database layers.
- `frontend` — Client-side user interfaces.
- `infrastructure` — Cloud, server, and container infrastructure.
- `systems` — Low-level systems programming.
- `unknown` - Default when not defined.

<ConfigTabs
  file="moon"
  config={{
    stack: "frontend",
  }}
/>

### Layers

The [`layer`](/api/moon/ProjectConfig#layer) setting describes _what role the project plays within its stack_.

Supported values:

- `application` - An application of any kind, such as a web app, API service, or CLI.
- `automation` - An automated process, such as scripts, cron jobs, or end-to-end test suites.
- `configuration` - Shared configuration, such as an ESLint or TypeScript config package.
- `library` - Shared, reusable code, consumed by other projects.
- `scaffolding` - Templates or generators for creating new code.
- `tool` - An internal tool, such as a build script or code generator.
- `unknown` - Default when not defined.

<ConfigTabs
  file="moon"
  config={{
    layer: "library",
  }}
/>

Layers aren't purely descriptive — they're enforced. When the [`constraints.enforceLayerRelationships`](/api/moon/ConstraintsConfig#enforcelayerrelationships)
setting in [`.moon/workspace.config`](./workspace) is enabled (the default), a project can only
depend on projects in the same layer or a lower one, preventing, for example, a library from
depending on an application.

| Layer           | Can depend on                                                    |
| --------------- | ---------------------------------------------------------------- |
| `automation`    | `application`, `tool`, `library`, `scaffolding`, `configuration` |
| `application`   | `tool`, `library`, `scaffolding`, `configuration`                |
| `tool`          | `tool`, `library`, `scaffolding`, `configuration`                |
| `library`       | `library`, `scaffolding`, `configuration`                        |
| `scaffolding`   | `scaffolding`, `configuration`                                   |
| `configuration` | `configuration`                                                  |
| `unknown`       | Anything                                                         |

Every layer can also depend on projects with an `unknown` layer. Note that applications and
automation projects cannot depend on other projects of their own layer.

<Callout>
  Layer constraints are only enforced between projects in the same
  [stack](#stacks), so a frontend application can depend on a backend
  application. Dependencies with the `build` or `root` scope are also exempt.
</Callout>

### Tags

The [`tags`](/api/moon/ProjectConfig#tags) setting is a list of arbitrary identifiers for grouping projects however you see fit,
such as by team, domain, or deployment target. Unlike stacks and layers, tags have no predefined
values.

<ConfigTabs
  file="moon"
  config={{
    tags: ["payments", "public-api"],
  }}
/>

Tags are used throughout moon:

- In [targets](./target), with the tag scope — `#payments:build` runs `build` in every project
  tagged `payments`.
- In [task inheritance](./task-inheritance#scoping-inheritance), with the [`inheritedBy.tags`](/api/moon/InheritedByConfig#tags)
  condition.
- In [MQL](./advanced/query-lang), with the `projectTag` field.

Tags can also enforce boundaries, through the [`constraints.tagRelationships`](/api/moon/ConstraintsConfig#tagrelationships) setting in
[`.moon/workspace.config`](./workspace). It maps a tag to a list of allowed tags, and a project with
that tag may only depend on projects that share the tag, or have one of the allowed tags.

<ConfigTabs
  file=".moon/workspace"
  config={{
    constraints: {
      tagRelationships: {
        payments: ["shared"],
      },
    },
  }}
  comments={{
    tagRelationships:
      "Projects tagged `payments` can only depend on `payments` or `shared` projects",
  }}
/>

### Language

The [`language`](/api/moon/ProjectConfig#language) setting describes _what the code is written in_. moon will try to auto-detect this from config
files in the project — a `package.json` implies `javascript`, a `Cargo.toml` implies `rust`, and so
on — but an explicit value in `moon.config` always takes precedence.

<ConfigTabs
  file="moon"
  config={{
    language: "typescript",
  }}
/>

The language is also used to [infer toolchains](#toolchains), so a project with the `typescript`
language is associated with the applicable toolchains without further configuration.

## Ownership

As a repository grows, knowing _who_ is responsible for a project becomes as important as knowing
what it does. moon supports this through human-readable metadata, and code ownership rules that can
be synced to your VCS provider.

### Metadata

The [`project`](/api/moon/ProjectConfig#project) setting provides information about the project for humans: what it is, who owns it,
and where to go for help. It has no effect on how moon runs tasks, but it's displayed by
[`moon project`](./commands/project), and is available to the [MCP server](./commands/mcp) and
anything else consuming the project graph.

- [`title`](/api/moon/ProjectMetadataConfig#title) - A human-readable name for the project.
- [`description`](/api/moon/ProjectMetadataConfig#description) - What the project does, and why it exists.
- [`owner`](/api/moon/ProjectMetadataConfig#owner) - The owning individual, team, or organization. The format is unspecified.
- [`maintainers`](/api/moon/ProjectMetadataConfig#maintainers) - A list of individual maintainers. The format is unspecified.
- [`channel`](/api/moon/ProjectMetadataConfig#channel) - A Slack, Discord, IRC, etc channel to discuss the project. Must start with `#`.

<ConfigTabs
  file="moon"
  config={{
    project: {
      title: "Payments API",
      description: "Handles checkout, refunds, and billing webhooks.",
      owner: "@acme/payments",
      maintainers: ["@alice", "@bob"],
      channel: "#team-payments",
    },
  }}
/>

Any additional fields are also accepted, and are preserved as custom metadata.

### Codeowners

The [`owners`](/api/moon/ProjectConfig#owners) setting defines which users, teams, or groups own the source code within the project,
by mapping file paths and globs, relative to the project root, to owners. moon aggregates these
rules from every project into a single `CODEOWNERS` file, formatted for your configured
[VCS provider](./workspace).

Paths can be defined as a map, where each path has its own list of owners:

<ConfigTabs
  file="moon"
  config={{
    owners: {
      paths: {
        "**/*": ["@acme/payments"],
        "src/webhooks/**/*": ["@acme/payments", "@acme/security"],
      },
    },
  }}
/>

Or as a list, where every path is owned by the [`defaultOwner`](/api/moon/OwnersConfig#defaultowner):

<ConfigTabs
  file="moon"
  config={{
    owners: {
      defaultOwner: "@acme/payments",
      paths: ["**/*"],
    },
  }}
/>

Some settings only apply to specific providers:

- [`optional`](/api/moon/OwnersConfig#optional) - GitLab only. Marks the code owners section as optional.
- [`requiredApprovals`](/api/moon/OwnersConfig#requiredapprovals) - BitBucket (legacy) and GitLab only. The number of approvals required for a
  request to be satisfied.
- [`customGroups`](/api/moon/OwnersConfig#customgroups) - BitBucket (legacy) only. A map of custom groups (prefixed with `@@@`) to lists of
  users and groups.

The `CODEOWNERS` file is generated with [`moon sync code-owners`](./commands/sync/code-owners), or
automatically during syncing when the [`codeowners.sync`](/api/moon/CodeownersConfig#sync) setting is enabled in
[`.moon/workspace.config`](./workspace).

## Ecosystem

Beyond running tasks, projects can be configured for the tools and platforms they're shipped with.

### Docker

moon's [Docker integration](./commands/docker) builds on top of the project graph, and the [`docker`](/api/moon/ProjectConfig#docker)
setting customizes how it treats this project.

The [`docker.file`](/api/moon/ProjectDockerConfig#file) settings configure the `Dockerfile` generated by
[`moon docker file`](./commands/docker/file):

- [`image`](/api/moon/DockerFileConfig#image) - The base Docker image. Defaults to the image provided by the first matching toolchain,
  otherwise `scratch`.
- [`buildTask`](/api/moon/DockerFileConfig#buildtask) - A task in this project to run when building the image. If not defined, the build
  step is skipped.
- [`startTask`](/api/moon/DockerFileConfig#starttask) - A task in this project to run in the `CMD` instruction. If not defined, the
  instruction is omitted.
- [`runSetup`](/api/moon/DockerFileConfig#runsetup) <VersionLabel version="2.0.0" /> - Run [`moon docker setup`](./commands/docker/setup)
  after scaffolding, but before building.
- [`runPrune`](/api/moon/DockerFileConfig#runprune) <VersionLabel version="2.0.0" /> - Run [`moon docker prune`](./commands/docker/prune)
  after building, but before starting.
- [`template`](/api/moon/DockerFileConfig#template) <VersionLabel version="2.0.0" /> - A custom [Tera](https://keats.github.io/tera/)
  template file, relative from the workspace root, to render the `Dockerfile` with.

<ConfigTabs
  file="moon"
  config={{
    docker: {
      file: {
        image: "node:22-alpine",
        buildTask: "build",
        startTask: "start",
      },
    },
  }}
/>

The [`docker.scaffold`](/api/moon/ProjectDockerConfig#scaffold) settings configure [`moon docker scaffold`](./commands/docker/scaffold), which
copies files into the build context in two phases:

- [`configsPhaseGlobs`](/api/moon/DockerScaffoldConfig#configsphaseglobs) <VersionLabel version="2.0.0" /> - Globs of additional files to include in
  the configs skeleton, which is used to install dependencies.
- [`sourcesPhaseGlobs`](/api/moon/DockerScaffoldConfig#sourcesphaseglobs) <VersionLabel version="2.0.0" /> - Globs of files to include in the sources
  skeleton, which is used to build the project.

<ConfigTabs
  file="moon"
  config={{
    docker: {
      scaffold: {
        sourcesPhaseGlobs: ["src/**/*", "!**/*.test.ts"],
      },
    },
  }}
/>
