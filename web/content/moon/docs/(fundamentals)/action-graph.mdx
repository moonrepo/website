The **action graph** is what moon actually executes, known as [actions](./action.mdx). Where the [project graph](./project-graph.mdx)
and [task graph](./task-graph.mdx) describe how things relate to one another, the action graph
describes the complete set of work required to satisfy a command, and the order that work has to
happen in.

It's built fresh for every run, from the targets you asked for. Running a single task is rarely
just running that task: the toolchain it needs may not be installed, dependencies may not be
installed, projects may need syncing, and other tasks may need to run first. Each of those is a
node in the graph, and the edges between them encode the ordering.

## How the graph is built

Requesting a task inserts a `RunTask` node, and then moon works backwards from it, adding the
nodes that must come first:

1. `RunTask` requires the project to be synced, so a `SyncProject` node is added.
2. `SyncProject` requires the workspace to be synced, and requires the projects it depends on to
   be synced first — so it fans out into `SyncWorkspace` and further `SyncProject` nodes.
3. `RunTask` also requires its toolchains' dependencies, adding `InstallDependencies`.
4. `InstallDependencies` requires `SetupEnvironment`, which requires `SetupToolchain`, which
   requires `SetupProto` when a version is involved — each also depending on `SyncWorkspace`.
5. Finally, the task's own [dependencies](./task.mdx#dependencies) are added as further
   `RunTask` nodes, recursively.

Every one of these steps is conditional. A toolchain that manages no versioned tool contributes no
`SetupToolchain` node; a task whose toolchains install nothing contributes no
`InstallDependencies`. Commands can also disable whole categories of action — this is what
[`moon run --no-actions`](../commands/run.mdx) does, reducing the graph to task execution alone.
[`moon exec`](../commands/exec.mdx) can also skip dependencies that weren't selected with
`--no-dependencies`, or add the tasks that depend on the selected ones with `--dependents`, both of
which can also be configured in the [`graph`](../guides/exec-plan.mdx#graph) block of an execution
plan.

## Ordering

Once built, the graph is sorted topologically so that every node runs after the nodes it depends
on. Because the graph is directed and acyclic, this ordering always exists — and when it doesn't,
moon reports the cycle by name rather than proceeding.

Topological order alone doesn't decide _when_ something runs, only what it must follow. Nodes with
no relationship between them are free to run in parallel, bounded by the pipeline's concurrency,
which defaults to the number of available CPU cores, and can be changed with the
[`--concurrency`](../commands/overview.mdx#concurrency) global option.

### Priority

Task nodes carry a priority, set through [`options.priority`](/moon/api/TaskOptionsConfig#priority), and the sorted graph is grouped by it
before dispatch:

| Priority   | Level |
| ---------- | ----- |
| `critical` | 0     |
| `high`     | 1     |
| `normal`   | 2     |
| `low`      | 3     |

Higher priority groups are dispatched first. Priority never overrides dependency order — it only
decides which of the currently _runnable_ nodes gets picked up next.

### Persistent tasks

[Persistent tasks](./task.mdx#persistent) never complete, so waiting on them in the middle of a
graph would stall everything behind them. moon avoids this by
dispatching them topologically like any other node, as soon as their own dependencies have
completed, and then treating them as done the moment they start. They also run outside of the
pipeline's concurrency limit, so a handful of long-running servers can't starve the rest of the
graph.

The effect is that a dev server's dependencies are guaranteed to have been built before it starts,
the server starts without waiting on unrelated tasks, and running a backend and a frontend server
together works without either blocking the other. Only persistent tasks, and tasks that
[`wait`](./task.mdx#dependency-types) for them to start, can depend on a persistent task.

```shell
# The servers start as soon as they're ready, while docs continue to build
$ moon run api:dev web:dev docs:build
```

### Interactive tasks

[Interactive tasks](./task.mdx#interactive) own stdin, so they run in isolation: once one is
dispatched, no other node is dispatched until it has completed. Nodes that were already running
continue in the background.

### Cleanup and wait dependencies

Task [dependency
types](./task.mdx#dependency-types) change how edges are dispatched:

- A `wait` dependency is dispatched before the task, but the task is released as soon as the
  dependency has _started_. Like persistent tasks, it runs outside of the concurrency limit, so the
  task waiting on it can always run alongside it.
- A `cleanup` dependency is dispatched _after_ the task has ran its command. When a failure aborts
  the pipeline, the cleanup dependencies of tasks that already ran are still dispatched before moon
  exits.

## Inspecting

The action graph is the most useful of the three graphs for answering "why is this running?", and
the most granular — a single task expands into several nodes here.

- [`moon action-graph`](../commands/action-graph.mdx) - Serves the interactive visualizer, or prints
  the graph with `--dot` (Graphviz) or `--json`. Pass targets to focus it.
- [`moon run --summary`](../commands/run.mdx) - Prints a summary of every action the pipeline ran,
  after the fact.
- [`moon ci`](../commands/ci.mdx) - Builds the graph from affected targets, and
  [shards it across jobs](../guides/ci.mdx#parallelizing-tasks) with `--job` and `--job-total`.

```shell
# Visualize everything moon would do for a target
$ moon action-graph app:build

# Include every task that depends on it too
$ moon action-graph app:build --dependents deep
```
