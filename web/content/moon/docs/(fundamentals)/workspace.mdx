The **workspace** is the root of a moon-managed repository, and the boundary of everything moon
does. It's where moon discovers [projects](./project.mdx), builds the
[project graph](./project-graph.mdx) and [task graph](./task-graph.mdx), runs [tasks](./task.mdx),
and stores its cache. A workspace is marked by a `.moon` directory, typically at the root of your
repository, and configured by [`.moon/workspace.config`](#configuration).

Most repositories have a single workspace that spans the whole repository, but a workspace can also
live in a subdirectory, like when moon only manages part of a larger repository.

## Key characteristics

- **Rooted by a directory** - The directory that contains `.moon` is the workspace root, and moon
  finds it from anywhere inside, so commands work the same from any project.
- **Configuration driven** - `.moon/workspace.config` is the only required file. Toolchains,
  extensions, and inherited tasks each have their own optional file.
- **A single graph** - Every project in the workspace, and every task within them, is part of one
  project graph and task graph, so dependencies can cross any project boundary.
- **VCS aware** - Git powers change detection, file hashing, and hooks, which is what keeps affected
  runs and caching fast.

## Workspace root

When you run a command, moon looks for a `.moon` directory in the current working directory, then in
each parent directory, until it finds one. That directory becomes the workspace root, and
workspace-relative paths in configuration are resolved from it.

- A `.config/moon` directory is also supported, for repositories that keep tool configuration under
  `.config`. When both exist, `.config/moon` is used.
- The `MOON_WORKSPACE_ROOT` environment variable skips the search and uses the given directory,
  which must contain a `.moon` or `.config/moon` directory.
- Your home directory is never a workspace, as `~/.moon` is where moon stores its own global data,
  like downloaded plugins.

When no workspace is found, commands fail with an error like "Unable to determine workspace root".
To create a workspace, run [`moon init`](../commands/init.mdx), which writes a starter
`.moon/workspace.config` and detects VCS settings from your repository.

```shell
# Create a workspace in the current directory
$ moon init

# Run a command from a different directory
$ MOON_WORKSPACE_ROOT=/path/to/repo moon projects
```

### Directory layout

The `.moon` directory holds configuration, and the files moon generates:

- `workspace.config` - Configures the workspace, as described on this page. Required.
- [`toolchains.config`](./toolchain.mdx) - Enables and configures [toolchains](./toolchain.mdx).
- [`extensions.config`](./extension.mdx) - Registers [extensions](./extension.mdx).
- [`tasks/*.config`](./task-inheritance.mdx) - Tasks inherited by projects (see
  [task inheritance](./task-inheritance.mdx)).
- `cache` - The local cache of hashes, task outputs, and state. Clean it up with
  [`moon clean`](../commands/clean.mdx).
- `docker` - The skeleton generated by
  [`moon docker scaffold`](../commands/docker/scaffold.mdx).
- `hooks` - Scripts generated for [VCS hooks](#vcs-hooks).

The `cache` and `docker` directories are specific to each machine, and `moon init` adds them to your
`.gitignore`. Configuration files should be committed, so the whole team shares them.

## Core features

### Version control integration

moon integrates with Git, the only supported [`vcs.client`](/moon/api/VcsConfig#client), and uses it
for:

- **Changed files** - Files changed in your working tree, or between two revisions, determine which
  projects and tasks are [affected](../advanced/affected.mdx). This powers affected tracking and detection.
- **Project discovery** - Directories ignored by Git are skipped when matching project globs.
- **Hooks** - Commands can run on Git events, like before a commit (see [VCS hooks](#vcs-hooks)).

Revisions are compared against [`vcs.defaultBranch`](/moon/api/VcsConfig#defaultbranch) (`master`
unless configured, but [`moon init`](../commands/init.mdx) detects it), using the merge base with
your current branch. moon also checks the same branch on each of the
[`vcs.remoteCandidates`](/moon/api/VcsConfig#remotecandidates) (`origin` and `upstream`), and uses
the most recent divergence point, so a stale local branch or a fork doesn't inflate the list of
changed files. See [comparing revisions](../guides/ci.mdx#comparing-revisions) for how CI picks its
revisions.

<ConfigTabs
  file=".moon/workspace"
  config={{
    vcs: {
      defaultBranch: "main",
      provider: "gitlab",
    },
  }}
/>

The Git repository is found by walking up from the workspace root, so the workspace doesn't need to
be at the root of the repository. Worktrees and submodules are supported. When there's no `.git`, or
no `git` binary on `PATH`, Git integration is disabled: inputs are hashed by walking the file system,
and hooks aren't generated.

### Project discovery

Projects are located with the [`projects`](/moon/api/WorkspaceConfig#projects) setting, which
accepts a list of globs, a map of project IDs to paths, or both. Nothing is discovered by default,
so a new workspace has no projects until this setting is configured.

<ConfigTabs
  file=".moon/workspace"
  config={{
    projects: {
      globs: ["apps/*", "packages/*"],
      sources: {
        root: ".",
      },
    },
  }}
/>

See [project discovery](./project.mdx#discovery) for the full rules, and run
[`moon projects`](../commands/projects.mdx) to list what was found.

### Project constraints

As a repository grows, it's easy for projects to depend on things they shouldn't, like a library
importing from an application. The [`constraints`](/moon/api/WorkspaceConfig#constraints) setting
enforces boundaries between projects, and building the project graph fails when a dependency
crosses one:

- **Layers** - With [`enforceLayerRelationships`](/moon/api/ConstraintsConfig#enforcelayerrelationships)
  enabled (the default), a project can only depend on projects in the same or a lower
  [layer](./project.mdx#layers), within the same [stack](./project.mdx#stacks).
- **Tags** - [`tagRelationships`](/moon/api/ConstraintsConfig#tagrelationships) maps a tag to the
  tags its projects may depend on. A project with that tag may only depend on projects that share
  the tag, or have one of the allowed tags (see [tags](./project.mdx#tags)).

<ConfigTabs
  file=".moon/workspace"
  config={{
    constraints: {
      enforceLayerRelationships: true,
      tagRelationships: {
        payments: ["shared"],
      },
    },
  }}
  comments={{
    tagRelationships:
      "Projects tagged `payments` can only depend on `payments` or `shared` projects",
  }}
/>

### Code ownership

moon can generate a `CODEOWNERS` file from the [`owners`](./project.mdx#codeowners) of every
project, so ownership lives next to the code it describes. The workspace's
[`codeowners`](/moon/api/WorkspaceConfig#codeowners) setting adds rules of its own, and controls how
the file is generated:

- [`globalPaths`](/moon/api/CodeownersConfig#globalpaths) - Owners for paths outside of projects,
  like the workspace root. They're written before project rules, so project rules take precedence
  where both match.
- [`orderBy`](/moon/api/CodeownersConfig#orderby) - Order project rules by `file-source` (the
  default) or `project-id`.
- [`requiredApprovals`](/moon/api/CodeownersConfig#requiredapprovals) - The number of approvals
  required for every path (GitLab and Bitbucket legacy only).
- [`sync`](/moon/api/CodeownersConfig#sync) - Generate the file automatically during workspace
  syncing.

<ConfigTabs
  file=".moon/workspace"
  config={{
    codeowners: {
      globalPaths: {
        "*": ["@acme/admins"],
        "/.github/": ["@acme/infra"],
      },
      sync: true,
    },
  }}
/>

The file's format and location follow [`vcs.provider`](/moon/api/VcsConfig#provider):
`.github/CODEOWNERS` for GitHub, `.gitlab/CODEOWNERS` for GitLab, `.bitbucket/CODEOWNERS` for
Bitbucket, and `CODEOWNERS` otherwise. To generate it manually, run
[`moon sync code-owners`](../commands/sync/code-owners.mdx). See the
[code owners guide](../guides/codeowners.mdx) for more.

### Code generation

[`moon generate`](../commands/generate.mdx) scaffolds files from templates, like a new library or
application. The [`generator.templates`](/moon/api/GeneratorConfig#templates) setting lists where
templates are located, and defaults to the `./templates` directory. Locations can be file paths or
globs relative to the workspace root, Git repositories, npm packages, or URLs to an archive, so
templates can be shared across repositories.

<ConfigTabs
  file=".moon/workspace"
  config={{
    generator: {
      templates: ["./templates", "git://github.com/acme/templates#main"],
    },
  }}
/>

See the [code generation guide](../guides/codegen.mdx) for how templates are written.

### Content hashing

Before running a task, moon hashes everything that can affect its result, like its
[inputs](./task.mdx#inputs), command, arguments, environment variables, and toolchain versions. When
the hash matches a previous run, moon restores the cached outputs instead of running the task. The
[`hasher`](/moon/api/WorkspaceConfig#hasher) setting tunes how this works:

- [`walkStrategy`](/moon/api/HasherConfig#walkstrategy) - How a project's files are collected. With
  `vcs` (the default), moon asks Git for the project's tracked, modified, and untracked files, which
  skips ignored files and is faster than walking the file system. With `glob`, the file system is
  walked. Globs are always walked for projects at the workspace root, for inputs outside the task's
  project, and when Git is unavailable.
- [`optimization`](/moon/api/HasherConfig#optimization) - With `accuracy` (the default), toolchains
  hash dependency versions from lockfiles. With `performance`, the version ranges from manifests are
  hashed instead, which is faster but misses upgrades within the same range (see
  [parsing manifest and lock files](./toolchain.mdx#parsing-manifest-and-lock-files)).
- [`ignorePatterns`](/moon/api/HasherConfig#ignorepatterns) - Workspace-relative globs for files to
  leave out of every hash, like generated files that change on every run. Prefix them with `**/`.
- [`warnOnMissingInputs`](/moon/api/HasherConfig#warnonmissinginputs) - Logs a warning when an
  input file doesn't exist (enabled by default). Files matching
  [`ignoreMissingPatterns`](/moon/api/HasherConfig#ignoremissingpatterns), which defaults to `.env`
  files, are never warned about.

<ConfigTabs
  file=".moon/workspace"
  config={{
    hasher: {
      ignorePatterns: ["**/*.snap"],
      warnOnMissingInputs: false,
    },
  }}
/>

Uncommitted changes are hashed too, so local runs always reflect your current code. To see what
went into a hash, run [`moon hash`](../commands/hash.mdx).

### Pipeline management

Tasks run in the [action pipeline](./action-graph.mdx), alongside the actions that prepare for them,
like syncing projects and installing dependencies. The
[`pipeline`](/moon/api/WorkspaceConfig#pipeline) setting controls which of those actions run, and
how processes behave:

- [`syncWorkspace`](/moon/api/PipelineConfig#syncworkspace),
  [`syncProjects`](/moon/api/PipelineConfig#syncprojects), and
  [`syncProjectDependencies`](/moon/api/PipelineConfig#syncprojectdependencies) - Toggle syncing
  before tasks run. See [syncing operations](./toolchain.mdx#syncing-operations).
- [`installDependencies`](/moon/api/PipelineConfig#installdependencies) - Toggle installing
  dependencies before tasks run, for all toolchains or a list of toolchain IDs. See
  [installing dependencies](./toolchain.mdx#installing-and-deduping-dependencies).
- [`killProcessThreshold`](/moon/api/PipelineConfig#killprocessthreshold) - How long, in
  milliseconds, to wait for running tasks to exit after moon receives a signal (like pressing
  Ctrl+C), before killing them. Defaults to `2000`, and `0` lets them run to completion.
- [`logRunningCommand`](/moon/api/PipelineConfig#logrunningcommand) - Log each task's command and
  arguments when it runs.
- [`inheritColorsForPipedTasks`](/moon/api/PipelineConfig#inheritcolorsforpipedtasks) - Pass moon's
  color settings to tasks, so tools keep their colored output even though moon pipes it. Enabled by
  default.

<ConfigTabs
  file=".moon/workspace"
  config={{
    pipeline: {
      installDependencies: ["node"],
      logRunningCommand: true,
    },
  }}
  comments={{
    installDependencies: "Only install dependencies for the Node.js toolchain",
  }}
/>

### Caching

Hashes, task outputs, and state are cached in `.moon/cache`. After each run, moon removes cached
items older than [`pipeline.cacheLifetime`](/moon/api/PipelineConfig#cachelifetime) (`7 days` by
default), unless [`pipeline.autoCleanCache`](/moon/api/PipelineConfig#autocleancache) is disabled. To clean it manually, run [`moon clean`](../commands/clean.mdx).

The [`cache`](/moon/api/WorkspaceConfig#cache) setting configures the local store of task outputs:

- [`cas.maxSize`](/moon/api/CacheCasConfig#maxsize) - The maximum size of the store, like `10gb`.
  When exceeded, the least recently used outputs are evicted. Unlimited by default.
- [`cas.verifyIntegrity`](/moon/api/CacheCasConfig#verifyintegrity) - Verify outputs on every read,
  which is slower, but detects corruption on disk.
- [`sharedWorktreeCache`](/moon/api/CacheConfig#sharedworktreecache) - Share task outputs between
  the Git worktrees of a repository, so switching worktrees doesn't rebuild everything. Hashes and
  state are still kept per worktree. This setting is unstable, and is configured as
  `unstable_sharedWorktreeCache`.

<ConfigTabs
  file=".moon/workspace"
  config={{
    cache: {
      cas: {
        maxSize: "10gb",
      },
    },
    pipeline: {
      cacheLifetime: "3 days",
    },
  }}
/>

See the [cache guide](../advanced/cache.mdx) for more.

### Remote caching

A local cache only helps the machine that created it. With remote caching, task outputs are shared
between every developer and CI machine, so a task that already ran anywhere doesn't need to run
again. moon supports any service that implements the Bazel Remote Execution API, like
[bazel-remote](https://github.com/buchgr/bazel-remote), over gRPC (the default) or HTTP.

Remote caching is enabled by configuring a [`remote.host`](/moon/api/RemoteConfig#host):

<ConfigTabs
  file=".moon/workspace"
  config={{
    remote: {
      host: "grpcs://cache.example.com",
      auth: {
        token: "REMOTE_CACHE_TOKEN",
      },
      cache: {
        localReadOnly: true,
      },
    },
  }}
  comments={{
    token: "The name of an environment variable that contains the token",
    localReadOnly: "Only upload outputs in CI",
  }}
/>

The [`auth`](/moon/api/RemoteConfig#auth), [`tls`](/moon/api/RemoteConfig#tls), and
[`mtls`](/moon/api/RemoteConfig#mtls) settings configure authentication. With
[`cache.localReadOnly`](/moon/api/RemoteCacheConfig#localreadonly) enabled, local machines only
download outputs, and only CI uploads them, which keeps unverified local builds out of the shared
cache.

### Notifications

The [`notifier`](/moon/api/WorkspaceConfig#notifier) setting reports on runs, which is handy for
long builds you don't want to watch:

- [`terminalNotifications`](/moon/api/NotifierConfig#terminalnotifications) - Show an operating
  system notification when the pipeline succeeds or fails, or when a task fails.
- [`webhookUrl`](/moon/api/NotifierConfig#webhookurl) - Send pipeline events to a secure URL, like
  a CI dashboard or chat integration.

<ConfigTabs
  file=".moon/workspace"
  config={{
    notifier: {
      terminalNotifications: "failure",
    },
  }}
/>

See the [notifications guide](../guides/notifications.mdx) for the events and payloads.

## Configuration

The workspace is configured in `.moon/workspace.config`, which must exist for moon to run. Every
setting is optional, but most workspaces configure at least [`projects`](#project-discovery) and
[`vcs`](#version-control-integration).

<ConfigTabs
  file=".moon/workspace"
  config={{
    projects: ["apps/*", "packages/*"],
    vcs: {
      defaultBranch: "main",
    },
    versionConstraint: ">=2.6.0",
  }}
/>

Settings not covered above:

- [`docker`](/moon/api/WorkspaceConfig#docker) - Defaults for moon's Docker integration, like the
  base image of generated `Dockerfile`s. See the [Docker guide](../guides/docker.mdx).
- [`experiments`](/moon/api/WorkspaceConfig#experiments) - Opt in to, or out of, features that are
  still being developed.
- [`telemetry`](/moon/api/WorkspaceConfig#telemetry) <TypeLabel type="boolean" /> - Collect
  anonymous usage information, and check for new moon versions. Defaults to `true`, and can be
  disabled with `MOON_TELEMETRY=false`.
- [`$schema`](/moon/api/WorkspaceConfig#schema) <TypeLabel type="string" /> - The JSON schema used
  by editors for validation and autocompletion. See [schema validation](./config.mdx#schema-validation).

### Sharing configuration

The [`extends`](/moon/api/WorkspaceConfig#extends) setting inherits settings from one or more other
files, so a common configuration can be shared across repositories. It accepts a relative file path
or an `https://` URL, or a list of them, and extended files can extend others in turn. Settings in
the extending file take precedence over the files it extends.

<ConfigTabs
  file=".moon/workspace"
  config={{
    extends: "https://example.com/moon/workspace.yml",
    projects: ["apps/*"],
  }}
/>

### Version constraint

Running a different moon version than the rest of your team can lead to confusing differences in
behavior. The [`versionConstraint`](/moon/api/WorkspaceConfig#versionconstraint) setting requires
the moon binary to match a version range, and moon fails with an error like "Invalid moon version,
unable to proceed" when it doesn't.

<ConfigTabs
  file=".moon/workspace"
  config={{
    versionConstraint: "^2.6.0",
  }}
/>

When upgrading with [`moon upgrade`](../commands/upgrade.mdx), pass `--update-constraint` to update
the constraint to the new version.
