Running [tasks](<../(fundamentals)/task.mdx>) is the most common way to interact with moon, so what
do you do when your task isn't working as expected? Diagnose it of course! Diagnosing the root cause
of a broken task can be quite daunting, but do not fret, as the following steps will help guide you
in this endeavor. If the task works, but is slow, see the [profiling guide](../guides/profile.mdx)
instead.

## Using an AI skill

We provide an AI agent skill called `debug-task` that helps you systematically diagnose failing or
misbehaving moon tasks. If you've ever spent time hunting down why a task is producing stale
results, getting unexpected cache misses, or behaving differently in CI, this skill is for you.

To install this skill, run the following command:

```shell
# Install the skill from the moon repository
$ npx skills add moonrepo/moon --skill debug-task
```

The skill walks your agent through a 5-step diagnostic workflow, using the same commands described
in the rest of this page:

1. Inspect the resolved task configuration (after inheritance merging).
2. Run with maximum verbosity to see exactly what moon is doing.
3. Inspect cache state and hash manifests.
4. Match symptoms to root causes using a built-in decision table.
5. Validate that the fix actually resolves the issue.

It covers over 30 specific symptoms across cache issues, configuration mistakes, execution problems,
and CI vs local discrepancies. Most issues resolve by step 3, with deeper reference material
available on demand.

To use it, simply describe your task problem in Claude Code, Codex, OpenCode, or another AI agent
that supports skills. Mention the task target, what you expected, and what actually happened, and
the skill takes it from there.

```text
/debug-task Help me debug why the `app:build` task is not being cached
```

## Verify configuration

Before we dive into the internals of moon, we should first verify that the task is actually
configured correctly. Our configuration layer is very strict, but it can't catch everything, so jump
to the [tasks](<../(fundamentals)/task.mdx>) documentation for more information.

To start, inspect the task with [`moon task`](../commands/task.mdx), which displays the task after
[inheritance](<../(fundamentals)/task-inheritance.mdx>) has been merged, [tokens](../advanced/tokens.mdx)
have been resolved, and paths have been expanded. Pass `--json` to see every field.

```shell
# Inspect the resolved task
$ moon task app:build

# Print every field as JSON
$ moon task app:build --json
```

Some issues to look out for:

- Have `command` and `args` been parsed correctly? Commands with shell syntax, like pipes (`|`) or
  `&&`, must use [`script`](/moon/api/TaskConfig#script) instead.
- Have [tokens](../advanced/tokens.mdx) resolved correctly? If not, verify syntax or try another
  token type.
- Have `inputFiles`, `inputGlobs`, and `inputEnv` expanded correctly from
  [`inputs`](/moon/api/TaskConfig#inputs)? In a multi-project workspace, tasks in the
  [root-level project](../guides/root-project.mdx#inputs-are-empty-by-default) have no inputs by
  default.
- Have `outputFiles` and `outputGlobs` expanded correctly from
  [`outputs`](/moon/api/TaskConfig#outputs)?
- Are the `toolchains` correct for the command, and in the right order? The first toolchain is the
  primary one. If incorrect, explicitly set [`toolchains`](/moon/api/TaskConfig#toolchains).
- Are the `type`, `options`, and `state` correct? For example, whether the task is
  [persistent](<../(fundamentals)/task.mdx#persistent>), cached, or
  [runs in CI](<../(fundamentals)/task.mdx#local-only>).

<Callout>
  moon also writes a snapshot of each project, including its resolved tasks, to
  `.moon/cache/states/<project>/snapshot.json` in the `SyncProject` action,
  which typically runs before its tasks.
</Callout>

### Verify inherited configuration

If the configuration from the previous step looks correct, you can skip this step, otherwise let's
verify that the inherited configuration is also correct. The human-readable output of
[`moon task`](../commands/task.mdx) lists which configuration layers the task's settings came from.
For more detail, inspect the root `inherited` object of
[`moon project <id> --json`](../commands/project.mdx) (or the project's `snapshot.json`), which is
structured as follows:

- `configs` - A mapping of [`.moon/tasks/*.config`](<../(fundamentals)/task-inheritance.mdx>) files
  that were inherited by the project, in order. Each config represents a partial object (not
  expanded or resolved).
- `layers` - A mapping of task IDs to the configuration files they inherited from.

## Inspect trace logs

If configuration looks good, let's move on to inspecting the trace logs, which can be a non-trivial
amount of effort. Run the task to generate the logs, bypass the cache, and include debug
information:

```shell
# Run the task with trace logs, bypassing the cache
$ MOON_DEBUG_PROCESS_ENV=true MOON_DEBUG_PROCESS_INPUT=true moon run app:build --log trace --force
```

- `--force` bypasses the cache (while still writing to it), and runs the task even if it's not
  affected by changes.
- `MOON_DEBUG_PROCESS_ENV` logs every environment variable passed to child processes, instead of
  only those prefixed with `MOON_` or `PROTO_`.
- `MOON_DEBUG_PROCESS_INPUT` logs the full input passed to child processes, instead of truncating
  it.

Not every problem shows up in these logs. When the daemon is enabled, failures to archive or restore
outputs are only reported in [its own logs](../guides/daemon.mdx#task-outputs-are-missing-or-stale),
and connection errors with a [remote cache](../guides/remote-cache.mdx#debugging) are only logged
when `MOON_DEBUG_REMOTE` is set.

Once ran, a large amount of information will be logged to the terminal (pass `--log-file <path>` to
write it to a file instead). However, most of it can be ignored, as we're only interested in how
the task's inputs are gathered and hashed. This breaks down as follows:

1. First, we gather changed files from the local checkout with
   `git status --porcelain --untracked-files --ignore-submodules -z`, so that uncommitted changes in
   the project are reflected in the hash.
2. Secondly, for tasks with input globs, we gather all files from the project directory with
   `git ls-files --full-name --cached --modified --others --exclude-standard -z <path>`. This
   command can also be ran locally to verify the output. Projects at the workspace root, and the
   `glob` [`hasher.walkStrategy`](/moon/api/HasherConfig#walkstrategy), walk the file system
   instead.
3. Lastly, the contents of all matching input files are hashed. By default, moon hashes files
   natively, but when [`experiments.nativeFileHashing`](/moon/api/ExperimentsConfig#nativefilehashing)
   is disabled, the `git hash-object --stdin-paths` command is used instead, and
   `MOON_DEBUG_PROCESS_INPUT` displays the list of every file being hashed.

If all went well, you should see a log entry that looks like this:

```text
moon_task_runner::task_runner  Generated a unique hash  task_target="app:build" hash="<hash>"
```

The important piece is the hash, which is a 64-character SHA-256 hash, and represents the unique
hash of this task/target. This is what moon uses to determine a cache hit/miss, and whether or not
to skip re-running a task.

<Callout>
  For a quicker way to get the hash, pass `--output-style hash` to [`moon
  run`](../commands/run.mdx), which prints the hash instead of the task's
  output, or read the `hash` field from
  `.moon/cache/states/<project>/<task>/lastRun.json`, which records the last
  run.
</Callout>

Let's copy the hash and move on to the next step.

## Inspect the hash manifest

With the hash in hand, let's dig deeper into moon's internals, by inspecting the hash manifest with
the [`moon hash`](../commands/hash.mdx) command. Manifests are stored as blobs in the local
content-addressable cache (`.moon/cache/blobs`), so always read them through this command. A unique
prefix of the hash works too.

```shell
# Inspect a hash manifest
$ moon hash <hash>
```

The manifest is JSON and its contents are all the information used to generate its unique hash.
This information is an array, and breaks down as follows:

- The first item in the array is the task itself. The important fields to diagnose here are `deps`
  and `inputs`.
  - Dependencies are other tasks (and their hash) that this task depends on.
  - Inputs are all the files (and their content hash) this task requires to run.
  - The `command`, `args`, `env`, `inputEnv`, `outputs`, and `toolchains` fields are also
    included, as changing any of them changes the hash.
- The remaining array items are toolchain specific, contributed by each of the task's toolchains,
  like the current tool version, and the resolved versions of dependencies from lockfiles (see
  [`hasher.optimization`](/moon/api/HasherConfig#optimization)).
- When the task has [`fingerprint` checks](<../(fundamentals)/task.mdx#checks>), their results are
  the last item.

Some issues to look out for:

- Do the dependencies match the task's configured [`deps`](/moon/api/TaskConfig#deps) and
  [`implicitDeps`](/moon/api/InheritedTasksConfig#implicitdeps)?
- Do the inputs match the task's configured [`inputs`](/moon/api/TaskConfig#inputs) and
  [`implicitInputs`](/moon/api/InheritedTasksConfig#implicitinputs)? If not, try tweaking the
  config.
- Are the toolchain specific items correct?
- Are dependency versions/hashes correctly parsed from the appropriate lockfile?

<Callout>
  If `moon hash` can't find the manifest, it may have been removed when the
  cache was cleaned. Run the task again with `--force` to regenerate it.
</Callout>

### Diffing a previous hash

Another avenue for diagnosing a task is to diff the hash against a hash from a previous run. Since
we require multiple hashes, we'll need to run the task multiple times,
[inspect the logs](#inspect-trace-logs), and extract the hash for each. If you receive the same hash
for each run, you'll need to tweak configuration or change files to produce a different hash.

Once you have 2 unique hashes, we can pass them to the [`moon hash`](../commands/hash.mdx) command.
This will produce a `git diff` styled output, allowing for simple line-by-line comparison
debugging.

```shell
# Diff two hash manifests
$ moon hash <hash-left> <hash-right>
```

```diff
Left:  0b55b234f1018581c45b00241d7340dc648c63e639fbafdaf85a4cd7e718fdde
Right: 2388552fee5a02062d0ef402bdc7232f0a447458b058c80ce9c3d0d4d7cfe171

[
	{
		"command": "build",
		"args": [
+			"./dist"
-			"./build"
		],
		...
	}
]
```

This is extremely useful in diagnosing why a task is running differently than before, and is much
easier than inspecting the hash manifests manually!
