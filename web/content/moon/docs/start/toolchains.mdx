At this point, moon knows about your projects, but not which languages they're written in. Every
task runs through the `system` toolchain, which runs commands with the binaries on your `PATH`.
That works, but leaves a lot on the table. Enabling a [toolchain](<../(fundamentals)/toolchain.mdx>)
for a language teaches moon about its ecosystem, so it can:

- **Detect usage** - Recognize which projects and tasks use the language, from files like
  `package.json` or `Cargo.toml`, and commands like `node` or `cargo`.
- **Install dependencies** - Install dependencies before tasks run, like `pnpm install`, but only
  when the lockfile, manifests, or settings change.
- **Infer relationships** - Turn dependencies between packages in your manifests into project
  dependencies, so they don't need to be repeated in `dependsOn`.
- **Hash precisely** - Include the locked versions of a project's dependencies in its task hashes,
  so upgrading a dependency only re-runs the tasks that use it.
- **Pin versions** - Download and install a specific version of the language, so every machine runs
  the same one.

Toolchains are optional, and can be enabled at any time. If you'd rather keep running your own
tools from `PATH` for now, skip ahead to [creating tasks](./tasks.mdx).

## Enabling a toolchain

Toolchains are enabled in [`.moon/toolchains.config`](<../(fundamentals)/toolchain.mdx>), where each
top-level key is a toolchain ID. The easiest way to add one is with
[`moon toolchain add`](../commands/toolchain/add.mdx), which detects a version from your
repository, prompts for the toolchain's settings, and writes the entry for you (creating the file
if needed).

Choose your ecosystem below. Most languages need a single toolchain, while ecosystems like
JavaScript and Python combine a language toolchain with one for the runtime or package manager.

The [JavaScript toolchain](../toolchains/javascript/index.mdx) integrates with `package.json`
files and installs dependencies, while the [Node.js](../toolchains/javascript/node.mdx) toolchain
manages the runtime, and a package manager toolchain, like [pnpm](../toolchains/javascript/pnpm.mdx),
manages the package manager.

```shell
$ moon toolchain add javascript
$ moon toolchain add node
$ moon toolchain add pnpm
```

Using a language or tool that moon doesn't support out of the box? Toolchains are WASM plugins, so
you can enable a third-party toolchain, or
[create your own](<../(fundamentals)/toolchain.mdx#creating-a-toolchain>). Unlike built-in
toolchains, moon doesn't know where to download these plugins from, so they require a
[`plugin`](/moon/api/ToolchainPluginConfig#plugin) locator that points to the plugin's `.wasm` file.
Pass it as the second argument to `moon toolchain add`:

```shell
# Add a toolchain from a GitHub release
$ moon toolchain add example github://acme/example-toolchain@v1.0.0

# Add a toolchain that you're developing locally
$ moon toolchain add example file://../plugins/example_toolchain.wasm
```

<ConfigTabs
  file=".moon/toolchains"
  config={{
    example: {
      plugin: "github://acme/example-toolchain@v1.0.0",
      version: "1.2.0",
      someSetting: true,
    },
  }}
  comments={{
    version: "Only applies if the plugin supports tool management",
    someSetting: "A setting of the plugin's own",
  }}
/>

The ID (`example` above) is up to you, and is how projects, tasks, and environment variables refer to
the toolchain. Locators support the `file://`, `https://`, `github://`, and `registry://` protocols
(see [plugin locators](../../../wasm/docs/plugin-locators.mdx)), and relative `file://` paths are
resolved from the `.moon` directory. Any setting that isn't one of moon's own, like `someSetting`, is
passed to the plugin as its configuration.

</Tab>
</Tabs>

toolchains detected for each project. See [built-in toolchains](<../(fundamentals)/toolchain.mdx#built-in-toolchains>)
for every toolchain that moon supports out of the box.

## Pinning tool versions

The `version` setting is what makes moon manage the tool for you. When a task needs a toolchain
with a version, moon downloads and installs that version through [proto](../../../proto/docs/index.mdx)
(installing proto itself first, if needed), and runs the task with it on `PATH`. Every developer and
CI machine gets the exact same version, without installing anything themselves.

Without a `version`, moon uses the tool's binary on your `PATH` instead, which must already be
installed.

If your repository already pins versions in a `.prototools` file, you can leave `version` out of
`.moon/toolchains.config`, as moon inherits versions from `.prototools` by default:

```toml title=".prototools"
node = "24.12.0"
pnpm = "10.24.0"
```

Tools are installed the first time they're needed, like when running a task. To install them ahead
of time, or to check that installation works, run [`moon setup`](../commands/setup.mdx). And to find
the binary that tasks will use, run [`moon bin`](../commands/bin.mdx).

```shell
# Install every configured tool
$ moon setup

# Print the path to the Node.js binary that tasks run with
$ moon bin node
```

See [tool management](<../(fundamentals)/toolchain.mdx#tier-3-tool-management>) for where versions
are resolved from, and how to override them.
