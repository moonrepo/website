The Rust toolchain integrates [Rust](https://www.rust-lang.org) and [Cargo](https://doc.rust-lang.org/cargo/) into moon.
With it enabled, moon:

- Detects which projects and tasks use Rust, and infers project aliases and dependencies from `Cargo.toml` manifests.
- Includes the crate versions locked in `Cargo.lock` in task hashes, so upgrading a crate only invalidates the projects that
  use it.
- Installs Rust toolchains through rustup, and keeps `rust-toolchain.toml` and the minimum supported Rust version in sync
  with the configured version.
- Installs rustup components, targets, and Cargo binaries on demand.
- Scaffolds and prunes Docker images for Rust projects.

Enable it whenever your repository contains Rust code, whether that's a single binary crate, a Cargo workspace with dozens of
members, or a polyglot monorepo where Rust is one language of many.

## Prerequisites

Before enabling the Rust toolchain, make sure you have the following:

- **Rust** - When [`version`](/moon/api/ToolchainPluginConfig#version) is configured, moon installs Rust for you (with
  rustup, which is installed first if it's missing). Otherwise, a `cargo` binary must be available on your `PATH`, typically
  installed with [rustup](https://rustup.rs). Besides running tasks, moon runs `cargo` itself to generate lockfiles, install
  [`bins`](#cargo-binaries), and read package metadata when pruning Docker images. The toolchain doesn't require a minimum
  Rust version.
- **rustup** - Required by the [`components` and `targets`](#components-and-targets) settings, which run `rustup` directly.

### Repository structure

The Rust toolchain supports the following repository layouts. Directories only become moon
[projects](<../(fundamentals)/project.mdx>) when they're matched by the [`projects`](/moon/api/WorkspaceConfig#projects)
setting in [`.moon/workspace.config`](<../(fundamentals)/workspace.mdx>). The toolchain doesn't discover Cargo workspace
members on its own.

#### Single crate

A single package at the root of the repository.

```text
./
├── .moon/
├── src/
│   └── main.rs
├── Cargo.lock
└── Cargo.toml
```

In this layout, the crate is both the project and its own dependencies root.

#### Multiple crates workspace

The most common layout for monorepos, where the root `Cargo.toml` is a virtual manifest that only defines a `[workspace]`
table, and each member crate is a moon project.

```text
./
├── .moon/
├── crates/
│   ├── client/
│   │   ├── src/
│   │   └── Cargo.toml
│   ├── server/
│   │   ├── src/
│   │   └── Cargo.toml
│   └── utils/
│       ├── src/
│       └── Cargo.toml
├── Cargo.lock
└── Cargo.toml
```

In this layout, the root is the dependencies root for every member, and they all share the root `Cargo.lock` and `target`
directory.

<ConfigTabs
  file=".moon/workspace"
  config={{
    projects: ["crates/*"],
  }}
/>

If the root `Cargo.toml` defines both `[package]` and `[workspace]` tables (a root package with members), it's treated the
same way. Map the root crate to a project as well if you want to run tasks against it.

#### Nested crates and workspaces

Crates and Cargo workspaces in subdirectories, where independent crates (each with their own `Cargo.lock`) live alongside
other ecosystems in a polyglot monorepo.

```text
./
├── .moon/
├── apps/
│   ├── server/
│   │   ├── src/
│   │   ├── Cargo.lock
│   │   └── Cargo.toml
│   └── web/
│       └── package.json
└── tools/
    ├── cli/
    │   ├── src/
    │   └── Cargo.toml
    ├── codegen/
    │   ├── src/
    │   └── Cargo.toml
    ├── Cargo.lock
    └── Cargo.toml
```

In this layout, `apps/server` is its own dependencies root, while `tools/cli` and `tools/codegen` share the `tools` Cargo
workspace.

See [locating dependencies root](#locating-dependencies-root) for how the root is found.

## Installation

The Rust toolchain is built into moon, so no [`plugin`](/moon/api/ToolchainPluginConfig#plugin) locator is required. Enable
it by adding a `rust` entry to [`.moon/toolchains.config`](<../(fundamentals)/toolchain.mdx>), or by running
[`moon toolchain add`](../commands/toolchain/add.mdx), which writes the entry for you.

```shell
# Add the Rust toolchain, answering each prompt
$ moon toolchain add rust

# Add the Rust toolchain with default settings
$ moon toolchain add rust --yes
```

When adding the toolchain, moon also asks whether to enable [`syncToolchainConfig`](#syncing-rust-toolchaintoml), which
`--yes` enables and `--minimal` skips.

<ConfigTabs
  file=".moon/toolchains"
  config={{
    rust: {
      version: "1.90.0",
    },
  }}
/>

Configure a [`version`](/moon/api/ToolchainPluginConfig#version) to have moon install Rust for you (see
[tool management](#tier-3-tool-management)).

## Configuration

The following settings are available under the `rust` entry of
[`.moon/toolchains.config`](<../(fundamentals)/toolchain.mdx>).

- `addMsrvConstraint` <TypeLabel type="boolean" /> - When `version` is also defined, writes it as the minimum supported Rust
  version (MSRV) in the dependencies root's `Cargo.toml`. Defaults to `false`. See
  [minimum supported Rust version](#minimum-supported-rust-version).
- `bins` <TypeLabel type="(string | { bin: string, args?: string[], force?: boolean, local?: boolean })[]" /> - A list of Cargo binaries to
  install globally with `cargo-binstall`, such as `cargo-nextest` or `cargo-insta`. An entry can be a crate name, optionally
  with a version (`cargo-nextest@0.9.100`), or an object with the following fields. Defaults to `[]`. See
  [Cargo binaries](#cargo-binaries).
  - `args` <TypeLabel type="string[]" /> - Additional arguments to pass to `cargo binstall` for this binary. Defaults to `[]`.
  - `bin` <TypeLabel type="string" /> - The crate name, optionally with a version. Required.
  - `force` <TypeLabel type="boolean" /> - Always install the binary, even if it already exists. Defaults to `false`.
  - `local` <TypeLabel type="boolean" /> - Only install the binary locally, and skip it in CI. Defaults to `false`.
- `binstallVersion` <TypeLabel type="string" /> - The fully-qualified version of `cargo-binstall` to install when it's
  missing. Not set by default, so the latest version is installed. See [Cargo binaries](#cargo-binaries).
- `components` <TypeLabel type="string[]" /> - A list of rustup components to install, like `clippy`, `rustfmt`, or
  `rust-src`. Defaults to `[]`. See [components and targets](#components-and-targets).
- `syncToolchainConfig` <TypeLabel type="boolean" /> - When `version` is also defined, writes it to the `toolchain.channel`
  field in `rust-toolchain.toml`. Defaults to `false`. See [syncing `rust-toolchain.toml`](#syncing-rust-toolchaintoml).
- `targets` <TypeLabel type="string[]" /> - A list of target triples to install with rustup, like `wasm32-unknown-unknown`
  or `x86_64-unknown-linux-musl`. Defaults to `[]`. See [components and targets](#components-and-targets).
- [`version`](/moon/api/ToolchainPluginConfig#version) <TypeLabel type="string" /> - The version of Rust to download and
  install through proto. When not defined, the `cargo` binary on your `PATH` is used. Accepts a Rust release or a rustup
  channel (see [installing with proto](#installing-with-proto)).

<ConfigTabs
  file=".moon/toolchains"
  config={{
    rust: {
      version: "1.90.0",
      syncToolchainConfig: true,
      components: ["clippy", "rustfmt"],
      targets: ["wasm32-unknown-unknown"],
      bins: ["cargo-nextest", { bin: "cargo-insta", local: true }],
    },
  }}
/>

### Project overrides

Projects can override these settings with the `rust` entry of the [`toolchains`](/moon/api/ProjectConfig#toolchains) setting
in their [`moon.config`](<../(fundamentals)/project.mdx>), as described in
[project overrides](<../(fundamentals)/toolchain.mdx#project-overrides>).

<ConfigTabs
  file="moon"
  config={{
    toolchains: {
      rust: {
        version: "1.89.0",
        targets: ["wasm32-unknown-unknown"],
      },
    },
  }}
/>

As with the workspace `version`, rustup decides which toolchain actually runs, so pair a `version` override with a
`rust-toolchain.toml` in the project (see [caveats](#caveats)).

## Core features

### Syncing `rust-toolchain.toml`

Writes the configured `version` to the `rust-toolchain.toml` file in the dependencies root, so rustup, your editor, and
anyone running Cargo directly use the same toolchain as moon. Enable it with the `syncToolchainConfig` setting, and it runs
when moon [sets up the environment](#setting-up-the-environment).

Tasks run `cargo`, `rustc`, and friends through the rustup proxies in Cargo's bin directory (`~/.cargo/bin`), which means
rustup decides which installed toolchain actually runs. rustup uses the closest `rust-toolchain.toml` file (searching upwards
from the working directory), and otherwise falls back to your default toolchain. moon installs the configured `version`, but
doesn't read `rust-toolchain.toml` when running tasks, so the two can drift apart without this setting.

<ConfigTabs
  file=".moon/toolchains"
  config={{
    rust: {
      version: "1.90.0",
      syncToolchainConfig: true,
    },
  }}
/>

```toml title="rust-toolchain.toml"
[toolchain]
channel = "1.90.0"
```

When enabled, a legacy `rust-toolchain` file in the dependencies root is also converted to `rust-toolchain.toml`. Its
contents become the `toolchain.channel` field, or the file is renamed if it already contains a `[toolchain]` table.

<Callout type="warning">
  moon updates an existing `rust-toolchain.toml` (or converts a legacy
  `rust-toolchain` file), but doesn't create one from scratch. If neither file
  exists when `version` is configured, setting up the environment fails, so
  create a `rust-toolchain.toml` with an empty `[toolchain]` table before
  enabling this setting.
</Callout>

### Minimum supported Rust version

Writes the configured `version` as the [minimum supported Rust version](https://doc.rust-lang.org/cargo/reference/rust-version.html)
(MSRV) in the dependencies root's `Cargo.toml`, so Cargo reports a clear error when someone builds with an older toolchain.
Enable it with the `addMsrvConstraint` setting (it also requires `version`), and it runs when moon
[sets up the environment](#setting-up-the-environment).

- For a Cargo workspace, the version is written to `workspace.package.rust-version`, which members can inherit with
  `rust-version.workspace = true`.
- For a standalone crate, or a root package that doesn't inherit `rust-version` from the workspace, the version is written
  to `package.rust-version`.

The value is written without being resolved, so use a fully-qualified version like `1.90.0`, not a partial version or a
channel.

<ConfigTabs
  file=".moon/toolchains"
  config={{
    rust: {
      version: "1.90.0",
      addMsrvConstraint: true,
    },
  }}
/>

```toml title="Cargo.toml"
[workspace]
members = ["crates/*"]

[workspace.package]
rust-version = "1.90.0"
```

### Components and targets

Installs [rustup components](https://rust-lang.github.io/rustup/concepts/components.html), like `clippy` and `rustfmt`, and
[compilation targets](https://doc.rust-lang.org/rustc/platform-support.html), like `wasm32-unknown-unknown`, so every machine
has the tools your tasks expect. Enable it with the `components` and `targets` settings, and it runs when moon
[sets up the environment](#setting-up-the-environment).

<ConfigTabs
  file=".moon/toolchains"
  config={{
    rust: {
      components: ["clippy", "rustfmt", "rust-src"],
      targets: ["wasm32-unknown-unknown"],
    },
  }}
/>

moon runs `rustup component add` and `rustup target add` in the dependencies root, so they're added to whichever toolchain
rustup resolves there. This is another reason to enable [syncing `rust-toolchain.toml`](#syncing-rust-toolchaintoml).

### Cargo binaries

Installs Cargo binaries, like `cargo-nextest` or `cargo-insta`, into Cargo's bin directory with
[`cargo-binstall`](https://github.com/cargo-bins/cargo-binstall), which downloads prebuilt binaries instead of compiling
them. Enable it with the `bins` setting, and it runs when moon [sets up the environment](#setting-up-the-environment).

<ConfigTabs
  file=".moon/toolchains"
  config={{
    rust: {
      bins: ["cargo-nextest@0.9.100", { bin: "cargo-insta", local: true }],
    },
  }}
/>

- If `cargo-binstall` isn't in Cargo's bin directory yet, moon first installs it with
  `cargo install cargo-binstall --force --locked`, pinned to `binstallVersion` when set.
- Binaries are then installed with `cargo binstall --no-confirm`.
- Binaries that already exist in Cargo's bin directory are skipped, unless `force` is enabled. Binaries marked as `local`
  are skipped in CI.
- Binaries with `args` are installed individually, with the arguments placed before the crate name, as they would
  otherwise apply to every crate in the command.

Installed `cargo-<name>` binaries can also be run as task commands without the `cargo-` prefix (see
[extending tasks](#extending-tasks)).

## Tier 1: Syncing and usage detection

### Project and task detection

A project is associated with the Rust toolchain when its root directory contains any of the following files: `Cargo.toml`,
`Cargo.lock`, `rust-toolchain.toml`, `rust-toolchain`, or a `.cargo/*.toml` file (like `.cargo/config.toml`). Unless the
project configures a [`language`](/moon/api/ProjectConfig#language), its language is detected as `rust`. Projects that set
`language` to `rust` are associated with the Rust toolchain as well.

A task is associated with the Rust toolchain when its command (or the first word of its script) is `cargo`, `rustc`,
`rustdoc`, `rustfmt`, or `rustup`.

### Docker integration

The Rust toolchain integrates with the following steps of the [Docker workflow](../guides/docker.mdx):

- [`moon docker scaffold`](../commands/docker/scaffold.mdx) - Copies `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`,
  `rust-toolchain`, and `.cargo/*.toml` files. Because Cargo refuses to load a manifest without a build target, it also
  creates an empty placeholder for each of a Rust project's library and binary targets within `src` (like `src/lib.rs`
  or `src/main.rs`), so Cargo commands work before sources are copied.
- [`moon docker file`](../commands/docker/file.mdx) - Uses `rust:<version>` (or `rust:latest` when no version is configured)
  as the default base image.
- [`moon docker prune`](../commands/docker/prune.mdx) - Deletes the `target` directory in the dependencies root, but
  preserves binaries built by the workspace's packages (found with `cargo metadata`) in `target/release` and `target/debug`,
  so the image can still run them. Cargo has no production-only install, so it then only runs `cargo generate-lockfile` when
  the dependencies root has no `Cargo.lock`.

### Version detection

When running [`moon toolchain add`](../commands/toolchain/add.mdx), moon detects the Rust version from the following files,
and uses the first match:

1. `rust-toolchain.toml` - The `toolchain.channel` field.
2. `rust-toolchain` - The file's contents, in the legacy plain text format.

## Tier 2: Ecosystem integration

### Extending projects

When building the [project graph](<../(fundamentals)/project-graph.mdx>), moon asks the Rust toolchain to extend each project
with information from its `Cargo.toml`:

- **Alias** - The `package.name` becomes a project [alias](<../(fundamentals)/project.mdx#aliases>), so the project can be
  referenced by it wherever a project ID is accepted. For example, a crate named `api_client` can be referenced as
  `api_client`.
- **Dependencies** - Local `path` dependencies on crates that are moon projects become implicit
  [project dependencies](<../(fundamentals)/project.mdx#dependencies>), scoped as `production` for `[dependencies]`,
  `development` for `[dev-dependencies]`, and `build` for `[build-dependencies]`. Registry and git dependencies are ignored.

Only manifests that define a `[package]` table are used, so virtual workspace manifests are skipped. For example, the
following manifest makes `server` depend on `utils` (production) and `test-utils` (development), without any
[`dependsOn`](/moon/api/ProjectConfig#dependson) configuration.

```toml title="crates/server/Cargo.toml"
[package]
name = "server"
version = "0.1.0"

[dependencies]
serde = "1"
utils = { path = "../utils" }

[dev-dependencies]
test-utils = { path = "../test-utils" }
```

### Extending tasks

- **Commands** - When a task that uses the Rust toolchain runs a [`command`](/moon/api/TaskConfig#command) that's a Cargo
  subcommand, it's run through `cargo`. If the command isn't `cargo`, `rls`, or a `rust*` binary, and a matching
  `cargo-<name>` binary exists in Cargo's bin directory (`$CARGO_INSTALL_ROOT/bin`, `$CARGO_HOME/bin`, or `~/.cargo/bin`),
  the task is rewritten to `cargo <name> ...`.

For example, both of the following tasks run `cargo nextest run` when `cargo-nextest` is installed (see
[Cargo binaries](#cargo-binaries)).

<ConfigTabs
  file="moon"
  config={{
    tasks: {
      test: {
        command: "nextest run",
      },
      testAlt: {
        command: "cargo-nextest run",
      },
    },
  }}
/>

### Locating dependencies root

The dependencies root is the directory where Cargo resolves dependencies, and where the `Cargo.lock` lives. Cargo resolves
dependencies for a whole workspace at once, with a single `Cargo.lock` and `target` directory, and moon mirrors that. For each
project, moon walks up from the project's root looking for each of the following in order, and uses the first directory it
finds:

1. A directory containing a `Cargo.lock`.
2. A `Cargo.toml` that defines a `[workspace]` table.
3. A `Cargo.toml` that defines a `[package]` table (a standalone crate).

When the root is a Cargo workspace, a project is a member if it's the root, or its path matches one of the
`workspace.members` globs (and none of the `workspace.exclude` globs).

### Installing and deduping dependencies

Before running a task that uses the Rust toolchain, moon installs dependencies in the project's
[dependencies root](#locating-dependencies-root):

```shell
# Generate a lockfile, when Cargo.lock doesn't exist
$ cargo generate-lockfile
```

Cargo doesn't have a separate install step, as it downloads crates on demand when building. As such, this step only
generates a `Cargo.lock` when the dependencies root doesn't have one, and otherwise runs nothing.

moon re-installs when the `Cargo.lock`, the dependencies in `Cargo.toml` files, or the toolchain's settings change, and
always when `target` doesn't exist yet.

### Parsing manifest and lock files

When hashing a task, moon parses the project's `Cargo.toml`, and resolves each dependency it declares against the
`Cargo.lock` in the [dependencies root](#locating-dependencies-root). The resolved checksum (or version, for crates without a
checksum) is included in the task's hash, so upgrading a dependency only invalidates the tasks of projects that declare it.

- Dependencies are read from the `[dependencies]`, `[dev-dependencies]`, and `[build-dependencies]` tables. Target-specific
  tables, like `[target.'cfg(unix)'.dependencies]`, aren't read.
- Entries in `[dependencies]` that use `workspace = true` take their version requirement from `[workspace.dependencies]` in
  the root manifest. Inherited dev and build dependencies aren't resolved, and are skipped (see [caveats](#caveats)).
- Dependencies without a version requirement, like `path` and `git` dependencies without a `version`, are skipped.

### Setting up the environment

Before installing dependencies, moon sets up the Rust environment in each [dependencies root](#locating-dependencies-root),
which syncs configuration files and installs extra tooling.

Each step only runs when its setting is configured, in the following order:

1. Writes `version` to `rust-version` in `Cargo.toml`, when `addMsrvConstraint` is enabled (see
   [minimum supported Rust version](#minimum-supported-rust-version)).
2. Writes `version` to `rust-toolchain.toml`, when `syncToolchainConfig` is enabled (see
   [syncing `rust-toolchain.toml`](#syncing-rust-toolchaintoml)).
3. Installs `components` with `rustup component add`, and `targets` with `rustup target add` (see
   [components and targets](#components-and-targets)).
4. Installs missing `bins` with `cargo binstall`, installing `cargo-binstall` first when needed (see
   [Cargo binaries](#cargo-binaries)).

### Hashing task content

When hashing a task that uses the Rust toolchain, moon also includes the following in the task's hash:

- The host operating system, architecture, and libc. Compiled Rust artifacts are platform specific, so cache entries are
  never shared across platforms (for example, macOS locally and Linux in CI).

## Tier 3: Tool management

### Installing with proto

When a [`version`](/moon/api/ToolchainPluginConfig#version) is configured, moon installs Rust through
[proto](../../../proto/docs/index.mdx), with [rustup](https://rustup.rs). Versions that are already installed are reused.

- The version can be a Rust release (`1.90.0`), a partial version (`1.90`) that resolves to the latest matching release, or
  a rustup channel: `stable`, `beta`, `nightly`, or a dated nightly like `nightly-2025-06-01`. Channels are passed to rustup
  as-is.
- If `rustup` isn't found, moon downloads and runs the official rustup installer (from `sh.rustup.rs`, or `win.rustup.rs` on
  Windows) with `--default-toolchain none`, so no default toolchain is installed or changed.
- If the toolchain isn't installed yet, moon runs `rustup toolchain install <version>-<host triple>`. A broken (empty)
  toolchain directory is uninstalled and reinstalled.
- Toolchains are installed into rustup's own directory (`~/.rustup/toolchains`, or `$RUSTUP_HOME/toolchains`) instead of
  proto's store, so they're shared with your regular rustup usage, and no proto shims are created.

For tasks that use the Rust toolchain, moon prepends Cargo's bin directories (`$CARGO_INSTALL_ROOT/bin` and
`$CARGO_HOME/bin` when those variables are set, and `~/.cargo/bin`) to `PATH`, ahead of the installed toolchain's `bin`
directory. As a result, `cargo` and `rustc` run through rustup's proxies, so rustup picks the toolchain (see
[syncing `rust-toolchain.toml`](#syncing-rust-toolchaintoml)).

## Caveats

- **Configuring `version` doesn't pin the toolchain that runs.** rustup's proxies choose the toolchain, so without a matching
  `rust-toolchain.toml`, tasks run your default toolchain. This also applies to a project's `version` override. On a machine
  where moon installed rustup (such as a fresh CI runner), there may be no default toolchain at all, in which case rustup
  errors instead. Enable [`syncToolchainConfig`](#syncing-rust-toolchaintoml) to keep them aligned.
- **Nested Cargo workspace roots aren't scaffolded unless they're projects.**
  [`moon docker scaffold`](../commands/docker/scaffold.mdx) only copies files from the workspace root and each project's
  root, so the `Cargo.toml` and `Cargo.lock` of a Cargo workspace like `tools` in the
  [nested layout](#nested-crates-and-workspaces) are left out. Map that directory to a project, or add its files to
  [`docker.scaffold.configsPhaseGlobs`](/moon/api/DockerScaffoldConfig#configsphaseglobs).
- **Docker pruning only preserves `release` and `debug` binaries.** Binaries built with a custom profile or for an explicit
  `--target` (like `target/x86_64-unknown-linux-musl/release`) are deleted along with the rest of `target`. A custom target
  directory (`CARGO_TARGET_DIR` or `build.target-dir`) isn't pruned at all. Disable
  [`docker.prune.deleteVendorDirectories`](/moon/api/DockerPruneConfig#deletevendordirectories) if you need these.
- **Some dependencies aren't included in task hashes.** Dev and build dependencies that use `workspace = true`, dependencies
  in target-specific tables, and git dependencies without a `version` aren't resolved against `Cargo.lock`, so upgrading them
  doesn't invalidate the cache. Add the root `Cargo.lock` to the task's [inputs](<../(fundamentals)/task.mdx#inputs>) if
  these matter.
- **Only direct `path` dependencies become project relationships.** Dependencies inherited from the workspace
  (`utils = { workspace = true }`), even when `[workspace.dependencies]` declares a `path`, aren't linked. Neither are
  dependencies in target-specific tables (`[target.'cfg(unix)'.dependencies]`), or renamed dependencies whose key doesn't
  match the crate's `package.name`. Declare those relationships with [`dependsOn`](/moon/api/ProjectConfig#dependson).
- **`moon teardown` affects rustup globally.** Toolchains live in rustup's shared directory, so tearing down removes that
  toolchain for every project on the machine, not only this workspace.
- **Crates aren't pre-fetched.** Since installing dependencies only generates a lockfile, crates are downloaded by the first
  Cargo command that needs them. In a `Dockerfile`, run `cargo fetch` after
  [`moon docker setup`](../commands/docker/setup.mdx) if you want crates cached in their own layer.
- **Installing `cargo-binstall` compiles from source.** The first environment setup with `bins` runs
  `cargo install cargo-binstall`, which can take a few minutes. Pre-install `cargo-binstall` in CI images to avoid the delay.
