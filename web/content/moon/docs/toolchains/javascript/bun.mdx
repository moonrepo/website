The Bun toolchain integrates [Bun](https://bun.com) into moon. Bun is a JavaScript runtime and a
package manager in a single binary, and moon supports it in both roles: running tasks with `bun`,
and installing `node_modules` with `bun install`.

The `bun` toolchain itself is intentionally small. It detects which projects and tasks use Bun,
passes [`executeArgs`](#task-commands) to `bun` task commands, provides Docker defaults, and
downloads and installs a pinned version of Bun through [proto](../../../../proto/docs/index.mdx).
Everything that involves your dependencies (locating workspaces, installing and deduping, parsing
`bun.lock`, inferring project relationships and tasks from `package.json`) is implemented by the
[JavaScript toolchain](./index.mdx), which uses Bun when its `packageManager` setting is
`bun`.

Enable it whenever your repository runs code with Bun, installs dependencies with Bun, or both:

| Setup                                              | Toolchains                                           | `packageManager`         |
| -------------------------------------------------- | ---------------------------------------------------- | ------------------------ |
| Bun as the runtime and package manager             | `javascript`, `bun`                                  | `bun`                    |
| Node.js as the runtime, with Bun for installs      | `javascript`, `node`, `bun`                          | `bun`                    |
| Bun as a runtime, with npm, pnpm, or Yarn installs | `javascript`, `node`, `bun`, and the package manager | `npm`, `pnpm`, or `yarn` |

Bun is a standalone binary, so when it's the package manager, the JavaScript toolchain doesn't
require the [Node.js toolchain](./node.mdx). Only enable `node` if some of your tasks run `node`
directly.

## Prerequisites

- **Bun** - If you configure a [`version`](/moon/api/ToolchainPluginConfig#version), moon installs
  Bun for you. Otherwise, a `bun` binary must be available on your `PATH`.
- **The [JavaScript toolchain](./index.mdx)** - Required to install dependencies, and for
  everything else that involves `package.json` and `bun.lock`. The Bun toolchain on its own never
  runs `bun install`.
- **Supported platforms** - When moon installs Bun, prebuilt binaries are available for Linux (x64
  and arm64), macOS (x64 and arm64), and Windows (x64 since Bun v1.1, and arm64 since Bun v1.3.10).
  musl-based Linux distributions, like Alpine, require Bun v1.1.35 or newer.
- **A recent Bun for the best install behavior** - Some behavior depends on the configured
  `version`: v1.2.20+ to install with `bun ci` in CI, and v1.4+ for `bun dedupe` and focused installs
  that include workspace dependencies. See [dependency installation](#dependency-installation).
- **`bun` on `PATH` for `bun.lockb`** - The legacy binary lockfile can only be read by Bun itself.
  See [lockfiles](#lockfiles).

### Repository structure

When `packageManager` is `bun`, the JavaScript toolchain locates each project's _dependencies root_,
the directory where `bun install` runs, by walking up from the project's directory and stopping at
the first match:

1. A directory containing a `bun.lock` or `bun.lockb`.
2. A directory containing a `package.json` with a `workspaces` field.
3. A directory containing a `package.json`.

An optional `bunfig.toml` lives alongside the lockfile, and is read by Bun itself.

#### Single package

A single `package.json` at the repository root, typical of a polyrepo. The root is both the only
project and the dependencies root.

```text
/
├── .moon/
├── src/
├── bun.lock
├── bunfig.toml
└── package.json
```

#### Bun workspaces

A monorepo where the root `package.json` declares its members in `workspaces`, and a single
`bun.lock` at the root is shared by every package. Each package is installed by a single action at
the root.

```text
/
├── .moon/
├── apps/
│   └── web/
│       └── package.json
├── packages/
│   └── utils/
│       └── package.json
├── bun.lock
└── package.json
```

The `workspaces` field can be an array of globs, or an object with `packages`. Bun's `catalog` and
`catalogs` are read from the same `package.json`, either at the top level or within `workspaces`,
so that `catalog:` versions can be resolved when hashing tasks.

```json title="package.json"
{
  "name": "acme",
  "private": true,
  "workspaces": {
    "packages": ["apps/*", "packages/*"],
    "catalog": {
      "react": "^19.0.0"
    }
  }
}
```

Workspaces in a sub-directory, and isolated packages with their own `bun.lock`, are supported as
well. Refer to the [JavaScript toolchain](./index.mdx) for how projects map to dependencies
roots.

When Bun is only used as a runtime, your package manager's lockfile and workspace configuration
determine the structure instead, and Bun has no requirements of its own.

## Installation

Enable the toolchain with [`moon toolchain add`](../../commands/toolchain/add.mdx). To use Bun as the
package manager, add the JavaScript toolchain as well.

```shell
# Add Bun as the runtime and package manager
$ moon toolchain add javascript
$ moon toolchain add bun

# Add Bun with default settings, without prompting
$ moon toolchain add bun --yes
```

When adding `bun`, moon detects the version to pin from a `.bumrc`, `.bun-version`, or
`package.json` in the current directory (see [version detection](#version-detection)), and
otherwise prompts for one. When adding `javascript`, moon sets `packageManager` to `bun` if the
`packageManager` field in `package.json` is set to Bun (like `"bun@1.3.5"`), or if a `bun.lock` or
`bun.lockb` exists.

The result in [`.moon/toolchains.config`](<../../(fundamentals)/toolchain.mdx>) looks like the
following. As Bun is a built-in toolchain, no `plugin` locator is required.

<ConfigTabs
  file=".moon/toolchains"
  config={{
    javascript: {
      packageManager: "bun",
    },
    bun: {
      version: "1.3.5",
    },
  }}
/>

To run tasks with Bun while another package manager installs dependencies, enable `bun` next to your
existing setup. In this case, Bun's `installArgs` setting is unused.

<ConfigTabs
  file=".moon/toolchains"
  config={{
    javascript: {
      packageManager: "pnpm",
    },
    node: {
      version: "24.12.0",
    },
    pnpm: {
      version: "10.24.0",
    },
    bun: {
      version: "1.3.5",
    },
  }}
/>

To use the `bun` binary on your `PATH` instead, omit `version`. If `version` isn't set but your root
`.prototools` pins `bun`, moon inherits that version instead, which is controlled by
[`versionFromPrototools`](/moon/api/ToolchainPluginConfig#versionfromprototools).

## Configuration

The following settings are configured within the `bun` entry of
[`.moon/toolchains.config`](<../../(fundamentals)/toolchain.mdx>).

- `executeArgs` <TypeLabel type="string[]" /> - Arguments to pass to `bun` when a task's
  [`command`](/moon/api/TaskConfig#command) is `bun`. They're inserted after the executable, but
  before the task's own arguments. See [task commands](#task-commands). Defaults to `[]`.
- `installArgs` <TypeLabel type="string[]" /> - Arguments to append to the `bun install` (or
  `bun ci`) command that installs dependencies. Only used when the JavaScript toolchain's
  `packageManager` is `bun`. Defaults to `[]`.
- [`version`](/moon/api/ToolchainPluginConfig#version) <TypeLabel type="string" /> - The version of
  Bun to download and install through proto. When not defined, the `bun` binary on your `PATH` is
  used. The version also determines which [install behavior](#dependency-installation) is enabled.

<ConfigTabs
  file=".moon/toolchains"
  config={{
    bun: {
      version: "1.3.5",
      executeArgs: ["--smol"],
      installArgs: ["--no-summary"],
    },
  }}
/>

Dependencies are installed by the `javascript` toolchain, so to disable installs, set
[`installDependencies`](/moon/api/ToolchainPluginConfig#installdependencies) on the `javascript`
entry, not on `bun`.

### Project overrides

Individual projects can override these settings, including `version`, through
[toolchain overrides](<../../(fundamentals)/project.mdx#overrides>) in their
[`moon.config`](<../../(fundamentals)/project.mdx>). For example, to run a project's tasks with an
older Bun and a smaller memory footprint:

<ConfigTabs
  file="moon"
  config={{
    toolchains: {
      bun: {
        version: "1.2.20",
        executeArgs: ["--smol"],
      },
    },
  }}
/>

- Lists replace the workspace-level value instead of merging with it.
- A project's `installArgs` only apply when the project is its own dependencies root, like an
  isolated package with its own `bun.lock`. Members of a workspace are installed together at the
  root, using the workspace-level settings.

## Tiers

The Bun toolchain implements all three tiers of toolchain support, but most of its ecosystem
integration is delegated to the JavaScript toolchain, which runs Bun on its behalf. Run
[`moon toolchain info`](../../commands/toolchain/info.mdx) to inspect them.

```shell
# Show the toolchain's settings and supported tiers
$ moon toolchain info bun
```

### 1) Usage detection

#### Projects

A project is associated with the Bun toolchain when its root contains a `package.json`, `bun.lock`,
`bun.lockb`, or `bunfig.toml`. The toolchain doesn't define a language, so detecting a project's
[`language`](/moon/api/ProjectConfig#language) is left to the JavaScript toolchain.

Since every `package.json` counts, enabling `bun` alongside `node` associates both with every
JavaScript project. Disable the one a project doesn't use with a
[toolchain override](<../../(fundamentals)/project.mdx#overrides>), like `bun: false` or
`node: false`.

#### Tasks

A task is associated with the Bun toolchain when its command is `bun` or `bunx`, unless the task
configures [`toolchains`](/moon/api/TaskConfig#toolchains) explicitly. The JavaScript toolchain
recognizes these commands as well, so these tasks also use the `javascript` toolchain, along with the
toolchains it requires for your `packageManager`. Tasks with any other command, like `vite` or
`tsc`, inherit the toolchains of their project.

This makes it easy to share tasks between every Bun project with
[task inheritance](<../../(fundamentals)/task-inheritance.mdx#scoping-inheritance>):

<ConfigTabs
  file=".moon/tasks/bun"
  config={{
    inheritedBy: {
      toolchains: "bun",
    },
    tasks: {
      test: {
        command: "bun test",
      },
      build: {
        command: "bun build ./src/index.ts --outdir ./dist",
        outputs: ["dist"],
      },
    },
  }}
/>

#### Version detection

When running [`moon toolchain add`](../../commands/toolchain/add.mdx), the version is detected from
the first of the following files that exists in the current directory, and contains a version:

1. `.bumrc` or `.bun-version` - The first line that isn't empty or a comment.
2. `package.json` - The first of the following fields: a `devEngines.runtime` or
   `devEngines.packageManager` entry named `bun`, `volta.bun` (following `volta.extends`),
   `engines.bun`, or `packageManager` (like `bun@1.3.5`).

<Callout>
  These files are only used to detect a version when adding the toolchain. When
  running tasks, moon uses the configured
  [`version`](/moon/api/ToolchainPluginConfig#version) (or the version inherited
  from `.prototools`).
</Callout>

#### Docker

- [`moon docker file`](../../commands/docker/file.mdx) uses `oven/bun:<version>` as the default base
  image, where `<version>` is the configured `version`, or `latest` when not configured. If a
  project also uses another toolchain with a default image, like `node`, configure
  [`docker.file.image`](/moon/api/DockerFileConfig#image) to choose explicitly.
- [`moon docker scaffold`](../../commands/docker/scaffold.mdx) copies `package.json`, `bun.lock`,
  `bun.lockb`, and `bunfig.toml` files into the skeleton, from the workspace root and each project,
  along with `*.js`, `*.cjs`, and `*.mjs` files, which are commonly used by `postinstall` scripts.
  `node_modules` directories are excluded.
- [`moon docker prune`](../../commands/docker/prune.mdx) is handled by the JavaScript toolchain. It
  removes `node_modules` at the dependencies root (when
  [`docker.prune.deleteVendorDirectories`](/moon/api/DockerPruneConfig#deletevendordirectories) is
  enabled), and then installs production dependencies for only the focused projects, filtered by
  their `package.json` names (when
  [`docker.prune.installToolchainDependencies`](/moon/api/DockerPruneConfig#installtoolchaindependencies)
  is enabled).

```shell
# Bun v1.4+, also installs the workspace packages that `@acme/web` depends on
$ bun install --production --filter @acme/web...

# Older versions, or when no version is configured
$ bun install --production --filter @acme/web
```

### 2) Ecosystem integration

The Bun toolchain itself only extends task commands. Everything else in this tier is implemented by
the [JavaScript toolchain](./index.mdx), including project aliases and relationships from
`package.json`, task inference, adding `node_modules/.bin` to `PATH`, syncing, and hashing, and it
applies to Bun like any other package manager. The sections below cover what's specific to Bun.

#### Task commands

When a task's command is `bun`, the `executeArgs` setting is inserted right after the executable.
For example, with the following configuration:

<ConfigTabs
  file=".moon/toolchains"
  config={{
    bun: {
      executeArgs: ["--smol"],
    },
  }}
/>

A task with the command `bun run build` executes as:

```shell
$ bun --smol run build
```

- Only commands that are exactly `bun` are extended, not `bunx`, and not tasks that use a
  [`script`](/moon/api/TaskConfig#script). The task must also use the Bun toolchain.
- The arguments are inserted for every subcommand, like `bun test` or `bun x`, so only use flags
  that Bun accepts before any subcommand.
- When `packageManager` is `bun`, tasks inferred from `package.json` scripts run as
  `bun run <script>`, so they receive `executeArgs` as well.

#### Dependency installation

When `packageManager` is `bun`, the JavaScript toolchain installs dependencies in each dependencies
root before tasks run. Refer to the [JavaScript toolchain](./index.mdx) for when installs run,
and how to skip them. The following commands are used:

- `bun install` - Installs dependencies locally, and in CI when `bun ci` isn't available.
- `bun ci` <VersionLabel version="2.5.3" /> - Installs dependencies in CI, when a `bun.lock` exists
  and the configured `version` is v1.2.20 or newer. Unlike other package managers, Bun doesn't
  freeze the lockfile in CI automatically. `bun ci` is equivalent to
  `bun install --frozen-lockfile`, so it fails when the lockfile is out of date, instead of
  updating it.
- `bun dedupe` <VersionLabel version="2.5.3" /> - Runs after installing, when the JavaScript
  toolchain's `dedupeOnLockfileChange` setting is enabled (the default) and the configured
  `version` is v1.4 or newer. Only runs locally, never in CI, and is skipped on the very first
  install.

```shell
# Locally
$ bun install
$ bun dedupe

# In CI
$ bun ci
```

The `installArgs` setting is appended to `bun install` and `bun ci` (including production installs
for Docker), but not to `bun dedupe`. Settings in `bunfig.toml`, like registries under `[install]`,
still apply, as moon runs Bun's own commands.

Because the JavaScript toolchain requires the Bun toolchain when `packageManager` is `bun`, Bun is
installed before dependencies are. If the `bun` toolchain isn't configured, moon fails with an error
like _"Toolchain javascript requires the toolchain bun, but it has not been configured!"_.

#### Lockfiles

When hashing tasks with the default [`hasher.optimization`](/moon/api/HasherConfig#optimization) of
`accuracy`, the JavaScript toolchain parses the lockfile at the dependencies root, so a task's cache
is invalidated when one of its dependencies resolves to a new version. Both of Bun's lockfile
formats are supported:

- `bun.lock` - The text-based (JSONC) lockfile, and Bun's default since v1.2. It's parsed directly.
  Registry packages are recorded with their resolved version and integrity hash, and workspace
  packages with the `version` from their `package.json`. GitHub (`github:`) dependencies are
  recorded with their integrity hash when the lockfile includes one, while dependencies installed
  from a Git or tarball URL are skipped.
- `bun.lockb` - The legacy binary lockfile. moon runs `bun bun.lockb` in the lockfile's directory,
  which prints its contents in the Yarn v1 lockfile format, and parses that output. This uses the
  `bun` binary on your `PATH`, not the version moon installs.

#### Package manager differences

A few JavaScript toolchain settings behave differently when `packageManager` is `bun`:

- `dependencyVersionFormat` - The `workspace-caret` and `workspace-tilde` formats are written as
  `workspace:*` when syncing project dependencies into `package.json`.
- `syncPackageManagerField` - Doesn't apply to Bun. moon never writes Bun's version to the
  `packageManager` field in `package.json`.
- `inferTasksFromScripts` - Inferred tasks run `bun run <script>`, and use the `javascript` and
  `bun` toolchains.

### 3) Tool management

When a [`version`](/moon/api/ToolchainPluginConfig#version) is configured, moon installs Bun with
proto in a `SetupToolchain` action, which runs before any task that uses the Bun toolchain (and
before dependencies are installed with Bun), and during [`moon setup`](../../commands/setup.mdx). If
the version is already installed, nothing is downloaded. To try another version without editing
configuration, set the `MOON_BUN_VERSION` environment variable, which takes precedence over the
workspace-level `version`.

- Available versions are loaded from the Git tags of the
  [oven-sh/bun](https://github.com/oven-sh/bun) repository, like `bun-v1.3.5`. The `canary` version
  is also supported.
- Prebuilt archives are downloaded from Bun's GitHub releases, and verified against the release's
  `SHASUMS256.txt` checksums (canary releases aren't verified). On x64 Linux machines without AVX2
  support, the `baseline` build is downloaded instead.
- On musl-based Linux, like Alpine, the `musl` build is downloaded. This, along with support for
  Windows on arm64, requires moon <VersionLabel version="2.5.3" />.
- `bun` is the primary executable, and `bunx` is provided as an alias for `bun x`. Use
  [`moon bin`](../../commands/bin.mdx) to locate the installed binary.

```shell
# Print the path to the Bun binary managed by moon
$ moon bin bun
```

For tasks (and toolchain commands) that use the Bun toolchain, moon prepends the installed Bun's
directory and Bun's global binaries directory (`~/.bun/bin`) to `PATH`, and sets the
`PROTO_BUN_VERSION` environment variable. This ensures tasks use the pinned version, and that
packages installed with `bun add --global` can be used as task commands. To use the `bun` binary on
your `PATH` instead, set `MOON_TOOLCHAIN_FORCE_GLOBALS=bun`.

The configured `version` is also included in the hash of every task that uses the Bun toolchain, so
upgrading Bun invalidates their caches.

The toolchain doesn't perform any additional setup or teardown beyond installing Bun.
[`moon teardown`](../../commands/teardown.mdx) uninstalls the configured version from proto.

## Caveats

- **Version-gated behavior needs a configured version.** Without a `version` (or with an alias like
  `latest`), moon can't tell which features are available, and assumes they aren't: dependencies
  are installed with `bun install` in CI, `bun dedupe` never runs, and Docker focused installs omit
  workspace dependencies. Version requirements are compared by their lowest version, so `^1.2` is
  treated as v1.2.0, while `canary` enables everything.
- **Older setups don't freeze the lockfile in CI.** Without `bun ci` (Bun older than v1.2.20, no
  configured `version`, or a `bun.lockb` lockfile), CI installs run `bun install`, which updates an
  out-of-date lockfile instead of failing.
- **Changing Bun settings doesn't reinstall dependencies.** The install action re-runs when the
  lockfile, a `package.json`, or the `javascript` toolchain's settings change, or when
  `node_modules` is missing. Changes to Bun's `installArgs` or `version` apply to the next install,
  so delete `node_modules` (or run `bun install` yourself) to apply them right away.
- **`bun.lockb` requires a global `bun`.** Reading the binary lockfile runs `bun` from your `PATH`,
  so a Bun installed by moon isn't enough on its own. Without a `bun` on `PATH` (or proto's shims),
  hashing tasks fails. Migrating to the text-based `bun.lock` avoids this, and enables `bun ci`.
- **Node.js and Bun side by side.** Both toolchains detect projects by `package.json`, so tasks that
  don't run `node` or `bun` directly inherit both, with both binaries on `PATH`, and both versions
  in their hash. Disable the unused toolchain per project with a
  [toolchain override](<../../(fundamentals)/project.mdx#overrides>), and configure
  [`docker.file.image`](/moon/api/DockerFileConfig#image) when generating a `Dockerfile`.
