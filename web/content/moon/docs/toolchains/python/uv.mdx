The uv toolchain integrates [uv](https://docs.astral.sh/uv/), Astral's fast Python package and project manager, into
moon. With it enabled, moon:

- Downloads, installs, and pins uv through [proto](../../../../proto/docs/index.mdx), so every developer and CI job runs
  the same version.
- Creates a virtual environment with `uv venv`, and runs `uv sync` before your tasks run, with your own arguments, and
  only when dependencies have changed.
- Supports [uv workspaces](https://docs.astral.sh/uv/concepts/projects/workspaces/), where every member shares one
  lockfile, one virtual environment, and one install.
- Includes the checksums of locked dependencies from `uv.lock` in task hashes, so upgrading a dependency only
  invalidates the tasks that use it.
- Associates projects and tasks with uv, based on their files and commands.
- Copies uv's manifests and lockfiles into Docker skeletons, and installs only production dependencies when pruning.

Enable it whenever your repository manages Python dependencies with uv, typically when it contains a `uv.lock` file.

uv support is shared with the [Python toolchain](./index.mdx), which creates the virtual environment, runs `uv sync`,
and reads `pyproject.toml` and `uv.lock` when its `packageManager` setting is `uv`. This page covers everything that's
specific to uv, wherever it's implemented.

<Callout type="warning">
  The uv toolchain is **unstable**, so it's enabled with the `unstable_uv`
  identifier instead of `uv`. Its settings and behavior may change between moon
  releases.
</Callout>

## Prerequisites

Before enabling the uv toolchain, make sure you have the following:

- **Python toolchain** - The uv toolchain requires the [Python toolchain](./index.mdx), with its `packageManager`
  setting set to `uv`. See [requiring other toolchains](#requiring-other-toolchains).
- **uv** - When [`version`](/moon/api/ToolchainPluginConfig#version) is configured, moon installs uv for you.
  Otherwise, a `uv` binary must be available on your `PATH`.
- **A `pyproject.toml`** - uv installs the dependencies declared in it, and moon uses it (or `uv.lock`) to
  [locate the dependencies root](#locating-dependencies-root).

### Repository structure

The uv toolchain supports the following repository layouts. Directories only become moon
[projects](<../../(fundamentals)/project.mdx>) when they're matched by the [`projects`](/moon/api/WorkspaceConfig#projects)
setting in [`.moon/workspace.config`](<../../(fundamentals)/workspace.mdx>).

#### Single project

The repository is a single uv project, with the workspace root
[registered as a project](<../../(fundamentals)/project.mdx#discovery>).

```text
./
├── .moon/
├── .venv/
├── src/
├── pyproject.toml
└── uv.lock
```

In this layout, the workspace root is the dependencies root, and holds `uv.lock` and the virtual environment. A project
without a lockfile works too, as `uv sync` creates `uv.lock` on the first run.

#### Multiple projects

Each project owns its `pyproject.toml` and `uv.lock`, and gets its own virtual environment and install. Use this instead
of a uv workspace when projects need dependencies that can't be resolved together.

```text
./
├── .moon/
├── apps/
│   └── api/
│       ├── .venv/
│       ├── pyproject.toml
│       └── uv.lock
└── packages/
    └── utils/
        ├── .venv/
        ├── pyproject.toml
        └── uv.lock
```

In this layout, each project is its own dependencies root. moon only installs dependencies for projects whose tasks are
running, and each project can pin a different uv version through [project overrides](#project-overrides) (or a
different Python version through an override of `unstable_python`).

#### uv workspaces

A root `pyproject.toml` defines a [uv workspace](https://docs.astral.sh/uv/concepts/projects/workspaces/), and every
project that matches its `members` globs is a member.

```text
./
├── .moon/
├── .venv/
├── packages/
│   ├── api/
│   │   └── pyproject.toml
│   └── utils/
│       └── pyproject.toml
├── pyproject.toml
└── uv.lock
```

In this layout, the workspace root is the dependencies root of every member, so members share the root's `uv.lock`,
`.venv`, and a single install, and the root doesn't need to be a moon project. This is the most efficient layout for a
monorepo.

See [locating dependencies root](#locating-dependencies-root) for how the root is found.

## Installation

The uv toolchain is built into moon, so no [`plugin`](/moon/api/ToolchainPluginConfig#plugin) locator is required.
Enable it by adding an `unstable_uv` entry to [`.moon/toolchains.config`](<../../(fundamentals)/toolchain.mdx>), or by
running [`moon toolchain add`](../../commands/toolchain/add.mdx), which writes the entry for you.

```shell
# Add the Python toolchain, and select uv as the package manager
$ moon toolchain add unstable_python

# Add the uv toolchain, answering each prompt
$ moon toolchain add unstable_uv

# Add the uv toolchain with default settings
$ moon toolchain add unstable_uv --yes
```

When adding `unstable_python`, `uv` is selected as the package manager automatically if the current directory contains
a `uv.lock` or `uv.toml`, even when Poetry or pip files exist too. If no package manager files exist, you're prompted
to choose one.

<ConfigTabs
  file=".moon/toolchains"
  config={{
    unstable_python: {
      version: "3.13.1",
      packageManager: "uv",
    },
    unstable_uv: {
      version: "0.8.0",
    },
  }}
/>

Both entries are required, as each toolchain requires the other. When one is missing, moon fails with an error like
"Toolchain unstable_python requires the toolchain unstable_uv, but it has not been configured!". Refer to the
[Python toolchain](./index.mdx) for its settings, like `version` and `venvName`.

Configure a [`version`](/moon/api/ToolchainPluginConfig#version) to have moon install uv for you (see
[tool management](#tier-3-tool-management)).

To install with uv's pip interface (`uv pip install`) instead of `uv sync`, see [`uv-pip` mode](#uv-pip-mode).

## Configuration

The following settings are available under the `unstable_uv` entry of
[`.moon/toolchains.config`](<../../(fundamentals)/toolchain.mdx>). The Python toolchain reads `syncArgs` and `venvArgs`
when it creates the virtual environment and installs dependencies, so they only apply when `packageManager` is `uv`
(or `uv-pip`, for `venvArgs`).

- `syncArgs` <TypeLabel type="string[]" /> - Arguments appended to every `uv sync` command, including the production
  install during [`moon docker prune`](../../commands/docker/prune.mdx). Replaces the default arguments below. Defaults
  to `[]`. See [installing and deduping dependencies](#installing-and-deduping-dependencies).
- `venvArgs` <TypeLabel type="string[]" /> - Arguments appended to the `uv venv` command that creates the virtual
  environment. Replaces the default arguments below. Defaults to `[]`. See
  [setting up the environment](#setting-up-the-environment).
- [`version`](/moon/api/ToolchainPluginConfig#version) <TypeLabel type="string" /> - The version of uv to download and
  install through proto. When not defined, the `uv` binary on your `PATH` is used.

When `syncArgs` or `venvArgs` is empty, moon passes its own default arguments to that command instead:

- `--no-managed-python` and `--no-python-downloads` - Only when the Python toolchain has a `version` (configured or
  inherited from `.prototools`). These ensure uv uses the Python that moon installed, instead of a Python that uv
  manages or downloads itself.
- `--no-progress` - Always, to keep the output of moon's actions readable.

Configuring your own arguments _replaces_ these defaults, so include them in your list if you still need them.

<ConfigTabs
  file=".moon/toolchains"
  config={{
    unstable_uv: {
      version: "0.8.0",
      syncArgs: [
        "--all-packages",
        "--no-managed-python",
        "--no-python-downloads",
        "--no-progress",
      ],
    },
  }}
  comments={{
    syncArgs: "Repeats moon's defaults, as custom arguments replace them",
  }}
/>

Dependencies are installed by the Python toolchain, so configure
[`installDependencies`](/moon/api/ToolchainPluginConfig#installdependencies) on `unstable_python`, not `unstable_uv`.

### Project overrides

Projects can override these settings with the `unstable_uv` entry of the
[`toolchains`](/moon/api/ProjectConfig#toolchains) setting in their [`moon.config`](<../../(fundamentals)/project.mdx>),
as described in [project overrides](<../../(fundamentals)/toolchain.mdx#project-overrides>).

<ConfigTabs
  file="moon"
  config={{
    toolchains: {
      unstable_uv: {
        version: "0.7.0",
        syncArgs: [
          "--extra",
          "ml",
          "--no-managed-python",
          "--no-python-downloads",
          "--no-progress",
        ],
      },
    },
  }}
  comments={{
    syncArgs: "Only used when this project is its own dependencies root",
  }}
/>

When disabling `unstable_uv` for a project and the Python toolchain's `packageManager` is `uv`, disable
`unstable_python` for the project as well, as it requires `unstable_uv`.

## Core features

### `uv-pip` mode

Setting the Python toolchain's `packageManager` to `uv-pip` uses uv's
[pip interface](https://docs.astral.sh/uv/pip/) instead of its project interface, for projects that manage dependencies
with requirements files rather than `uv.lock`, but want uv's speed. Enable it with the `packageManager` setting of
`unstable_python`, and it runs when setting up the environment and installing dependencies.

<Callout type="warning">
  `uv-pip` doesn't currently work. The Python toolchain requires a toolchain
  named `unstable_uv-pip` for it, which isn't a built-in toolchain, so moon
  fails with an error like "Toolchain unstable_python requires the toolchain
  unstable_uv-pip, but it has not been configured!". Use `uv` instead.
</Callout>

It differs from `uv` as follows:

- **Dependencies root** - Located like with pip: a `pylock.toml` or `requirements.txt` takes priority, then a
  `pyproject.toml` or `requirements.in`. uv workspaces aren't supported.
- **Environment setup** - Uses `uv venv`, with `venvArgs` (or the default arguments) from `unstable_uv`.
- **Installation** - Runs `uv pip install` from the dependencies root, with `-r requirements.txt` (or
  `-r requirements.in`) and `-c constraints.txt` when those files exist, followed by `installArgs` from `unstable_pip`
  (see the [pip toolchain](./pip.mdx)). `syncArgs` and the default arguments aren't used.
- **Production installs** - pip has no concept of production dependencies, so
  [`moon docker prune`](../../commands/docker/prune.mdx) reinstalls everything.

Because settings are read from both toolchains, `unstable_uv` and `unstable_pip` must both be enabled.

<ConfigTabs
  file=".moon/toolchains"
  config={{
    unstable_python: {
      packageManager: "uv-pip",
    },
    unstable_pip: {
      installArgs: ["--compile-bytecode"],
    },
    unstable_uv: {
      version: "0.8.0",
    },
  }}
/>

## Tier 1: Syncing and usage detection

### Project and task detection

A project is associated with the uv toolchain when its root directory contains any of the following files:
`pyproject.toml`, `uv.lock`, or `uv.toml`. Since a `pyproject.toml` alone matches, every Python project with a manifest
is associated with uv while the toolchain is enabled.

A task is associated with the uv toolchain when its command (or the first word of its script) is `uv` (not `uvx`).

Through [requirements](#requiring-other-toolchains), projects and tasks associated with uv are associated with the
Python toolchain as well. When scoping [task inheritance](<../../(fundamentals)/task-inheritance.mdx>) with
[`inheritedBy.toolchains`](/moon/api/InheritedByConfig#toolchains), use the stable `uv` identifier, as inheritance is
matched against stable identifiers.

<ConfigTabs
  file=".moon/tasks/uv"
  config={{
    inheritedBy: {
      toolchains: "uv",
    },
    tasks: {
      test: {
        command: "pytest",
      },
      typecheck: {
        command: "uv run --no-sync mypy .",
      },
    },
  }}
  comments={{
    toolchains: "Not `unstable_uv`!",
  }}
/>

### Docker integration

- [`moon docker scaffold`](../../commands/docker/scaffold.mdx) - Copies `pyproject.toml`, `uv.lock`, and `uv.toml`.
- [`moon docker prune`](../../commands/docker/prune.mdx) - The [Python toolchain](./index.mdx#docker-integration)
  handles this for uv, and installs production dependencies with `uv sync --package <name> --no-dev`, with a
  `--package` argument for the alias (`pyproject.toml` name) of each focused project, followed by `syncArgs` (or the
  default arguments).

### Version detection

When running [`moon toolchain add`](../../commands/toolchain/add.mdx), moon detects the uv version from the following
files, and uses the first match:

1. `uv.toml` - The `required-version` field.
2. `pyproject.toml` - The `required-version` field of the `[tool.uv]` table.

PEP 440 specifiers are converted to moon's version syntax, so `~=0.8` becomes `~0.8`, and `==0.8.0` becomes `=0.8.0`.

```toml title="pyproject.toml"
[tool.uv]
required-version = "==0.8.0"
```

## Tier 2: Ecosystem integration

### Requiring other toolchains

The uv toolchain requires the [Python toolchain](./index.mdx), so Python is set up first.

In turn, the [Python toolchain](./index.mdx#requiring-other-toolchains) requires the uv toolchain when
`packageManager` is `uv`, so Python projects and tasks are associated with uv too, and uv is installed before the
virtual environment is created.

Before a task in a uv project runs, moon:

1. Installs Python, if a version is configured for `unstable_python`.
2. Installs uv, if a version is configured for `unstable_uv`.
3. Creates the virtual environment (see [setting up the environment](#setting-up-the-environment)).
4. Installs dependencies (see [installing and deduping dependencies](#installing-and-deduping-dependencies)).
5. Runs the task.

### Extending projects

The [Python toolchain](./index.mdx#extending-projects) handles this for uv. Only the standard `[project]` table of
`pyproject.toml` is read, so dependencies that are only listed in `[dependency-groups]` or `[tool.uv]`
`dev-dependencies` don't become project dependencies.

For a local package to become a project dependency, list it in `dependencies` by name only, without a version specifier
or URL. Then mark it as a workspace source in `[tool.uv.sources]`, so that uv installs it from the repository:

```toml title="packages/api/pyproject.toml"
[project]
name = "api"
version = "1.0.0"
dependencies = ["utils", "fastapi>=0.115"]

[tool.uv.sources]
utils = { workspace = true }
```

Here, `api` depends on the `utils` project, while `fastapi` is treated as an external package.

### Extending tasks

The [Python toolchain](./index.mdx#extending-tasks) handles this for uv. For every command that moon runs with the
Python toolchain, including tasks that run `uv` and the `uv venv` and `uv sync` commands, the virtual environment's
`bin` directory (`Scripts` on Windows) is prepended to `PATH`. That's why tools like `pytest` run without activating the
environment, or wrapping them in `uv run`. If you do use `uv run`, pass `--no-sync`, as moon has already synced the
environment.

### Locating dependencies root

The [Python toolchain](./index.mdx#locating-dependencies-root) handles this for uv when `packageManager` is `uv`.
The dependencies root is the directory with your `uv.lock`, where the virtual environment is created and dependencies
are installed. For each project, moon walks up from the project's root and uses the first directory that contains:

1. A `uv.lock`.
2. Otherwise, a `pyproject.toml` that defines a `[tool.uv.workspace]` table. This is only checked when no directory
   matched the first step.
3. Otherwise, a `pyproject.toml`. This is only checked when no directory matched the previous steps.

If none is found, moon doesn't create an environment or install anything for the project. When the root defines a uv
workspace, only the root and projects matching its `members` globs (and none of its `exclude` globs) belong to it, and
other projects are skipped (see [caveats](#caveats)).

```toml title="pyproject.toml"
[project]
name = "monorepo"
version = "0.0.0"

[tool.uv.workspace]
members = ["packages/*"]
```

### Installing and deduping dependencies

The [Python toolchain](./index.mdx#installing-and-deduping-dependencies) handles this for uv when
`packageManager` is `uv`. It runs the following from the dependencies root, with `syncArgs` appended (or the default
arguments, see [configuration](#configuration)):

```shell
# Install dependencies, with the default arguments when Python has a `version`
$ uv sync --no-managed-python --no-python-downloads --no-progress

# Install dependencies, with `syncArgs` set to `["--all-packages", "--no-progress"]`
$ uv sync --all-packages --no-progress
```

moon re-installs when the `uv.lock`, the dependencies in `pyproject.toml` files, or the Python toolchain's settings
change. Changes to `unstable_uv` settings aren't tracked (see the [Python toolchain's caveats](./index.mdx#caveats)).

### Parsing manifest and lock files

The [Python toolchain](./index.mdx#parsing-manifest-and-lock-files) handles this for uv when `packageManager` is
`uv`. When hashing a task, it parses the `uv.lock` in the dependencies root, and reads the version of every locked
package, along with the SHA-256 checksum of its source distribution, or otherwise of its first wheel. Each requirement
with a version specifier in the `dependencies` field of the project's `[project]` table (like `fastapi>=0.115`) is
resolved against it, and the locked checksum (or the version, if it has no distributions) is included in the task's
hash. Updating a locked dependency only invalidates the tasks of projects that depend on it.

### Setting up the environment

The [Python toolchain](./index.mdx#setting-up-the-environment) handles this for uv when `packageManager` is `uv` or
`uv-pip`. It creates the virtual environment in the dependencies root, with `venvArgs` appended (or the default
arguments, see [configuration](#configuration)):

```shell
# Create the virtual environment, from the dependencies root
$ uv venv .venv
```

The directory name is the Python toolchain's `venvName` (`.venv` by default). `uv sync` then installs into this
environment, as uv uses the `.venv` in the project or workspace root by default.

If the directory already exists, it's left as-is. To recreate it whenever moon re-runs environment setup, for example
after the Python `version` changes, add `--clear` to `venvArgs`, along with the default arguments. Adding `--clear`
itself also recreates the environment without reinstalling dependencies, so run `uv sync` yourself once afterwards.

## Tier 3: Tool management

### Installing with proto

When a [`version`](/moon/api/ToolchainPluginConfig#version) is configured, moon installs uv through
[proto](../../../../proto/docs/index.mdx), by downloading a prebuilt archive. Versions that are already installed are
reused.

- Fully-qualified (`0.8.0`) and partial (`0.8`) versions, and the `latest` alias, are resolved against the Git tags of
  the [astral-sh/uv](https://github.com/astral-sh/uv) repository. Canary releases aren't supported.
- Archives are downloaded from uv's GitHub releases for Linux (x64 and arm64, glibc and musl), macOS (x64 and arm64),
  and Windows (x64), and verified against their published SHA-256 checksum.
- uv is installed into proto's store (for example, `~/.proto/tools/uv/0.8.0`), which is shared with proto, so a version
  installed with `proto install uv` is reused.
- The installation provides the `uv` and `uvx` executables, with `uv` as the primary executable.

The `uv venv` and `uv sync` commands that the Python toolchain runs also use the installed uv.

## Caveats

- **`uv-pip` mode fails.** The Python toolchain requires a toolchain named `unstable_uv-pip` for it, which doesn't
  exist, so moon fails with a "requires the toolchain unstable_uv-pip" error. Use `uv` instead. See
  [`uv-pip` mode](#uv-pip-mode).
- **Parent lockfiles take priority.** The search for a `uv.lock` covers every parent directory before a
  `pyproject.toml` is considered. A project without its own `uv.lock`, nested below a directory with one (such as the
  workspace root), resolves to that directory, and won't have dependencies installed for it unless it's a member of
  that directory's uv workspace, even though its tasks use the parent's `.venv`. Add the project to the workspace's
  `members`, or give it its own `uv.lock`.
- **Keep the virtual environment at `.venv`.** uv installs into the `.venv` in the project or workspace root by default.
  If you change the Python toolchain's `venvName`, moon creates the environment with that name, but `uv sync` and
  `uv pip install` still use `.venv`, unless you configure uv to match (for example, with the `UV_PROJECT_ENVIRONMENT`
  environment variable).
- **Only one lockfile is tracked.** Only the first of `pylock.toml`, `constraints.txt`, `requirements.txt`,
  `Pipfile.lock`, `poetry.lock`, or `uv.lock` that exists in the dependencies root is checked for changes. With a
  `requirements.txt` exported with `uv export` next to `uv.lock`, updating only `uv.lock` doesn't trigger a reinstall.
  Run `uv sync` yourself.
- **Settings require `packageManager: "uv"`.** `syncArgs` and `venvArgs` are only read by the Python toolchain when its
  `packageManager` is `uv` (or `uv-pip`, for `venvArgs`). With any other value, or none, they have no effect, and moon
  never runs `uv sync`.
- **Custom arguments replace the defaults.** Setting `syncArgs` or `venvArgs` drops `--no-managed-python`,
  `--no-python-downloads`, and `--no-progress` from that command. Without the first two, uv may use a different Python
  than the one moon installed.
- **Workspace roots only sync themselves.** When the workspace root is a package itself (it has a `[project]` table),
  `uv sync` only installs the root package and its dependencies. Add `--all-packages` to `syncArgs` to install the
  dependencies of every member, and run `uv sync --all-packages` once yourself, as changing `syncArgs` doesn't trigger
  a reinstall.
