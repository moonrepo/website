[uv](https://docs.astral.sh/uv/) is a fast Python package and project manager from Astral. The uv
toolchain lets the [Python toolchain](./index.mdx) use uv as its package manager, and pins the
version of uv that everyone on your team, and CI, runs. With both enabled, moon:

- Creates a virtual environment with `uv venv`, and installs dependencies with `uv sync` before
  your tasks run.
- Supports [uv workspaces](https://docs.astral.sh/uv/concepts/projects/workspaces/), where every
  member shares one lockfile, one virtual environment, and one install.
- Parses `uv.lock`, so locked dependency versions become part of task hashes.
- Detects uv projects (from `pyproject.toml`, `uv.lock`, and `uv.toml`) and uv tasks.
- Optionally downloads and installs a specific uv version through
  [proto](../../../../proto/docs/index.mdx).

The uv toolchain itself is intentionally thin: it provides the uv binary and the arguments for its
commands. The Python toolchain (`unstable_python`) does the rest when its `packageManager` setting
is `uv`, so the two are always enabled together. Behavior that's shared by every Python package
manager, like how tasks find the virtual environment, is covered on the
[Python toolchain](./index.mdx) page.

<Callout type="warning">
  The uv toolchain is **unstable**, so it's enabled with the `unstable_uv`
  identifier instead of `uv`. Its settings and behavior may change between moon
  releases.
</Callout>

## Prerequisites

- **The Python toolchain** - `unstable_python` must be enabled, with `packageManager` set to `uv`.
  The uv toolchain requires it, and moon fails to set up uv without it.
- **uv** - When a [`version`](/moon/api/ToolchainPluginConfig#version) is configured, moon installs
  uv for you (see [tool management](#3-tool-management)). Otherwise, a `uv` binary must be available
  on `PATH`.
- **A supported platform** (moon-managed uv only) - Pre-built binaries are available for Linux (x64
  and arm64), macOS (x64 and arm64), and Windows (x64).

### Repository structure

uv keeps everything next to the root `pyproject.toml`: dependencies are locked in `uv.lock` and
installed into a `.venv` directory. The Python toolchain calls this directory the _dependencies
root_, and locates it for each project by walking up from the project's directory, looking for (in
order of priority):

1. A `uv.lock` file.
2. A `pyproject.toml` that defines a `[tool.uv.workspace]` table.
3. A `pyproject.toml` file.

The virtual environment is created in, and `uv sync` runs from, the located root. The following
layouts are supported.

#### uv workspace

A root `pyproject.toml` defines the workspace, and every project that matches its `members` globs
(and not its `exclude` globs) is a member. This is the most efficient layout for a monorepo.

```text
./
├── .moon/
├── .venv/
├── packages/
│   ├── api/
│   │   └── pyproject.toml
│   └── utils/
│       └── pyproject.toml
├── pyproject.toml
└── uv.lock
```

```toml title="pyproject.toml"
[project]
name = "monorepo"
version = "0.0.0"

[tool.uv.workspace]
members = ["packages/*"]
```

All members share the root's `uv.lock` and `.venv`, and moon runs a single `uv sync` at the root, no
matter how many members are running tasks. The workspace root doesn't need to be a moon project.
Member tasks use the root's virtual environment, as the Python toolchain searches upwards from each
project for the nearest one.

<Callout>
  When the workspace root is a package itself (it has a `[project]` table, like
  above), `uv sync` only installs the root package and its dependencies. Add
  `--all-packages` to [`syncArgs`](#configuration) to install the dependencies
  of every member, and run `uv sync --all-packages` once yourself, as changing
  `syncArgs` doesn't trigger a reinstall.
</Callout>

#### Single project

The repository is a single Python project, typically configured as a root-level project. The
repository root is the dependencies root, and contains the manifest, the lockfile, and the virtual
environment.

```text
./
├── .moon/
├── .venv/
├── src/
├── pyproject.toml
└── uv.lock
```

#### Multiple independent projects

Each project has its own `pyproject.toml` and `uv.lock`, so each is its own dependencies root, with
its own virtual environment and install. Use this when projects need different dependency sets that
can't be resolved together, or a different Python version through
[project overrides](#project-overrides).

```text
./
├── .moon/
├── apps/
│   └── api/
│       ├── .venv/
│       ├── pyproject.toml
│       └── uv.lock
└── tools/
    └── scripts/
        ├── .venv/
        ├── pyproject.toml
        └── uv.lock
```

<Callout type="warning">
  A `uv.lock` in a parent directory takes priority over a project's own
  `pyproject.toml`. If that parent doesn't define a `[tool.uv.workspace]` that
  includes the project, the project resolves to the parent's root without being
  a member, and moon won't install dependencies for it.
</Callout>

## Installation

The toolchain is built into moon, so no `plugin` locator is required. Enable it by adding
`unstable_uv` to [`.moon/toolchains.config`](<../../(fundamentals)/toolchain.mdx>), alongside
`unstable_python` with `packageManager` set to `uv`. Configure a
[`version`](/moon/api/ToolchainPluginConfig#version) to have moon install and pin uv, or leave the
entry empty to use the `uv` on your `PATH`.

<ConfigTabs
  file=".moon/toolchains"
  config={{
    unstable_python: {
      version: "3.13.1",
      packageManager: "uv",
    },
    unstable_uv: {
      version: "0.8.0",
    },
  }}
/>

If `unstable_uv` is missing, moon fails when setting up the environment with an error like
"Toolchain unstable_python requires the toolchain unstable_uv, but it has not been configured!".

Alternatively, run [`moon toolchain add`](../../commands/toolchain/add.mdx) for each toolchain. When
adding `unstable_python` in a directory containing `uv.lock` or `uv.toml`, `packageManager` is set to
`uv` automatically. When adding `unstable_uv`, the version is detected from your uv configuration
(see [version detection](#version-detection)), and otherwise you're prompted for one.

```shell
# Add Python, which selects uv when `uv.lock` or `uv.toml` exists
$ moon toolchain add unstable_python

# Add uv, and pin its version
$ moon toolchain add unstable_uv
```

When `version` isn't set, moon inherits it from the `uv` entry in the root `.prototools` file, as
[`versionFromPrototools`](/moon/api/ToolchainPluginConfig#versionfromprototools) is enabled by
default. The `unstable_` prefix is dropped for this lookup.

```toml title=".prototools"
uv = "0.8.0"
```

To install with uv's pip interface (`uv pip install`) instead of `uv sync`, see
[the `uv-pip` package manager](#the-uv-pip-package-manager).

## Configuration

The following settings can be configured under `unstable_uv` in
[`.moon/toolchains.config`](<../../(fundamentals)/toolchain.mdx>). Settings for the virtual
environment's name and the Python version belong to `unstable_python`, and are documented on the
[Python toolchain](./index.mdx) page.

- `syncArgs` <TypeLabel type="string[]" /> - A list of arguments to append to the `uv sync` command
  that installs dependencies. Defaults to `[]`.
- `venvArgs` <TypeLabel type="string[]" /> - A list of arguments to append to the `uv venv` command
  that creates the virtual environment. Also used by the `uv-pip` package manager. Defaults to `[]`.
- [`version`](/moon/api/ToolchainPluginConfig#version) <TypeLabel type="string" /> - The version of
  uv to download and install through proto. When not defined, the `uv` binary on your `PATH` is
  used.

When `syncArgs` or `venvArgs` is empty, moon passes its own default arguments instead:

- `--no-progress` - Always, to keep the output of moon's actions readable.
- `--no-managed-python` and `--no-python-downloads` - Only when a `version` is configured for
  `unstable_python`. These ensure uv uses the Python that moon installed, instead of a Python that
  uv manages or downloads itself.

Configuring your own arguments _replaces_ these defaults, so include them in your list if you still
need them.

<ConfigTabs
  file=".moon/toolchains"
  config={{
    unstable_uv: {
      version: "0.8.0",
      syncArgs: [
        "--all-packages",
        "--no-progress",
        "--no-managed-python",
        "--no-python-downloads",
      ],
    },
  }}
  comments={{
    syncArgs: "Repeats moon's defaults, as custom arguments replace them",
  }}
/>

### Project overrides

Projects can override any of these settings with
[toolchain overrides](<../../(fundamentals)/project.mdx#overrides>) in their
[`moon.config`](<../../(fundamentals)/project.mdx>). Lists replace the workspace-level list, rather
than extending it.

<ConfigTabs
  file="moon"
  config={{
    toolchains: {
      unstable_uv: {
        syncArgs: [
          "--extra",
          "ml",
          "--no-progress",
          "--no-managed-python",
          "--no-python-downloads",
        ],
      },
    },
  }}
  comments={{
    syncArgs: "Only used when this project is its own dependencies root",
  }}
/>

A project's `version` always applies to its own tasks. However, `syncArgs` and `venvArgs` overrides
are only used when the project is its own dependencies root. Members of a uv workspace share the
root's environment, so it's always created and installed with the workspace-level settings.

## Tiers

The uv toolchain implements usage detection, version detection, and tool management itself. For
ecosystem integration, it only declares its requirements, and the uv-specific behavior described
below is implemented by the Python toolchain when `packageManager` is `uv`.

```shell
# Show the uv toolchain's settings and supported tiers
$ moon toolchain info unstable_uv
```

### 1) Usage detection

#### Projects and tasks

A project is associated with the uv toolchain when its root contains a `pyproject.toml`, `uv.lock`,
or `uv.toml` file. A task that doesn't configure [`toolchains`](/moon/api/TaskConfig#toolchains) is
associated with it when its command is `uv`. Other commands, including `uvx`, inherit their
project's toolchains instead. Because uv requires the Python toolchain, both projects and tasks are
always associated with `unstable_python` as well.

Tasks don't need `uv run` to use the virtual environment. The Python toolchain prepends its `bin`
directory to `PATH`, so tools like `pytest` can be called directly. If you do use `uv run`, pass
`--no-sync`, as moon has already synced the environment.

When scoping [task inheritance](<../../(fundamentals)/task-inheritance.mdx>) with
[`inheritedBy.toolchains`](/moon/api/InheritedByConfig#toolchains), use the stable `uv` identifier,
as inheritance is matched against stable identifiers.

<ConfigTabs
  file=".moon/tasks/uv"
  config={{
    inheritedBy: {
      toolchains: "uv",
    },
    tasks: {
      test: {
        command: "pytest",
      },
      typecheck: {
        command: "uv run --no-sync mypy .",
      },
    },
  }}
  comments={{
    toolchains: "Not `unstable_uv`!",
  }}
/>

#### Version detection

When running [`moon toolchain add`](../../commands/toolchain/add.mdx), the version is detected from
the `required-version` field in `uv.toml`, or in the `[tool.uv]` table of `pyproject.toml`, within
the current directory. PEP 440 specifiers like `==0.8.0` are converted to moon's version syntax.

```toml title="pyproject.toml"
[tool.uv]
required-version = "==0.8.0"
```

#### Docker

[`moon docker scaffold`](../../commands/docker/scaffold.mdx) copies `pyproject.toml`, `uv.lock`, and
`uv.toml` files into the skeleton, so dependencies can be installed before sources are copied.

When running [`moon docker prune`](../../commands/docker/prune.mdx) with
[`docker.prune.installToolchainDependencies`](/moon/api/DockerPruneConfig#installtoolchaindependencies)
enabled, the Python toolchain reinstalls production dependencies only, with `uv sync --no-dev`,
plus a `--package` argument for each focused project (by its `pyproject.toml` name), followed by
`syncArgs` (or the default arguments).

### 2) Ecosystem integration

#### Requirements

The two toolchains require each other, which moon uses to order setup actions:

- `unstable_uv` requires `unstable_python`, so Python is installed before uv.
- `unstable_python` requires `unstable_uv` when `packageManager` is `uv`, so uv is installed before
  the virtual environment is created.

Before a Python task runs, moon installs Python and uv (if versions are configured), creates the
virtual environment, installs dependencies, and then runs the task.

#### Environment setup

Before dependencies are installed, a `SetupEnvironment` action creates the virtual environment in
the dependencies root, using `venvName` from `unstable_python` (`.venv` by default) as the
directory name.

```shell
# Run from the dependencies root, followed by `venvArgs` (or the default arguments)
$ uv venv .venv
```

If the directory already exists, the command is skipped to avoid the overhead of recreating it.
The action itself is also cached, and only runs again when its inputs, like the settings of
`unstable_python`, change. Because this cache doesn't account for the environment on disk, a deleted
or outdated environment isn't repaired (see [caveats](#caveats)).

#### Dependency installation

An `InstallDependencies` [action](<../../(fundamentals)/action.mdx>) then runs `uv sync` in the
dependencies root, before the tasks of any project that resolves to it. Projects that resolve to
the same root, like the members of a uv workspace, share a single action.

```shell
# Run from the dependencies root, followed by `syncArgs` (or the default arguments)
$ uv sync
```

The action is skipped when nothing has changed since the last install, and re-runs when `uv.lock`
changes, when the dependencies in a `pyproject.toml` change, or when the settings of
`unstable_python` change. Changing `unstable_uv` settings, like `syncArgs`, doesn't trigger a
reinstall on its own (see [caveats](#caveats)). Installs are driven by the Python toolchain, so to
disable them, set
[`installDependencies`](/moon/api/ToolchainPluginConfig#installdependencies) to `false` for
`unstable_python` (setting it for `unstable_uv` has no effect).

#### Project relationships

In a uv workspace, members depend on each other by listing a member's name in `dependencies`, and
marking it as a workspace source. The Python toolchain reads `[project]` dependencies _without_ a
version specifier, and turns those that name another project into implicit
[dependencies](<../../(fundamentals)/project.mdx#dependencies>). In the following example, `api`
depends on `utils`. Refer to the [Python toolchain](./index.mdx) page for details.

```toml title="packages/api/pyproject.toml"
[project]
name = "api"
version = "1.0.0"
dependencies = ["utils", "fastapi>=0.115"]

[tool.uv.sources]
utils = { workspace = true }
```

#### Task hashing

The Python toolchain parses `uv.lock` in the dependencies root, and extracts the version and
SHA-256 checksum (from the source distribution, or otherwise the first wheel) of every locked
package. When hashing a task, each dependency in the project's `[project]` `dependencies` with a
version requirement, like `fastapi>=0.115` above, is resolved against the lockfile, and its locked
checksum (or version) is included in the hash. Upgrading a locked package only invalidates the
tasks of projects that declare it.

Lockfiles are only parsed when [`hasher.optimization`](/moon/api/HasherConfig#optimization) in
[`.moon/workspace.config`](<../../(fundamentals)/workspace.mdx>) is `accuracy` (the default).

#### The `uv-pip` package manager

Setting `packageManager` to `uv-pip` <VersionLabel version="2.3.0" /> uses uv's
[pip interface](https://docs.astral.sh/uv/pip/) instead of its project interface. It's intended for
projects that manage dependencies with requirements files rather than `uv.lock`, but want uv's
speed.

<Callout type="warning">
  `uv-pip` doesn't currently work. The Python toolchain requires a toolchain
  named `unstable_uv-pip` for it, which isn't a built-in toolchain, so moon
  fails with an error like "Toolchain unstable_python requires the toolchain
  unstable_uv-pip, but it has not been configured!". Use `uv` instead.
</Callout>

It differs from `uv` as follows:

- **Dependencies root** - Located like with pip: a `pylock.toml` or `requirements.txt` takes
  priority, then a `pyproject.toml` or `requirements.in`. uv workspaces aren't supported.
- **Environment setup** - Uses `uv venv`, with `venvArgs` (or the default arguments) from
  `unstable_uv`.
- **Installation** - Runs `uv pip install` from the dependencies root, with `-r requirements.txt`
  (or `-r requirements.in`) and `-c constraints.txt` when those files exist, followed by
  `installArgs` from `unstable_pip` (see the [pip toolchain](./pip.mdx)). `syncArgs` and the default
  arguments aren't used.
- **Production installs** - pip has no concept of production dependencies, so
  [`moon docker prune`](../../commands/docker/prune.mdx) reinstalls everything.

Because settings are read from both toolchains, `unstable_uv` and `unstable_pip` must both be
enabled.

<ConfigTabs
  file=".moon/toolchains"
  config={{
    unstable_python: {
      packageManager: "uv-pip",
    },
    unstable_pip: {
      installArgs: ["--compile-bytecode"],
    },
    unstable_uv: {
      version: "0.8.0",
    },
  }}
/>

### 3) Tool management

When a [`version`](/moon/api/ToolchainPluginConfig#version) is configured, moon installs uv with
proto in a `SetupToolchain` action, which runs before any task that uses uv, and during
[`moon setup`](../../commands/setup.mdx). Python is always set up first.

- Available versions are loaded from the Git tags of the
  [astral-sh/uv](https://github.com/astral-sh/uv) repository. Canary releases aren't supported.
- Pre-built archives are downloaded from uv's GitHub releases (including glibc and musl builds on
  Linux), and verified against their published SHA-256 checksum.
- The `uv` and `uvx` executables are made available, with `uv` as the primary executable. Use
  [`moon bin`](../../commands/bin.mdx) to locate it.
- uv is installed into proto's store under the `uv` identifier, so a version previously installed
  with `proto install uv` is reused as-is.

```shell
# Print the path to the uv binary managed by moon
$ moon bin uv
```

For tasks and commands that use the uv toolchain, including the Python toolchain's `uv venv` and
`uv sync` commands, moon prepends uv's installation directory to `PATH`, and sets the
`PROTO_UV_VERSION` environment variable. To use the `uv` on your `PATH` instead, set
`MOON_TOOLCHAIN_FORCE_GLOBALS=uv`.

The toolchain doesn't perform any additional setup or teardown.
[`moon teardown`](../../commands/teardown.mdx) uninstalls the configured version from proto, but
leaves virtual environments untouched.

## Caveats

- **Unstable** - The toolchain must be enabled as `unstable_uv`, and its settings may change in
  future releases. Use `uv` in [`inheritedBy.toolchains`](/moon/api/InheritedByConfig#toolchains)
  conditions.
- **Requires the Python toolchain** - Enabling `unstable_uv` on its own doesn't create environments
  or install dependencies. `unstable_python` must be enabled with `packageManager` set to `uv`.
- **Custom arguments replace defaults** - Setting `syncArgs` or `venvArgs` drops `--no-progress`,
  `--no-managed-python`, and `--no-python-downloads`. Without the latter two, uv may use a different
  Python than the one moon installed.
- **Workspace sync scope** - When the workspace root is a package, `uv sync` doesn't install
  member dependencies unless `--all-packages` is in `syncArgs`.
- **uv settings aren't part of the install cache** - Only the settings of `unstable_python` are
  part of the install action's cache key. Changing `syncArgs` or `venvArgs` doesn't trigger a
  reinstall, and only takes effect on the next install, when `uv.lock` or a manifest's dependencies
  change. To apply it immediately, run `uv sync` (with the new arguments)
  yourself.
- **Environments on disk aren't checked** - moon caches environment setup and installs by their
  inputs, not by the state of `.venv`. A deleted environment may not be recreated, and even when it
  is, dependencies aren't reinstalled into it. An existing environment is also never recreated, for
  example when the Python `version` changes. Rebuild it yourself with `uv venv --clear` followed by
  `uv sync`, rather than adding `--clear` to `venvArgs`, which can leave a recreated environment
  empty.
- **Custom `venvName`** - moon creates the environment with the configured name, but `uv sync` and
  `uv pip install` look for `.venv` by default. Keep the default name, or configure uv to match (for
  example, with the `UV_PROJECT_ENVIRONMENT` environment variable).
- **`uv-pip` is broken** - The `uv-pip` package manager fails due to an invalid toolchain
  requirement. See [the `uv-pip` package manager](#the-uv-pip-package-manager).
