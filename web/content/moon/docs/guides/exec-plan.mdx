An execution plan is a JSON file that declaratively configures how [`moon exec`](../commands/exec.mdx),
and the commands built on top of it ([`moon run`](../commands/run.mdx),
[`moon check`](../commands/check.mdx), and [`moon ci`](../commands/ci.mdx)), run tasks. Instead of
passing many command line options, you can define your execution settings in a file and pass it
with a single option, keeping your commands short and your configuration version-controlled.

Plans are especially useful when:

- Your CI pipeline is generated by a script, which can write a plan instead of assembling a long
  command line.
- You want to partition targets across CI jobs by hand, instead of letting moon split them evenly.
- Multiple pipelines or developers should run tasks the exact same way.

## Usage

Pass an execution plan with the `--plan` (or `-p`) option:

```shell
# Run tasks from a plan
$ moon exec --plan plan.json

# Plans are supported by the derived commands as well
$ moon ci --plan plan.json
```

Or set the `MOON_EXEC_PLAN` environment variable:

```shell
# Run tasks from a plan defined in the environment
$ MOON_EXEC_PLAN=plan.json moon exec
```

The path can be relative (resolved against the current working directory) or absolute. The file
must be valid JSON.

When both a plan and command line options are provided, plan values take priority. If targets are
defined in both the plan and the command line, the plan's targets are used and a warning is logged.
If neither defines targets, moon prompts you to select them. Because of this, a plan passed to
`moon ci` should define its targets, as `moon ci` only falls back to every task in the workspace when
no plan is provided.

<Callout>
  The `MOON_BASE` and `MOON_HEAD` environment variables still take precedence
  over the plan's `affected.base` and `affected.head` settings.
</Callout>

## Structure

A plan is a JSON object with four top-level blocks. All blocks are optional and default to safe
values when omitted, so `{}` is a valid plan. Unknown fields are rejected.

```json title="plan.json"
{
  "affected": {},
  "graph": {},
  "pipeline": {},
  "targets": []
}
```

### `targets`

Defines which tasks to run. Accepts the same [target](<../(fundamentals)/target.mdx>) syntax as the
`moon exec` command line (`project:task`, `:task`, `~:task`, `#tag:task`, globs, etc).

In its simplest form, `targets` is an array of target strings:

```json title="plan.json"
{
  "targets": ["app:build", "lib:build"]
}
```

For advanced use cases, `targets` can be an object with one of two strategies:

- **Filtered** - Run the targets in the `include` list, which currently behaves the same as the
  array form.

  ```json title="plan.json"
  {
    "targets": {
      "include": ["app:build", "#frontend:test"]
    }
  }
  ```

- **Partitioned** - Split targets into groups for parallel CI jobs, where each inner array is one
  partition, and each job only runs its own partition.

  ```json title="plan.json"
  {
    "targets": {
      "jobs": [
        ["app:build", "app:test"],
        ["lib:build", "lib:test"]
      ]
    }
  }
  ```

Partitioned targets require both a job index and a job total, from either the plan's
[`pipeline`](#pipeline) block, or the `--job` and `--job-total` options (or the `MOON_JOB` and
`MOON_JOB_TOTAL` environment variables). The number of partitions must match the job total, and
moon errors if either is missing or they don't match.

### `pipeline`

Controls how the pipeline executes tasks.

- `ci` <TypeLabel type="boolean" /> - Force CI mode on or off, which controls
  [`options.runInCI`](/moon/api/TaskOptionsConfig#runinci) checks, workspace syncing, and detecting
  revisions from the CI provider. Defaults to detecting the current environment. Same as `--ci`.
- `ignoreCiChecks` <TypeLabel type="boolean" /> - Ignore each task's `runInCI` setting. Same as
  `--ignore-ci-checks`.
- `noActions` <TypeLabel type="boolean" /> - Skip sync and setup actions, like toolchain
  installation, and only run the requested tasks. Same as `--no-actions`.
- `job` <TypeLabel type="number" /> - Index of the current job (0-based). Same as `--job`.
- `jobTotal` <TypeLabel type="number" /> - Total number of jobs. Same as `--job-total`.

When `job` and `jobTotal` are set without partitioned targets, moon splits the affected targets
evenly across the jobs, the same as passing `--job` and `--job-total`.

<Callout type="warning">
  The `concurrency` and `onFailure` fields are also accepted, but currently have
  no effect. Use the global `--concurrency` option, and the `--on-failure`
  option of `moon exec`, instead.
</Callout>

### `graph`

Controls which task relationships are included in the action graph.

- `upstream` <TypeLabel type="none | direct | deep" /> - Depth of upstream dependencies to include.
  With `deep`, every dependency of a target runs before it, `direct` only includes its immediate
  dependencies, and `none` skips them. Defaults to `deep`. Same as `--upstream`.
- `downstream` <TypeLabel type="none | direct | deep" /> - Depth of downstream dependents to
  include, which helps catch regressions in the tasks that depend on a target. Defaults to `none`,
  or `direct` for `moon ci`. Same as `--downstream`.

### `affected`

Restricts execution to tasks affected by changed files. When this block is present, affected
filtering is enabled, even without passing `--affected`. When omitted, all matched targets run
(except for `moon ci`, which always filters by affected status).

- `base` <TypeLabel type="string" /> - Base branch, commit, or revision to compare against. Defaults
  to [`vcs.defaultBranch`](/moon/api/VcsConfig#defaultbranch). Same as `--base`.
- `head` <TypeLabel type="string" /> - Current branch, commit, or revision to compare with. Defaults
  to `HEAD`, including uncommitted changes. Same as `--head`.
- `includeRelations` <TypeLabel type="boolean" /> - Include graph relations for affected checks,
  instead of just changed files. Same as `--include-relations`.
- `source` <TypeLabel type="local | remote" /> - Where changed files come from. With `local`, only
  uncommitted changes in the working tree are used (unless `base` or `head` is set), while `remote`
  compares the base and head revisions. Defaults to `remote` in CI, and `local` otherwise.
- `status` <TypeLabel type="string[]" /> - Filter changed files by status: `added`, `all`,
  `deleted`, `modified`, `staged`, `unstaged`, or `untracked`. Same as `--status`.
- `stdin` <TypeLabel type="boolean" /> - Accept changed files from stdin. Same as `--stdin`.

## Examples

### Run specific targets

The simplest plan, just list the targets to run:

```json title="plan.json"
{
  "targets": ["app:build", "lib:build"]
}
```

### CI with affected filtering

Only run tests affected by changes between the `main` branch and `HEAD`:

```json title="plan.json"
{
  "affected": {
    "base": "main",
    "source": "remote"
  },
  "pipeline": {
    "ci": true
  },
  "targets": [":test"]
}
```

### Partitioned CI jobs

Split targets across 3 CI jobs. The plan defines the job total, while each job passes its own index
with `--job` (or the `MOON_JOB` environment variable):

```json title="plan.json"
{
  "pipeline": {
    "ci": true,
    "jobTotal": 3
  },
  "targets": {
    "jobs": [
      ["app:build", "app:test"],
      ["lib:build", "lib:test"],
      ["docs:build"]
    ]
  }
}
```

Then in CI, run each partition:

```shell
# Job 0
$ moon exec --plan plan.json --job 0

# Job 1
$ moon exec --plan plan.json --job 1

# Job 2
$ moon exec --plan plan.json --job 2
```

### Deep dependency graph

Build a target along with all of its upstream dependencies and downstream dependents:

```json title="plan.json"
{
  "graph": {
    "upstream": "deep",
    "downstream": "deep"
  },
  "targets": ["core:build"]
}
```

### Full example

Combine all blocks, to run affected tests in CI across partitioned jobs, while also verifying the
direct dependents of each affected task:

```json title="plan.json"
{
  "affected": {
    "base": "main",
    "head": "HEAD",
    "includeRelations": true,
    "source": "remote",
    "status": ["modified", "added"]
  },
  "graph": {
    "upstream": "deep",
    "downstream": "direct"
  },
  "pipeline": {
    "ci": true,
    "jobTotal": 3
  },
  "targets": {
    "jobs": [
      ["app:test", "app:lint"],
      ["#frontend:test"],
      ["lib:test", "core:test"]
    ]
  }
}
```
