[Renovate](https://docs.renovatebot.com/) automates dependency updates by opening pull requests when
new versions are released. Because moon builds on [proto](../../../proto/docs/index.mdx) for
toolchain management, and proto is supported by Renovate out of the box, most moon repositories work
with Renovate with little to no configuration. This guide covers that native support, and how to
extend it to versions pinned in moon's own configuration files.

## Pin versions in `.prototools` (recommended)

The cleanest setup requires **no Renovate configuration and no annotations at all**. Renovate ships a
built-in [`proto` manager](https://docs.renovatebot.com/modules/manager/proto/) that updates tool
versions declared in `.prototools` files automatically, at any depth in the repository.

```toml title=".prototools"
node = "22.18.0"
yarn = "4.16.0"
rust = "1.85.0"
moon = "2.6.4"
```

Because moon toolchains inherit their version from `.prototools` by default (via
[`versionFromPrototools`](/moon/api/ToolchainPluginConfig#versionfromprototools)), you can leave the
`version` out of [`.moon/toolchains.config`](<../(fundamentals)/toolchain.mdx>) entirely and let
proto be the single source of truth:

<ConfigTabs
  file=".moon/toolchains"
  config={{
    node: {},
    rust: {},
  }}
/>

With this approach, Renovate keeps `.prototools` current, and moon resolves toolchain versions from
it. Files that moon derives from those versions, like the
[`packageManager` field](../toolchains/javascript/index.mdx#syncing-the-packagemanager-field) in
`package.json`, are updated the next time moon syncs. No `# renovate:` comments required.

<Callout type="idea">
  If you can, prefer this over hard-coding a `version` in
  `.moon/toolchains.config`. It's the least configuration, and nothing drifts
  out of sync.
</Callout>

Tools that are provided by third-party WASM plugins (configured under `[plugins]` in `.prototools`)
are skipped by Renovate's `proto` manager.

## Versions in moon configuration

If you'd rather pin versions in moon's config files, or you have versions that don't live in
`.prototools` at all (like a toolchain that isn't built into Renovate, or a CI input), moon
publishes a shared Renovate [config preset](https://docs.renovatebot.com/config-presets/) to cover
them.

<Tabs groupId="renovate-setup" items={['Extend the preset (recommended)', 'Inline configuration']}>
<Tab>

```json title="renovate.json"
{
  "$schema": "https://docs.renovatebot.com/renovate-schema.json",
  "extends": ["config:recommended", "github>moonrepo/moon//ecosystem/renovate"]
}
```

</Tab>
<Tab>

If you'd rather not depend on the preset, copy its
[custom managers](https://docs.renovatebot.com/modules/manager/custom/) directly into your
configuration. See the source at
[`ecosystem/renovate.json`](https://github.com/moonrepo/moon/blob/master/ecosystem/renovate.json).

</Tab>
</Tabs>

### Toolchain versions (no annotations)

The preset includes [JSONata managers](https://docs.renovatebot.com/modules/manager/jsonata/) that
read your [`.moon/toolchains.config`](<../(fundamentals)/toolchain.mdx>) _by structure_, so a
[`version`](/moon/api/ToolchainPluginConfig#version) pinned for one of the following toolchains is
updated automatically, with **no comments needed**: `node`, `npm`, `pnpm`, `yarn`, `bun`, `deno`,
`go`, and `rust`.

This works for the YAML (`.yml`, `.yaml`), JSON (`.json`), and TOML (`.toml`) formats, in either
`.moon/` or `.config/moon/`.

<ConfigTabs
  file=".moon/toolchains"
  config={{
    node: {
      version: "22.18.0",
    },
    rust: {
      version: "1.85.0",
    },
  }}
/>

### Other versions

For anything the structural managers don't cover, the preset also includes a regex manager that reads
a trailing `# renovate:` (or `// renovate:`) comment. Add it to the _end of the line_ containing the
version, and point it at a [datasource](https://docs.renovatebot.com/modules/datasource/) and
package. It applies to any `.moon/` (and `.config/moon/`) config,
[`moon.config`](<../(fundamentals)/project.mdx>) project files, and
`.github/workflows/*.yml`, in any comment-supporting format (`yml`, `yaml`, `toml`, `jsonc`, `pkl`,
`hcl`). Strict `json` has no comments.

The comment accepts the following fields, separated by spaces, and in this order:

- `datasource` (required) - The Renovate datasource to look up versions from.
- `depName` (required) - The dependency name, which is also used as the package name.
- `packageName` - The package name to look up, when it differs from `depName`.
- `versioning` - The Renovate versioning scheme. Defaults to `semver`.
- `extractVersion` - A regex that extracts the version from a tag or release name.

For example, to keep a toolchain that isn't covered by the structural managers up to date:

```yaml title=".moon/toolchains.yml"
unstable_python:
  version: "3.12.4" # renovate: datasource=github-tags depName=python/cpython extractVersion=^v(?<version>.*)$
```

Or a version in a CI workflow:

```yaml title=".github/workflows/ci.yml"
- uses: "moonrepo/setup-toolchain@v0"
  with:
    proto-version: "0.58.2" # renovate: datasource=github-releases depName=moonrepo/proto extractVersion=^v(?<version>.*)$
```

In formats that use `//` for comments (JSONC, Pkl, HCL), the `// renovate:` form works the same way:

```jsonc title=".moon/toolchains.jsonc"
{
  "unstable_python": {
    "version": "3.12.4", // renovate: datasource=github-tags depName=python/cpython extractVersion=^v(?<version>.*)$
  },
}
```

To annotate versions in _other_ files, add your own `customManagers` entry with the same
`matchStrings`, and the paths of those files in its `managerFilePatterns`.

### Datasource reference

Useful when annotating a version, or adding a toolchain the structural managers don't cover.

| Tool       | `datasource`      | `depName` / `packageName` | `extractVersion`        |
| ---------- | ----------------- | ------------------------- | ----------------------- |
| node       | `node-version`    | `node`                    |                         |
| npm / pnpm | `npm`             | `npm` / `pnpm`            |                         |
| yarn       | `npm`             | `@yarnpkg/cli`            |                         |
| rust       | `github-tags`     | `rust-lang/rust`          |                         |
| go         | `github-tags`     | `golang/go`               | `^go(?<version>.*)$`    |
| python     | `github-tags`     | `python/cpython`          | `^v(?<version>.*)$`     |
| deno       | `github-releases` | `denoland/deno`           | `^v(?<version>.*)$`     |
| bun        | `github-releases` | `oven-sh/bun`             | `^bun-v(?<version>.*)$` |
| moon       | `github-releases` | `moonrepo/moon`           | `^v(?<version>.*)$`     |
| proto      | `github-releases` | `moonrepo/proto`          | `^v(?<version>.*)$`     |

## Tips and limitations

- **Config format coverage.** Comment-free structural updates work for the `yml`, `yaml`, `json`,
  and `toml` formats; `jsonc`, `pkl`, and `hcl` are updated through `#` or `//` annotations. Strict
  `json` can't hold comments, so pin those toolchains structurally or in `.prototools`.
- **Aliases and ranges are skipped.** Values like `latest`, `stable`, `canary`, or `nightly` can't be
  resolved to a concrete version, and are ignored. Annotated versions default to `semver`
  versioning, which doesn't support ranges, so pin exact versions. For this reason, moon's
  [`versionConstraint`](/moon/api/WorkspaceConfig#versionconstraint) (usually a range like
  `>=2.0.0`) is best updated by hand.
- **Pin each toolchain in one place.** Don't set the same version in both `.prototools` and
  `.moon/toolchains.config` (or add an annotation on top of a structurally-managed version), as
  you'll get duplicate pull requests. A `version` in `.moon/toolchains.config` also takes precedence
  over `.prototools`, so the two can silently disagree.
- **Propagate changes on self-hosted Renovate.** You can run [`moon sync`](../commands/sync.mdx)
  after an update via
  [`postUpgradeTasks`](https://docs.renovatebot.com/configuration-options/#postupgradetasks) to
  include regenerated files, like `package.json`, in the same pull request.
- **Group toolchain updates.** Use
  [`packageRules`](https://docs.renovatebot.com/configuration-options/#packagerules) with a
  `groupName` to batch toolchain bumps into a single pull request.
