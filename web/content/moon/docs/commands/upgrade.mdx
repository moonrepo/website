Checks for a newer version of moon and, if one is available, downloads and installs it in
place of the currently running binary.

The command first requires an internet connection, and queries moon's release manifest for the
latest available version. If the currently installed version is already the latest, moon prints
a notice and exits without doing anything further.

How the upgrade is applied depends on how moon was originally installed:

- If moon was installed through [proto](/proto/docs), the upgrade defers to proto by running
  `proto install moon latest --pin local`, letting proto manage the download and pinning.
- If moon was installed via the official install script (living under `~/.moon`), moon downloads
  the appropriate release archive for your operating system and architecture (accounting for
  `musl` vs `gnu` on Linux), unpacks it into a temporary directory, and replaces the existing
  `moon` and `moonx` executables in place. The previous binaries are moved aside as `.backup`
  files rather than deleted outright, since a running executable can't be removed on most
  platforms. The destination directory can be overridden with the `MOON_INSTALL_DIR` environment
  variable; otherwise it defaults to the `bin` folder inside moon's store.
- If moon was installed some other way (for example, through a system package manager or a
  standalone binary outside of `~/.moon`), moon refuses to upgrade itself and exits with an error,
  since it has no reliable way to locate and replace the binary. In this case you'll need to
  upgrade using whatever mechanism originally installed it.

After a successful upgrade, moon also stops any currently running background
[daemon](../guides/daemon.mdx#lifecycle) so that the next invocation of moon picks up the newly
installed version.

```shell
$ moon upgrade
```

This command can also be run as `moon up`.

To also pin the newly installed version as the workspace's required version, pass
`--update-constraint`:

```shell
$ moon upgrade --update-constraint
```

## Hosting releases yourself

By default, moon checks for new versions against moonrepo's version manifest, and downloads releases
from GitHub. In a restricted network, or to control which version your team upgrades to, point both
at your own servers with the [`moon`](/moon/api/ToolchainsConfig#moon) setting in
[`.moon/toolchains.config`](<../(fundamentals)/toolchain.mdx>):

- [`manifestUrl`](/moon/api/MoonConfig#manifesturl) - A secure (`https://`) URL that returns the
  latest version as JSON, like `{ "current_version": "2.6.4" }`. It can also include a `message` and
  a `url`, which are printed alongside the notice that moon shows when a new version is available.
  Defaults to `https://launch.moonrepo.app/moon/check_version`.
- [`downloadUrl`](/moon/api/MoonConfig#downloadurl) - A secure URL to download a release archive
  from. `{file}` is replaced with the archive's file name, like `moon_cli-aarch64-apple-darwin.tar.xz`
  (or `.zip` on Windows), and `{version}` with the version being installed. Defaults to
  `https://github.com/moonrepo/moon/releases/latest/download/{file}`.

<ConfigTabs
  file=".moon/toolchains"
  config={{
    moon: {
      manifestUrl: "https://moon.example.com/check_version.json",
      downloadUrl: "https://moon.example.com/releases/v{version}/{file}",
    },
  }}
/>

The manifest is used by both `moon upgrade` and the new version notice, while `downloadUrl` is only
used when moon replaces itself, not when it defers to proto.

## Options

- `--update-constraint` - After a successful upgrade, updates the [`versionConstraint`](/moon/api/WorkspaceConfig#versionconstraint) setting in
  the [workspace](<../(fundamentals)/workspace.mdx>) configuration file to require (`^`) the newly installed version.
