Determine which [projects](<../../(fundamentals)/project.mdx>) and [tasks](<../../(fundamentals)/task.mdx>) are affected by changes in the
current [VCS](<../../(fundamentals)/workspace.mdx#version-control-integration>) working tree, and print the result as
JSON, like every other [`moon query`](../query.mdx) subcommand. This is the same affected detection logic used internally by [`moon ci`](../ci.mdx) and
`--affected` flags elsewhere in moon, exposed as a standalone query for scripting and tooling.

Under the hood, this command first collects a list of changed files (from the local index, or a
[comparison between 2 revisions](../../guides/ci.mdx#comparing-revisions), depending on the `[BY]`
argument and your VCS state), then walks the
project and task graphs to determine which nodes are affected by those files, optionally
propagating affected state to the projects and tasks that depend on them. Each task's
[`options.runInCI`](/moon/api/TaskOptionsConfig#runinci) setting is respected, so when running in
CI, tasks that [don't run in CI](../../guides/ci.mdx#configuring-tasks-to-run) are never affected, matching what [`moon ci`](../ci.mdx) would run.

If data is piped into this command via stdin (as produced by
[`moon query changed-files`](./changed-files.mdx)), it's used as the list of changed files instead of
querying the VCS directly, allowing the 2 commands to be composed together.

```shell
# Determine affected projects and tasks based on local changes
$ moon query affected

# Also include the projects and tasks that depend on affected ones
$ moon query affected --dependents deep

# Reuse the output of another query
$ moon query changed-files --status added --status modified | moon query affected
```

The output is a JSON object with a `projects` and `tasks` map, keyed by project ID and task target
respectively. Each entry records why that project or task was marked affected: the changed files
(or environment variables) that triggered it, its affected tasks (for projects), the affected
`dependencies` it was reached through, and its `distance`, the number of hops from a directly
affected project or task (`0` when directly affected). See
[inspecting affected state](../../advanced/affected.mdx#inspecting) for an example.

## Arguments

- `[BY]` - Conditions in which to track affected, as a comma-separated list. Accepts `true` or
  `false` to simply toggle affected tracking, or a string built from the following tokens:
  - `local` / `!remote` - Only consider local, uncommitted changes (`git status`).
  - `remote` / `!local` - Only consider changes between the 2 revisions below, ignoring local
    changes.
  - `<base>` or `<base>:<head>` - The base (and optionally head) revision to diff against, instead
    of the workspace's configured default branch and `HEAD`.

## Options

- `--dependents` <TypeLabel type="none | direct | deep | number" /> - Include the projects and
  tasks that depend on affected ones, up to this many hops away, by propagating affected state to
  them (see [tracking depth](../../advanced/affected.mdx#tracking-depth)). Defaults to `none`.
